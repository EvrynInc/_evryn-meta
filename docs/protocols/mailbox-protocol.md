## 1 · The one rule

> ### 🔴 **YOU WATCH YOUR OWN INBOX. YOU WRITE INTO THEIRS.**
>
> To reach someone, append to **their** file. **Never write into your own to "send" something** — nobody is watching it but you.

**Your address is `docs/mailboxes/inbox-<your-name>.md`, lowercased, no date.** `ACP` → `inbox-acp.md`. `ACT` → `inbox-act.md`.

**⇒ The address is DERIVABLE, which is the property that matters most.** You can reach a lane spun ten minutes ago that you have never spoken to, **with no prior coordination and no setup** — you create their inbox by writing to it. **That kills the *"a channel nobody is watching"* failure at its root.**

⚠️ **Slack is not a substitute.** Both channels reach **Justin and only Justin** — a ping addressed to "ACT" reaches Justin, who would have to relay it by hand. **These files are the only agent-to-agent channel.**

## 2 · 🔴 COMMITTING IS SENDING. Nothing before that is a message.

*(Justin's ruling, 2026-08-21, from ACv-2's report of being woken **three times for one message** — once when it was written, once when it was fixed, once when it was committed.)*

> **His framing, and it is the whole design: *"Can you imagine if every time you wrote one more word to an email, the recipient got notified?"***

**⇒ A watcher fires on a COMMIT that touches the file. Not on a save. Not on an edit.**

- **Write, re-read, fix, re-word, fix again — none of it wakes anybody.** You are drafting.
- **You get a pass to check you are happy with it.**
- **Then you commit, and exactly one wake lands.**

**The watcher shape:**

```bash
P="$HOME/Evryn/Code/_evryn-meta/docs/mailboxes/inbox-<your-name>.md"
[ -f "$P" ] || { echo "WATCHER FAULT: no inbox at $P — this watcher is BLIND. Fix before trusting its silence."; exit 1; }
echo "WATCHER ARMED — inbox-<your-name>.md. Proof-of-fire; every later line is real mail."
prev=$(git log --all -1 --format=%H -- "$P")
while true; do sleep 30
  cur=$(git log --all -1 --format=%H -- "$P")
  [ "$cur" != "$prev" ] && { echo "MAIL — your inbox changed in commit $cur. Read it."; prev=$cur; }
done
```

- 🔴 **`git log --all`, not your own `HEAD`.** A peer committing from a **different worktree** never moves your HEAD, so a HEAD-based watcher misses their message entirely.
- ⚠️ **The cost of commit-gating, stated so it is chosen and not discovered: an uncommitted message is INVISIBLE.** **Forgetting to commit means the message never sends** — the same failure as forgetting to hit send on an email, and it fails silent. ✅ **It is the right trade** (it is *your own* working tree, so you can see it) **but it is why mailbox commits are pre-authorized: nothing should ever sit between writing and sending.**
- 📌 **ACv-2 proposed hashing the file's contents instead of watching mtime, which would have removed one of its three wakes.** **Commit-gating removes two and adds the send semantics**, so it is the stronger version of the same instinct. **Content-hashing answers *"did this really change?"*; committing answers *"is the author finished?"* — and the second is the question a recipient actually cares about.**

## 3 · The loop, end to end

**Four acts. Two agents. No relaying.**

| # | Who | Does what |
|---|---|---|
| **1** | **Sender** | Appends a **pointer** entry to the recipient's inbox, **timestamped**, then **commits.** ⇒ one wake lands. |
| **2** | **Recipient** | Wakes, reads, **acts.** |
| **3** | **Recipient** | Writes a **RECEIVED** line into the **SENDER's** inbox, **clears the original from its own**, and **commits both with the work.** ⇒ one wake lands back. |
| **4** | **Sender** | Wakes, sees it landed and what happened, **deletes the RECEIVED line**, commits the deletion immediately. |

> ### 🔑 THE RECEIPT GOES IN THE SENDER'S INBOX. That is the whole fix.
>
> **In the old shared-file design the acknowledgement was free**, because both sides watched one file, so the recipient clearing it *was* the signal. **Splitting the file in two dropped that signal, and nobody noticed until the channel had been used enough to miss it.** ⇒ **Put it back as an explicit reply — which is better than the old bare *"absorbed,"* because a reply can say WHAT HAPPENED.**

**Why step 4 exists:** an undeleted RECEIVED line **wakes and puzzles instance after instance**, each of which has no memory of sending anything. **You MUST IMMEDIATELY clear your own receipts.**

⚠️ **Step 4 costs you ONE self-wake** — you are committing a change to a file you watch. **Do it at set-down**, batched with whatever else you are committing, when you are about to stop anyway.

✅ **Nothing here can loop.** You write into *theirs* and watch *yours*, so a receipt cannot bounce.

## 4 · Entry rules

1. 🔴 **AN ENTRY IS A POINTER, NEVER THE CONTENT.** Three lines maximum: **what happened · who owns the residue · where the real thing lives.** Substance goes to its right altitude — a Step, an ADR, a brief, a manual, a changelog entry — and the inbox says where.
   > **Why this is not tidiness:** a channel that carries content becomes a document nobody can skim, and it is *"one home per item"* applied to correspondence — **content in a mailbox is a second copy that starts drifting from the doc that owns it immediately.** ⭐ **It is also what makes a split conversation free:** a thread across two files costs nothing when the substance was never in the mailbox.
2. 🔴 **EVERY ENTRY CARRIES A TIMESTAMP.** **Format:** `**[YYYY-MM-DDTHH:MM · FROM → TO]** what changed, in one sentence → **where it lives.**` **Without it, git history cannot be aligned to a conversation** — which is exactly what the orphan case in §5 depends on.
3. **Newest at the BOTTOM. Append; never edit or delete another instance's entry** *(clearing a discharged entry from your OWN inbox is not editing theirs — see §3)*.
4. **Sign off per topic** with an explicit `OVER AND OUT`.
5. **No date in the filename, ever.** **Date the ARCHIVE, never the live file.**
6. 🔴 **LANE TRAFFIC DOES NOT COME HERE.** **A lane talks to its own conductor in its own lane doc; only what CROSSES lanes reaches an inbox.** Otherwise a dozen agents converge on one surface and it stops being skimmable at 3am — the single thing it has to be.

## 5 · Discharging, and the empty-inbox invariant

> ### 🔴 AN EMPTY INBOX MEANS NOTHING IS OWED. A NON-EMPTY ONE MEANS SOMETHING IS.
>
> **That is the entire state model. There is nothing else to remember.**

**When you have acted on an entry, delete it** — reply first, per §3. **The content is not lost: the sender committed it, so it is in git history permanently.** *(This is why "commit before you hand off" is non-negotiable — it is what makes clearing safe.)*

**The one marker worth keeping — for a message you have read but genuinely cannot finish yet:**

> `⏳ HELD [<ts>] · <instance> — <why> — until <testable condition>`

⚠️ **A `HELD` with no testable condition is the same failure as a held document with no retirement condition:** the next reader inherits the caution without the reasoning and has no way to test whether it still applies.

**Drain acknowledged traffic at `#lock` OR at ~40 lines, whichever comes first**, to `docs/mailboxes/archive/inbox-<name>-YYYY.MM.DD.md`. *(A drain rule that fires only on a checkpoint nobody schedules is not a rule.)* ⚠️ **Justin's caution, verbatim: *"be careful using docs that aren't intended to be ongoing mailboxes AS mailboxes — they'll get long and bloaty."***

### 📮 THE ORPHAN RECEIPT — you spun up, and there is a `RECEIVED` from someone you never wrote to

**This is normal and it is not an error.** Your predecessor sent it; you inherited the inbox, not the memory.

1. **Read the one-line context on the receipt** — that is what it is for. **Usually it settles the matter and nothing is owed.**
2. **If you need the original: `git log --all -p -- docs/mailboxes/inbox-<theirs>.md`** and find the entry by its **timestamp.** **The message is in history because the sender committed it before sending.**
3. **Then delete it** *(§3 step 4)* — **or it wakes and puzzles every instance after you.**

🔴 **⇒ THIS IS WHY A `RECEIVED` CARRIES CONTEXT AND A TIMESTAMP, and why a bare *"absorbed"* is not good enough.** **One clause naming what was received turns an orphan into a closed loop instead of an archaeology assignment.**

> **Shape:** `**[2026-08-21T11:09 · ACT → ACP]** ✅ RECEIVED — your note on the halt-signal class; verified at source, no propagation needed → recorded in SPRINT Step 117.` (The "ACT → ACP" might seem like overkill — this is, after all ACP's inbox in this example — the only reason to have sender *and* receiver is just in case someone wrote to the wrong inbox — that way this can get corrected.)

## 6 · Arming your watcher, and who gets a mailbox at all

> ### 🔴 ASK JUSTIN TWO THINGS AT SPIN-UP — they are separate acts with separate costs.
>
> ***"Should I arm a watcher on my inbox?"*** **and, if you do not have one,** ***"do I need a mailbox of my own created?"***

- **A top-level, standing agent should normally be watching.** *(Justin, 2026-08-21: arming should be a standard part of start-up, "unless there's some reason not to.")* **You are reachable by anyone, with no coordination, only while a watcher is up.**
- ⚠️ **ARMING IS STILL HIS CALL, because it decides whose traffic wakes you.** **Two instances of one lineage share an inbox**, so an unasked-for watcher wakes you on a peer's mail all day.
- 🔴 **A LANE DOES NOT GET A STANDING MAILBOX.** **A lane talks to its conductor in its lane doc** (§4 rule 6). **If a lane is given one for a specific reason, it is reaped at close-out with the lane's worktree and branch** — see `lock-protocol.md`'s subagent close-out. **An unreaped lane mailbox is a channel nobody watches, which is the failure this whole design exists to prevent.**

**Two watcher facts that bite:**

- 🔴 **ANCHOR THE PATH ON `$HOME` — never on `git rev-parse --show-toplevel`, never hardcoded.** **A `Monitor` shares the `Bash` tool's working directory, and that directory is MUTABLE** — any later `cd` silently re-points it. ⚠️ **It does not error; it goes quiet, and the silence reads exactly like an empty inbox.**
- 🔴 **EMIT A PROOF-OF-FIRE LINE BEFORE THE LOOP.** *"Monitor started"* means only that a process launched — **a script that dies on its first line reports the same thing.**
- ✅ **Do NOT try to detect the author.** Emit `MAIL — read the file` and go read it. **In a per-recipient inbox everything is for you anyway**, and an instrument that guesses can lie to you.
- 🔴 **`TaskStop` the watcher when you set down.** **It dies with your session regardless — so never hand a task id to a successor. Hand them the PATH to watch.**

🔴 **ABSENCE OF A NOTIFICATION IS NOT EVIDENCE OF ABSENCE.** **Any mechanism whose failure mode is *silence* needs a second mechanism whose output is *unconditional*** — here, the **spin-up read**, which runs at the one moment a watcher structurally cannot see: before it existed.

⚠️ **Do NOT have your heartbeat re-check your inbox every tick.** **A watcher firing wakes you by itself**, so a heartbeat that re-prints inbox state pays full turns to re-answer a free question. **The heartbeat's only job is *"are you still moving?"***

## 7 · Commit immediately — it is not hygiene, it is the send button

**Write, then commit, then walk away.** 🔴 **Mailbox commits are PRE-AUTHORIZED — they never wait for Justin's go-ahead.** All instances run on the same machine, so a **committed** message is visible with no push; push is only for GitHub and cross-machine durability.

⚠️ **An uncommitted message is not a slow message. It is not a message at all** — nothing is watching your working tree, and a stray `git reset` or branch switch erases it.

## 9 · 🔴 Renaming a mailbox — the agent and the file are different questions

**Renaming the file breaks every watcher armed on it, and it breaks them SILENTLY** — the watcher stays alive, polls a path that no longer changes, and reports nothing forever. ⚠️ **A watch that dies with its session is bad; a watch pointed at a renamed file is worse.**

🔑 **But a watcher is SESSION-BOUND, so a rename can only break watchers LIVE AT THAT MOMENT.**

> ### ⇒ **Don't rename a mailbox while a watcher is armed on it, without informing the watching agent so they can adjust.**

**The six steps, in order:**

1. **Confirm with Justin that no live session holds a watcher on it.** 🔴 **Only he can see that** — it is a claim about session state.
2. **`git mv` the file**, messages intact; update its own header, edit nobody's entries.
3. **Post the mapping into every peer's inbox** — into *theirs*, per §1.
4. **Repoint live references only.** ⚠️ **Changelogs, `docs/historical/**`, `docs/sessions/historical/**` and superseded handoffs are FROZEN RECORDS — a corrected path inside one is a falsification.**
5. **Record old → new in §8 and never delete the mapping.**
6. **Let anyone watching know** — if there are live sessions, they need to be informed now; if not, make sure upcoming briefs and handoffs have the updated info.

📌 **Worked example — `inbox-ac0.md` → `inbox-acp.md`, 2026-08-21.** The `AC0` → `ACP` rename happened 2026-08-19 and **the file deliberately kept its path at the time, because watchers were armed.** It moved two days later in a window when nothing was watching. **That distinction is the rule.**
