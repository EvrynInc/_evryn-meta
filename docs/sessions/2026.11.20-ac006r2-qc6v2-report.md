## New findings

**NON-BLOCKER F1: a lucas-tier re-authorization launders the acceptance tier of work Justin authorized himself**

- **Where:**
  - `006_authorization_record.sql:299-304`: an authorization of an already-active task is allowed at any tier.
  - `:314-322`: acceptance checks only the tier of the CURRENT pointer row (`v_auth_tier`).
- **What the code does:** once Lucas writes any lucas-tier authorization on the task, the pointer moves to that row. A lucas-tier acceptance then passes, although a `justin`-tier authorization of the same scope sits in the record.
- **What the spec expects:** §2.1 (d): *"if that authorization's tier is `justin`, the acceptance's tier MUST be `justin` too"* (`authorization-rules.md` §3: accepting work he authorized himself is his). The spec meant the active-task authorization as the **upgrade** path (*"how a backfilled or Lucas-tier row is upgraded to Justin-tier"*). **Its letter tests only the current pointer, so this is a gap in the spec's letter as well as in the code.**
- **Why it matters:** ET012's family is meant to be structural against the honest and "helpful" write. **Route N1b is exactly that path:**
  1. Justin authorizes.
  2. The owner withdraws (or pauses).
  3. Lucas re-authorizes the SAME scope at tier lucas. That is legitimate under `authorization-rules.md` §1 item 1, "continuing work Justin already authorized".
  4. Lucas accepts at tier lucas, and the database lets it through.
- **Why it is not a blocker:** it is not silent. Every row is in the record and the nightly audit. `authorization-rules.md` §4 puts Lucas's acceptance in the next brief under "decided without you", and `lucas` or `justin` can reopen the task.
- **What I RAN:**
  - **probe N1:** justin-tier authorization → hand in → lucas acceptance REFUSED (correct) → lucas-tier authorization on the `needs_acceptance` task ACCEPTED (pointer tier now lucas) → lucas acceptance ACCEPTED → `done`. Rows: `authorization:justin, authorization:lucas, acceptance:lucas`.
  - **probe2 N1b:** the withdraw route, same scope hash `f122e2f2` on all three rows → `done` by a lucas acceptance.
- **Fix sketch:** at `:318`, require tier `justin` when ANY justin-tier authorization of this task matches the current scope:
  ```sql
  if exists (select 1 from public.task_authorizations a
              where a.task_id = new.task_id and a.kind = 'authorization' and a.tier = 'justin'
                and a.scope_hash = v_hash)
     and new.tier is distinct from 'justin' then  -- ET012, the existing message
  ```
  A scope edit still frees the task, because a new scope has no justin row. **Add a test for both routes (N1, N1b), plus a control. Re-pin the hash.** Update §2.1 (d)'s wording to say "any justin-tier authorization of the current scope".
