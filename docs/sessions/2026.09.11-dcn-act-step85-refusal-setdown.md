## 2. What changed, file by file

### `src/composer/memory.ts` — the whole decision lives here

- **`MemoryRefusal` gains two members:** `'canary-missing' | 'canary-not-terminal'`, alongside the existing `unreadable | empty | vanished`.
  - 🔑 **Why two flat members and not one `damaged` member with a `canary` sub-field** *(a judgement call the brief left to me)*: `reason` is the **single discriminator** every consumer already switches on. A `{reason:'damaged', canary:…}` shape puts a field on the union that is meaningful for exactly one member — the shape that invites `undefined` handling at every call site. Flat members keep the exhaustive `switch` in `memoryRefusalMessage` doing the work: **add a member without handling it and the compiler refuses.**
- **The `damaged` arm of `MemoryGrade` is deleted.** `ComposableMemoryGrade` is now `intact | absent`.
- **The refuse grade gains two optional fields:** `chars` (the file's size, present **iff** the file was readable) and `reread` (set when the refusal survived a second read). Both follow the existing `code?` pattern.
- **`gradeMemory` stays PURE** — it takes a read outcome, returns a grade. The re-read is IO and deliberately lives outside it, because the suite drives `gradeMemory` directly and making it impure would have destroyed that.
- **NEW `readAndGradeMemory(path, prior, read = readFileOutcome)`** — the ONE re-read. `read` is injected so the race is testable deterministically.
- **NEW `TRANSIENT_READ_CODES`** and **`refusalDeservesReread`** — see §4.
- **`memoryRefusalMessage` rewritten** — see §3.
- **DELETED: `damagedMemoryWarning`** (the agent-facing warning). Under a refusal, no agent ever wakes to read it.
- **`MEMORY_LAYER_NAMES` loses `damaged-missing` / `damaged-not-terminal`.** No new manifest can record those grades.
- **`memoryAlarmKey`'s grade parameter narrows to `'absent'`** — the only grade that can still alarm. The key **keeps** its grade segment; the comment explains that the per-agent half is the live property and the grade half is what would stop a future second alarming grade colliding.
- **`memoryAlarmMessage` narrows to `(agent, path)`.** Its text is **byte-identical**; it simply never read the two arguments I removed.
- **NEW private `canaryDefectPhrase`** — one home for how a canary defect reads in a sentence, so two descriptions of the same file state cannot drift apart.

### `src/composer/index.ts`

- Calls `readAndGradeMemory(...)` instead of `gradeMemory(await readFileOutcome(...))`.
- **The alarm branch narrows from `absent || damaged` to `absent`.**
- The `memoryIntegrityWarning` computation and its conditional spread into the wake context are gone.
- **NEW test-only knob `opts.readMemory`** — the injected layer-6 read. Needed because a first-read-fails/second-read-succeeds sequence is a **race** in production, and racing a real file to reproduce it would be a flaky test of a flake-handling feature. Same injectable-knobs pattern as `boot/singleton.ts`'s `AcquireOpts`.

### `src/composer/layers.ts`

- **`WakeContext.memoryIntegrityWarning` and its render block removed.** Nothing else in the wake context moved, so every healthy wake composes byte-identically to before.

### `tests/composer-memory-grading.test.ts`

- Acceptance 4a / 4b now assert **refusals** (typed reason, defect named, size, repair, write-consequence, and that it says it re-read).
- **Acceptance 4c is kept and relabelled `THE CRY-WOLF CONTROL`.**

- The rate-gate test was split in two (see §7 for the honesty note on the dormant half).

### 3a. The delivery path, traced at source

| Question | Answer |
|---|---|

## 4. The ONE re-read — what re-reads, what does not, and why

**`readAndGradeMemory`: read → grade → if the grade is a refusal that could be transient, read ONCE more and grade that. ONE. No loop, no backoff, no third chance.**

**If the second read is clean the wake composes normally and NOTHING is raised** — no alarm, no marker, no note that the first attempt flaked. *(A successful read is a successful read; recording the recovered case would train the operator to ignore the next alert.)* **If it fails again, the message says the file was read twice**, which is what stops an operator dismissing a real refusal as a flake.

| Reason | Re-read? | Why |
|---|---|---|
| `canary-missing` | **YES** | Justin's explicit instruction. Reachable from a file caught mid-write. |
| `canary-not-terminal` | **YES** | Same. |
| `empty` | **YES** | A file caught mid-write can read as empty. |
| `vanished` | **YES** *(my call — the brief left it to me)* | Highest-stakes refusal (an established agent's memory gone) and the cost is one syscall. A checkout can briefly unlink a file. **Cheap insurance on the case where being wrong is worst.** |
| `unreadable`, transient errno | **YES** — allowlist: `EMFILE ENFILE EIO EAGAIN EBUSY EINTR ETIMEDOUT` | Each means "the system could not do it just now." |
| `unreadable`, anything else | **NO** — `EISDIR EACCES EPERM ENOTDIR ELOOP ENAMETOOLONG UNKNOWN` | These are statements about the **path or the file**. A second read returns the identical answer. Re-reading them would buy nothing and make this look like a retry loop. |

**It is an ALLOWLIST, deliberately** — an unknown errno does **not** get a re-read. That is a judgement call and the knob is one array if anyone disagrees.

### 🔴 A CORRECTION TO THE BRIEF'S STATED MECHANISM — the reason I was given is not the real one

ACT-20's amendment justified the re-read by saying *"the runtime itself writes that file (`appendNoteToMemoryFile`) … so a compose can race a write and see a half-written file."*

**That specific mechanism cannot happen.** `appendNoteToMemoryFile` (`src/wakes/memory-writer.ts`) writes a **temp file** and then **`rename()`s it over the target**, and rename is atomic — a reader sees the whole old file or the whole new one, **never a half**.

**The genuine window is the WORKSPACE GIT SYNC.** `git clone` / `git pull` write working-tree files **in place, non-atomically**, so a compose racing a sync can see a partial or momentarily-absent file. **Today that sync runs only at boot** — ARCHITECTURE cardinal invariant 1's "~15-min refresh" **does not exist** (SPRINT Step 72) — so the window is narrow.

⇒ **The re-read is correct and worth having, but for a different reason than the one given, and the difference is load-bearing: if the periodic refresh Step 72 describes is ever actually built, this re-read stops being cheap insurance and becomes structural.** That reasoning is recorded at `refusalDeservesReread` in the code so it cannot be "simplified away."
