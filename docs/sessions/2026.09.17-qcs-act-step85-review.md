## Standing patterns worth promoting

1. **A refusal's REPAIR instruction is part of the guard.**
   - *Trigger:* a fail-closed refusal whose message tells the operator how to fix it.
   - *Failure:* the recommended repair passes damaged input. When the detector is deliberately silent on that shape (as a no-cry-wolf control makes it), the laundering is invisible.
   - *Move:* perform the repair the message recommends, literally, on a damaged input, then grade the result again.
2. **A retry or re-read justified by "the racing writer only runs at X".**
   - *Move:* enumerate every writer of the file (including `git pull`, `checkout` and `rebase` called from app code), not just the app's own writer. Then **measure** whether an immediate retry actually clears a real race; here it cleared about 37%. Prefer waiting on the writer's lock over a blind retry.
3. **An error or park record written into a scope that a lifecycle keys on.**
   - *Move:* for any record inserted into a table with activity triggers, list the lifecycle predicates that read the bumped column (revival, staleness, dormancy), and ask whether the record itself re-arms one. It's the mirror of the "inert record" pattern. Here: park note → activity trigger → revival → completion rows wiped.
4. **Marker-locating predicate pairs need 0, 1 and ≥2 occurrence rows.**
   - *Move:* when a sibling pair locates a marker with `indexOf` or `lastIndexOf`, the shared test table must include an input with two occurrences, or the two sides can diverge with the suite green (M12 and M14 here).
