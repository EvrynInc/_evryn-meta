## 3 · Findings

### F1 · BLOCKER · `verify` exits 0 on a forged report, on the same machine, by editing one field
- **What the code does:** `cmdVerify` decides "cross-machine" by `fs.existsSync(meta.transcript)`, using the path **from the report itself**. If that path is missing, it checks only the report's own hashes and prints `VERIFY DOWNGRADED`, **exit 0**. The report records `machine` (`os.hostname()`), but **verify never compares it.**
- **Evidence, real path:**
  - I copied my real FAILing report, then edited its JSON so that `C9: "PASS"` and `"transcript": "C:/nowhere/forged.jsonl"`.
  - `verify --report forged.packout-report.md` printed `VERIFY DOWNGRADED (cross-machine) … no FAIL`, **exit 0**, while the real transcript exists on this machine.
  - The human-readable table in that report still says C9 FAIL, because verify reads only the JSON.
- **Evidence, fixture** (`probes/falsepass.mjs` P1): a C1-FAIL report with the same two edits also gave `VERIFY DOWNGRADED`, exit 0. The real transcript exists (`true`); `machine` = `JBM_XPS_15_9510`.
- **Spec:** §3.3 says verify *"confirms the same transcript hash … Cross-machine: downgrades."* The downgrade is meant for a different machine, not for a path that can be erased.
- **Fix sketch:**
  - FAIL when `meta.machine === os.hostname()` and the transcript is absent;
  - give DOWNGRADED its **own non-zero exit code**, so a hook can't read it as PASS;
  - have verify also take the footer's `PREDECESSOR` and `HANDOFF`, and FAIL if the report's `session` or `handoff` differ (today a report for any other packout verifies).
- **Test that fails without it:** the P1 forgery must exit non-zero.

### F2 · BLOCKER · `verify` re-derives verdicts from the state embedded IN the report it is verifying
- **What the code does:** `liveCheck(…, { stateOverride: meta.state })` takes `beganAt`, `incoming`, `agent` and the sweep list from the report's JSON. So a forged state re-derives forged verdicts consistently.
- **Evidence** (P2): the seat skipped the incoming re-read, so C7 FAILed ("no Read of the incoming handoff after line 4"). I edited the report's `state.incoming` to `null` and `C7` to `PASS`. `verify`: **`VERIFY PASS … 12 verdicts re-derived and equal`**, exit 0. The on-disk `state.json` still names the incoming file; verify never looks at it.
- **Same class:** an edited `state.beganAt` (earlier) would admit pre-packout writes for C1, C2, C4 and C12, and `state.agent` switches the profile (`AC*` makes C1 accept `PACKOUT-NONE C1`). *(Reasoned from the code path that P2 exercised; I didn't build a separate fixture for each.)*
- **Fix sketch:** derive `beganAt` and the arguments from the transcript itself. The `packout.mjs begin --agent … --handoff … --incoming …` Bash call, and each `sweep` call, are in the transcript, with their own lines and results. Or at least require the report's state to equal the on-disk `state.json` byte for byte. Never accept state from the report.
- **Test:** the P2 forgery must FAIL.
