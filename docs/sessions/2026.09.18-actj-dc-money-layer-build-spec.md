## 3 — The work, as requirements

Each item is a **requirement** and names **what enforces it**. **A requirement without its enforcing test is not done.**

### 3.1 — `ensureJobForDispatch` — lazy get-or-create, in `src/money/ledger.ts`

- **It MUST return the SAME job id for the same scope key on every call, and create a row only when none exists.**
  - **Scope keys:** a wakeup → `wakeup:<wakeup id>`; a check-in → `checkin:<agent>:<YYYY-MM-DD>` (the same string the check-in already uses as its `threadId`).
  - **Store the key in `jobs.metadata.scope_key`. NO migration** — `metadata` is documented as *"job scope metadata… plus free-form context"* (migration 002). ⚠️ **If the test fakes cannot express a JSON-path filter, that is a test-harness gap to report, NOT a reason to add a column** — a column is a migration, and a migration re-opens deploy gate G1, which is Justin's.
  - 🔑 **Enforced by:** a test that two calls for one key return the same id, **with a control** that two different keys return different ids — **mutation-proven** (§4).
- **Row shape at creation:** `title` (the wakeup's prompt, truncated; or `Daily check-in <date>`) · **`responsible_agent` = the waking agent** · `cap_usd` from §3.7 · `status` left at its column default `'authorized'` · `authorization_ref: null` · `metadata: { scope_key }`.
  - **`responsible_agent` MUST be the waking agent**, because the agent-facing `get_job_status` tool (`tools/tools.ts:573–575`) filters `.eq('responsible_agent', ctx.agent)` — set it wrong and the agent's own tool answers *"No jobs found."*
  - **Comment the `'authorized'` status at the mint:** here it means *"this job may run,"* **not** *"a human approved it"* — the word collides with the proposal lifecycle, and the next reader will assume otherwise.
- 🔴 **The comment at `ensureJobForDispatch` MUST state WHY two mints for one key cannot interleave — ACT-22 asked for this in writing, so that moving the mint cannot silently remove the guarantee.** **State this. ACTj confirmed every link of it at source on 2026-09-18 EXCEPT ONE — the singleton lock, which ACTj did NOT read (that link came from SPRINT Step 50 and `ARCHITECTURE.md`). ⇒ Read `src/boot/singleton.ts` yourself and verify that clause before you write it into code.**
  > **Mints for one key are never CONCURRENT, because each key has exactly one producer and every producer is sequential.** `cycle()` never overlaps itself — it re-arms only in its own `finally` (`scheduler/index.ts:835–837`) — and it awaits each `dispatch` in turn (`:745`); `planDispatches` yields at most one decision per agent per cycle (`dedup.ts:431–438`); the check-in cron loops agents sequentially, and its key has no other producer; the runtime singleton lock (`boot/singleton.ts`) means one process. **The per-agent `inFlight` set is NOT the guarantee**: it is consulted in `planDispatches` pass 2 (`dedup.ts:432`) and again inside `dispatch`, but neither of those is what keeps two mints for *one key* apart.
  >
  > **Repeat mints for one key DO happen — SEQUENTIALLY.** A wakeup whose dispatch is refused is not marked fired (`onDispatched` runs only after the lock, `:502–511`), so it is re-planned on a later cycle and the mint runs again for the same key. **That is why the GET half is load-bearing, and it is what the idempotency test pins.**
  >
  > ⚠️ **If you ever move the mint somewhere that is not one of these sequential producers, this reasoning no longer holds — take a unique index instead** (and tell your conductor: it is a migration, which re-opens gate G1).

### 3.2 — The job decision for a planned wake: a PURE, EXPORTED, EXHAUSTIVE function

- **Which job a `DispatchDecision` carries MUST be decided in ONE pure, exported function that switches over `TriggerKind` exhaustively with a `never` default** — the house pattern of `reasonForKind`, `partitionTriggerIds` and `velocityGate` in the same file. **A fifth trigger kind must then fail to compile until someone decides whether it carries a job.**
- **It MUST implement NO-JOB-DOMINATES:** if ANY trigger coalesced into the decision is `member` or `dormancy`, **or** two coalesced triggers carry different non-null jobs, **the decision carries no job.** *(Why: a wrong job can freeze a live conversation; a missing one degrades to today's behaviour with the fleet brake still on. It mirrors "dormancy dominates" in `dedup.ts:382–397`.)*
- 🔑 **Enforced by:** a test covering each kind alone **and** the two documented coalescing collisions — `park`+`member` and `dormancy`+`member` (see `dedup.ts:370–397`) — each proven by mutation.

### 3.3 — Thread the job into the two job-bearing sites

- **`buildPlannedWakeRequest` (`scheduler/index.ts:129–145`) MUST take the job id as a second, REQUIRED parameter.** **Not optional:** an optional parameter defaults silently, which is the fail-open shape `assessGlobalVelocity`'s required `basis` exists to prevent (`tests/fixtures/velocity-basis-omitted.ts` is the fixture that proves it). **It WILL break `tests/park-trigger.test.ts`'s two `buildPlannedWakeRequest(plan[0]!)` calls at compile time — that is the design working; update them.**
- **In `cycle()`, the planned path mints (for `wakeup`) or inherits (for `park`) immediately before its `dispatch(...)` (`:745`)** — this is the signed-off placement, and it leaves no orphan rows: a refused planned dispatch leaves its trigger unconsumed, so the next plan re-uses the same job through the GET half.
- 🔴 **The check-in cron (`:841–859`) MUST mint ONLY AFTER `dispatch` has passed its gate and acquired the lock. A check-in whose dispatch is refused MUST create no `jobs` row.**
  - **Why this is a requirement and not a nicety:** direct dispatchers have **no retry** (`:458–463`), so a refused check-in is dropped — and **the runtime boots paused by default** (`__global__ active=false` — *per `ARCHITECTURE.md`'s Phase-1 notes and SPRINT gate G4; ACTj did not read `boot/index.ts`, and the argument holds for ANY pause*; `cycle()` idles at `:556–559`) **while the check-in cron keeps firing daily.** **Mint before the gate, and every day the fleet sits paused leaves one orphan job per agent — an empty job the agent's own `get_job_status` then reports as live work.** That is the steady state, not an edge case.
  - **The principle is already in this file:** *"Trigger consumption happens ONLY after the lock is held (QC blocker 2)"* — `dispatch`'s `onDispatched` hook exists for exactly this (`:502–511`). **Minting a job is the same kind of act.**
  - **Shape is yours to choose** — e.g. a resolver passed to `dispatch` and invoked after `onDispatched`, before `runWake`. **Whatever you choose, the check-in's request literal must not be left reading `jobId: null` while a real id arrives by another route** — a reader will believe check-ins carry no job.
  - 🔑 **Enforced by:** a test that a check-in dispatched against a paused global creates **zero** `jobs` rows, **mutation-proven** by moving the mint ahead of the gate. ⚠️ **`dispatch` lives in `startScheduler`'s closure beside `cycle()`, whose prologue can `process.exit(1)` (SPRINT Step 43 — do not try to make `cycle()` callable).** **If the property cannot be reached safely, pin the ordering with a source-level assertion over stripped source — the precedent is `tests/scheduler-velocity-wiring.test.ts` PART 2, including its anti-vacuity proof — and say that is what you did.**

### 3.4 — `park` resumes under its original job

- **`parkNoteCandidate` (`dedup.ts:244–262`) MUST carry the park row's `job_id`, and `DispatchDecision` MUST carry it through**, so a re-armed park resumes under the job it parked under — or under none, if it had none, which is right for a resumed conversation. **The re-armed-park scan (`scheduler/index.ts:677–689`) already selects `*`**, so `job_id` is on the row.
- *(Today `parkNote` writes `job_id` into both the column and the JSON body — `wakes/index.ts:734`, `:738` — and nothing ever reads it back.)*
- 🔑 **Enforced by:** a test that a park candidate built from a row with a `job_id` yields a `WakeRequest` with that job id, and one built from a row with `null` yields `null`.

### 3.5 — `dormancy` and `member` carry no job — by construction, not by guard

**A frozen job on a closing-memory wake would refuse the wake before `parkNote` (`wakes/index.ts:239–247`), so no completion row is ever written, so the thread never reaches `dormant` — every sweep retries it, forever, with its digest up.** The refusal precedes `query()`, so it costs no model spend, **which is exactly why nothing would ever notice.** **§3.2's function is what makes this impossible; §3.2's test is what pins it.**
