**Where the lock lives:** `src/boot/workspace.ts:377`, in `makeMemoryGitHook`: `withKeyLock(`workspace-git:${workspacePath}`, …)`. **[SRC 09-18]** `withKeyLock` (`src/db/keyed-mutex.ts:16`) is an **in-process promise chain**: a caller runs after everything queued before it on that key. **[SRC 09-18]**

**Where the wait goes:** `readAndGradeMemory`, **between** `const first = …` (**memory.ts:321**) and `const second = …` (**:323**) — **only on the refusal path.** **Not before the first read**: that would put a lock wait on every wake's hot path, and Justin's ruling is "before the one re-read."

**Approach I would take:**
1. Keep `readAndGradeMemory` testable: add an **injected** parameter (e.g. `waitForWorkspaceGit?: () => Promise<void>`), exactly like the existing injected `read`.
2. composeWake supplies it as "acquire and immediately release" — `() => withKeyLock(<key>, async () => {})` — which resolves once everything queued ahead has finished.
3. 🔴 **ONE spelling of the key.** Export a helper from `src/boot/workspace.ts` (e.g. `workspaceGitLockKey(path)`) and make **both** `makeMemoryGitHook` and composeWake use it. **A second hand-typed `` `workspace-git:${…}` `` in the composer is a silent-drift trap:** misspell it and the wait resolves instantly on an unrelated key while every test still passes. *(Same class as `MEMORY_COMPONENT_PREFIX`, which already carries a warning about being a second spelling.)*
