## 2. ITEM TWO — the NUL byte that makes the runaway-killer invisible to review

### The problem, verified at source

`src/safety/loop-signature.ts` contains **exactly one raw NUL byte**, at **offset 1413, line 32** on `main` `9f48e8d`:

```
createHash('sha256').update(`${toolName}<NUL>${stable}`).digest('hex')
```

It is a **hash delimiter written as a literal null character instead of the escape `\0`.** Semantically it works — it separates the tool name from the serialized arguments in the wake fingerprint.

**The cost is that the entire text-tooling layer goes blind on this file:**
- `git diff` renders only **"Binary files … differ"**
- `git grep` returns only **"Binary file … matches"**
- **GNU `diff` refuses it too** — ACf hit this today and had to force `diff -a` to verify a change

**⇒ Every change to the file that detects and kills runaway wakes is invisible to normal review.** This is not hypothetical: it fired live during today's canary-sweep merge, where git reported the file as `Bin 2864 -> 3073 bytes` and ACf could not confirm from the diff that only comment lines had been added.

### The fix

**Replace the literal NUL character with the escape `\0` — semantically identical, one character.** `'\0'` in a JS template literal produces the same U+0000 code point, so **every existing signature hashes identically** and no behavior changes at all.

### 🔴 What your DC and QC must prove, and why reading won't do it

**This file is the reason "verify by breaking" exists.** Two things to establish, and neither is provable by inspection:

1. **The fix is behavior-neutral.** Prove it: compute `signature()` (or the equivalent hash) for a fixed `(toolName, args)` pair **before and after** the change and show the two digests are byte-identical. Do not reason about it — run it.
2. **The blindness is actually gone.** Prove it: after the change, confirm `git diff` on the file renders as **text**, and `git grep` returns real matching lines rather than "Binary file matches." **That is the deliverable** — the semantic no-op is the means, not the end.

⚠️ **And the trap ACf already fell into: writing a literal NUL into a file *while documenting the NUL bug*.** If you or your DC write about this in any doc, comment, or commit message, **write the escape, never the character** — otherwise you reproduce the defect in the artifact describing it.

## 3. ITEM THREE — the env-drift test (an instruction decays; a test cannot)

### Why this exists

`.env.example` had **7 undocumented variables** as of 2026-08-04, **one of them REQUIRED** (`META_REPO_PATH`) — so an operator copying the template got a boot refusal naming a variable the template never mentioned. That specific gap is now closed. **The point of this item is that it will happen again**, because "remember to update the template when you add a var" is an instruction, and instructions decay.

**Justin approved a structural fix: a test asserting that every variable the code REQUIRES appears in the template.** *(He also approved a CLAUDE.md rule saying the same thing in prose — that half is ACf's, not yours. Belt and suspenders: the rule tells a human what to do; the test catches them when they don't.)*

### The five `required()` sites on `main` `9f48e8d` (`src/boot/env.ts`)

```
required(env, `SUPABASE_URL_${suffix}`)          // ← note: TEMPLATED, resolves to _DEV / _PROD
required(env, `SUPABASE_SERVICE_KEY_${suffix}`)  // ← templated
required(env, 'CLAUDE_CODE_OAUTH_TOKEN')
required(env, 'WORKSPACE_REPO_PATH')
required(env, 'META_REPO_PATH')
```

### Yours to decide — and there is a real design question here worth thinking about

- **How the test discovers the required set.** Parsing `env.ts` source for `required(...)` is the obvious approach and it is **brittle in a specific, dangerous way: the two `SUPABASE_*` calls are template literals**, so a naive regex either misses them or yields a literal `${suffix}` that matches nothing in the template. A test that silently checks 3 of 5 vars is **worse than no test**, because its name tells the next reader all 5 are covered.
- **⇒ ACf's lean, which you may overrule: prefer a mechanism that cannot silently under-cover.** Options worth weighing: exercising `loadRuntimeConfig` against a synthesized env built from the template and asserting it does not throw (which finds every required var *by behavior*, templated or not); or an explicit hand-maintained list **plus** a second assertion that the list matches the `required()` call count in the source, so adding a 6th `required()` without listing it fails loudly. **Whichever you pick, state how it behaves when someone adds a templated required var**, because that is the case that will break it.
- **Whether it also asserts the reverse** (every var in the template is actually read by the code). *(ACf's lean: no — a template legitimately documents optional and operator-set vars. Don't build a rule that punishes documentation.)*
- **Scope: this repo only.** `.env.example` files for the *other* repos are ACf's docs work, not yours — see §6.
