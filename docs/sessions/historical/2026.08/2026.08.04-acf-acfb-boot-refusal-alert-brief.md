## 3. ACf's design position — ONE alert site, at the single funnel

**`src/index.ts:13` — `boot().catch(...)` — is the only top-level catch in the runtime's boot path, and every refusal above lands in it.** Verified: the sole `process.exit` on that path is `index.ts:15`. The only other `process.exit(1)` calls in `src/` are `scheduler/index.ts:349` (a *runtime* exit that already pings — see §6) and `tools/stdio-server.ts:68` (a separate process — see §6).

**So a single boot-safe alert in that catch covers every refusal uniformly — including refusals nobody has written yet.** ACf strongly prefers this to alert calls at N throw sites, for the reason this codebase keeps teaching: a structural invariant beats an instructional one. N sites is a list someone must remember to extend; one funnel cannot be silently bypassed.

**This is a recommendation you may overrule** — you'll have the code in front of you and ACf won't. If you find a reason the funnel is the wrong home, say so and say why.

### The four hard constraints — these are not negotiable, and each has a concrete failure behind it

1. **Boot-safe: read `process.env` DIRECTLY. Never a parsed `RuntimeConfig`.** `loadRuntimeConfig()` is *itself* one of the things that can throw, so the alert must not depend on its output. This is safe because `dotenv` runs at `index.ts:11`, **before** `boot()` — so `process.env` is populated either way. *Failure if ignored: the config-refusal case — the single most likely refusal — is the one case that can't alert.*

2. **AWAIT the send before `process.exit(1)`.** `index.ts:15` exits synchronously inside the catch, so a fire-and-forget `fetch` is **killed before the request lands.** The send must be awaited with a short timeout (`AbortSignal.timeout`, mirroring `src/safety/notify.ts`) and the exit moved after it. **⚠️ This is the trap most likely to produce a fix that reviews clean, ships, and never delivers a single alert.** Treat the exit-ordering as the thing most worth a real guard test.

3. **The emergency webhook var is OPTIONAL — a missing one must NEVER itself refuse boot.** Otherwise the alerting *for* boot refusals *becomes* a boot refusal — circular, and it would brick every environment that hasn't set the var yet (including dev). Absent → log-only, exactly how `createNotifier` degrades when `TEAM_ALERTS_WEBHOOK_URL` is unset (`src/safety/notify.ts:15`).

4. **Secret hygiene: the webhook URL must NEVER reach a log line, an error message, or an argv.** The house pattern is `src/safety/notify.ts` — it logs the message text and never the URL. Note the runtime **already** carries `TEAM_ALERTS_WEBHOOK_URL` (`src/boot/env.ts:181`) for normal ops; the emergency channel is a **separate, new** var. *(Justin's steer, carried from the L9 routing: point it at the product's `#emergency-alerts` — one "something's on fire" channel he already watches beats a second one he doesn't.)*
