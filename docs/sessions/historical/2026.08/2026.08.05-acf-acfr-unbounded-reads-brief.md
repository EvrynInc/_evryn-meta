`src/money/ledger.ts:122-129`, `lastHourSpendUsd`:


### Instance 1 — the agent's working memory

`src/composer/index.ts:311-318`, composer layer 10:

```ts
await db.from('agent_messages').select('*')
  .eq('thread_id', wake.threadId)
  .neq('message_type', 'heartbeat')
  .order('created_at', { ascending: true }),   // ← no .limit(), no pagination
```

**Why this is newly live rather than longstanding, and it matters for how you think about it:** until 2026-08-04 a hard 30-message window (`windowThread`) capped this layer, which made any underlying ceiling irrelevant. **Memory-track item (c) removed that window on purpose** — so that "the thread IS the session" would be literally true (design-of-record §3.3). **Above 1000 messages it silently isn't:** the agent receives the **oldest** 1000 and believes it holds the whole conversation. **Interaction you must not break:** `THREAD_HARD_CEILING_TOKENS` (`src/composer/layers.ts`) is a *token*-count backstop applied **after** the rows arrive. It cannot save you here — it can only window what was already fetched. A truncated fetch is invisible to it.

### Instance 2 — the digest watermark

`src/digest/index.ts:175-182`, `regenerateThreadDigest` — the same unbounded read, and then:

```ts
const highWater = messages[messages.length - 1]!.created_at;   // newest message RECEIVED
… .upsert({ thread_id: threadId, blurb, updated_at: highWater })
```

`updated_at` genuinely means *"the activity high-water mark this blurb reflects"* — which is the **correct** design (it is what makes the staleness comparison race-safe). **But a truncated read makes "where I got to" a lie about how much was read.** Staleness is `last_activity_at > updated_at`, so a short watermark makes the thread **permanently stale**: it regenerates every ~2 minutes (the floor), forever, each time re-reading the same truncated prefix. **That is the L7 spend-loop class this lane has already paid for once.**

### Class Three — folded in, because it lives in the same function

`src/digest/index.ts:286-290`, inside `refreshThreadDigestIfStale`:


A **persistently failing** regeneration never records an attempt, so the ~2-minute floor never engages, and it retries on every 30-minute sweep *and* every on-read compose — **no attempt bound, no wall-clock bound, no retirement or escalation.**

**Severity is low and you should treat it that way: it holds no position.** Nothing queues behind it; the consequences are repeated Haiku spend and a thread that stays *honestly* marked stale to the agent (the composer already degrades loudly). ## 3. ACf's design position — and the one rule worth generalizing

**The rule ACf proposed to AC0 for the shared manuals, which is the frame for this whole trip:**

> **Any read whose result determines a position, a watermark, a completeness judgment, or a safety threshold must set its page size explicitly and follow pagination to completion — or fail loud. An unset limit is a silent ceiling you do not control and did not choose.**

That is deliberately stronger than "paginate your API calls," because it names *which* reads matter. **A `select` that merely renders a list can be capped harmlessly; a `select` that feeds a `sum()`, a high-water mark, or an agent's belief about what it has seen cannot.**

**⇒ So your scope is not "add `.limit()` in three places."** It is: **audit every `.select(` call site in `src/` against that rule** (there are **63**), classify each as *consequential* or *harmless-if-capped*, fix the consequential ones, and **record the classification** so the next reader doesn't re-derive it. ACf expects the great majority to be harmless; the value is in the audit having been *done and written down*, not in the count of fixes.

### The four hard constraints

1. **🔴 VERIFY BY BREAKING, NOT BY READING. This is the whole point of the lane and it is non-negotiable.** *(AC0's meta-lesson, and it is what found this class in the first place.)* **Reading cannot find an absence** — a missing `.limit()` has no wrong line to notice, which is exactly why these files passed multiple full-load QC reviews, including a fresh-QC GO on `digest/index.ts`, and nobody saw it. **So: seed more than 1000 rows on the dev database and observe the wrong answer, then observe the fix produce the right one.** A test that mocks the client and asserts `.limit(1000)` was called is a self-comparison — it proves the code calls what the test expects it to call, not that the ceiling behaves as you believe. **At minimum instance 3 must be proven this way against a real client.** State per fix what you actually ran.

2. **Do not "fix" the watermark semantics.** `updated_at = highWater` is **correct** and load-bearing (design-of-record §4.1: a message committing *during* a regen keeps `last_activity_at` ahead of the captured mark and stays flagged stale, never silently lost). The defect is the **truncated read feeding it**, not the watermark design. Changing the watermark to wall-clock would reintroduce a real race this lane deliberately closed.

3. **Do not re-introduce a window on layer 10.** Item (c) removed `windowThread` from the normal path *on purpose*, on Justin's explicit ruling (*"forgetting the early part of a meta-meeting 30 messages in is a disaster"*). `windowThread` survives only as the `THREAD_HARD_CEILING_TOKENS` backstop. **If a thread genuinely exceeds what a wake can hold, the honest behaviors are (a) load it all, or (b) tell the agent loudly what it is missing — never silently hand it a prefix.** Which you choose is yours; silence is not on the menu.

4. **Typecheck strict-green + the full suite green** before you hand anything back. The suite is **299 tests** on `main` `9f48e8d`.

### Yours to decide (your lane, your design)
