## 1. The measured facts (ACfr ran this against the live team DEV database, 2026-08-05)

**This section is empirical, not inferred.** ACfr seeded 1200 marker rows into `cost_events` on the team DEV database, ran four read strategies against them, and deleted all 1200 afterward (verified 0 residual). Results:

| # | What was run | Result |
|---|---|---|
| 1 | The current production read, verbatim — `.select('usd_equiv').gte('created_at', since)`, no limit | **1000 rows of 1200. Sum $10.00 against a true $12.00.** |
| 2 | The same read with an explicit `.limit(1700)` | **Still 1000 rows.** The cap is enforced SERVER-side. |
| 3 | Cursor (keyset) pagination, page size 500 | **1200 rows, $12.00 — exact.** 4 requests. |
| 4 | Offset (`.range`) pagination, page size 500 | **1200 rows, $12.00 — exact.** 3 requests. |
| 5 | One `.range(0, 1099)` — a page request LARGER than the cap | **Returned 1000, silently.** |

**Three conclusions that DECIDE this build. Do not re-litigate them; they are measurements, not opinions:**

1. **The ceiling is real and it is 1000.** An unbounded read is silently truncated, and the truncation is invisible — there is no error, no flag, no short-read signal.
2. **Raising `.limit()` does NOT fix it (row 2).** A fix of the form *"add `.limit(50000)`"* is a no-op that reviews as a fix. If you find yourself writing one, stop.
3. **A page bigger than the cap is silently truncated (row 5) — so "I got fewer rows than I asked for, therefore I'm done" is only sound if you already know the cap.** That is the very dependency we are removing. **Cursor pagination terminates on a ZERO-row page instead, so its correctness does not depend on the ceiling's value.** That is why this spec mandates cursor and not offset, even though offset also worked here and costs one fewer request.

## 2. What you are building — a shared helper, then six call sites

### 2.1 The helper — `src/db/paginate.ts` (NEW file)

One place that knows how to read *every* row a filtered query matches. It belongs in `src/db/` beside `client.ts` / `keyed-mutex.ts` / `types.ts`, because it is a DB-read concern.

**Required behavior:**

- **Keyset (cursor) pagination on an ASCENDING timestamp column.** The caller supplies a query factory that takes `(cursor, limit)` and returns a supabase-js query. Each page resumes from the last row actually received.
- **Terminate on a page that yields ZERO NEW rows** — never on a short page. This is the whole point (fact 3 above).
- **Ascending order is mandatory and load-bearing.** Rows inserted *during* pagination get a newer `created_at`, so with ascending order they land at the END and the walk stays stable. Descending order would shift every page under you. Also apply a secondary `.order('id')` so ties have a deterministic order.
- **Handle duplicate cursor timestamps.** Use `.gte(cursor)` (not `.gt`) and skip rows whose id was already counted at that exact timestamp — otherwise `.gt` would skip rows sharing a microsecond. Keep only the ids at the boundary timestamp, so the set stays tiny.
- **Bounded page budget.** If the budget is exhausted with rows still unread, say so in the return value — never pretend completeness.
- **An optional caller-supplied early-stop.** Used by the ledger only (see 2.2).

**The return value must make the ending HONEST and un-ignorable.** Return a discriminated outcome, not a bare array:

- `'exhausted'` — every matching row was read. The result is the truth.
- `'stopped-early'` — the caller's own predicate said "I have enough." The result is a FLOOR, deliberately.
- `'budget-exhausted'` — the page budget ran out with rows unread. The result is a floor of UNKNOWN distance from the truth. **Every caller must branch on this.**

Exact names/signature are yours. Two hard requirements: the outcome is **not** a boolean (three states are three states), and it is **not** optional to inspect.

### 2.2 🔴 `src/money/ledger.ts` — `lastHourSpendUsd` — **BUILD AND PROVE THIS FIRST**

This is the runaway-spend brake. A runaway is precisely what generates >1000 `cost_events` rows in an hour, so today the total silently caps and **the brake reads low exactly when it must trip.** The safety mechanism weakens as the condition it guards against intensifies.

**Change it to:**

1. Read the trailing hour through the helper.
2. **Short-circuit as soon as the running sum reaches the ceiling.** Once `sum >= ceiling` the verdict is already `pause`; more rows cannot change it. This inverts the cost curve — the *worse* the runaway, the *earlier* the read stops. It needs the ceiling, so `lastHourSpendUsd` takes it as a parameter.
3. **Return the basis of the number, not just the number.** Three states, named honestly:
   - the exact total (read exhausted);
   - a floor that already reached the ceiling (short-circuited — verdict settled);
   - a floor of unknown distance (budget exhausted — **the brake could not establish safety**).

**`assessGlobalVelocity` (`src/money/budget.ts`) must consume the basis, and an unestablished total must PAUSE.**

- Order: over-ceiling → `pause`; **unknown-floor → `pause`**; ≥80% → `warn`; else `ok`.
- **The completeness input is REQUIRED, not defaulted.** A default would be fail-OPEN on a safety brake and a new call site could forget it. Make `tsc` force every caller to state it. Updating `tests/budget.test.ts` is expected.
- **Why pause on an unestablished total:** this runtime fails closed everywhere else that matters — `boot/env.ts` refuses on ambiguous config, `boot/schema.ts` refuses on a missing relation, `wakes/tool-gate.ts` denies on a gate error, `wakes/capabilities.ts` treats a missing grant as not-granted. A brake that cannot verify it is under the ceiling has not verified safety, and the house posture is to stop. Set the page budget generously enough that a legitimate hour never reaches it.

**The scheduler (`src/scheduler/index.ts`, the velocity gate in `cycle()`) must distinguish the two pause reasons in its message and its ping** — *"spend velocity $X/hr ≥ ceiling"* vs *"could not establish the last hour's spend (read N rows and there are more) — pausing because a brake that cannot verify safety must fail closed."* Justin reads these at 3am; the two mean different things and need different actions.

### 2.3 `src/composer/index.ts` — layer 10, the agent's working memory

The thread read. Until 2026-08-04 a hard 30-message window capped this; **memory-track item (c) removed that window on purpose** so "the thread IS the session" would be literally true. Above 1000 messages it silently isn't — the agent receives the **oldest** 1000 and believes it holds the whole conversation.

- **Paginate to completion.** Do NOT re-introduce a window — that is a hard constraint (Justin's explicit ruling: *"forgetting the early part of a meta-meeting 30 messages in is a disaster"*).
- `THREAD_HARD_CEILING_TOKENS` in `src/composer/layers.ts` already handles a genuinely enormous thread AFTER the rows arrive, and it windows LOUDLY with an elision marker. Leave that mechanism exactly as it is — it is the correct backstop and it now receives the true row set instead of a silent prefix.
- **If the page budget is ever exhausted, the agent must be TOLD, in layer 10, that it is not seeing the whole thread.** Silence is not on the menu; the honest options are load-it-all or say-what-is-missing. Set the budget high enough that this is a true backstop (the token ceiling bites long first).

### 2.4 `src/digest/index.ts` — `regenerateThreadDigest`, the watermark

Same unbounded read, and then `updated_at` is set to the newest message *received*. A truncated read makes "where I got to" a lie about how much was read — and because staleness is `last_activity_at > updated_at`, a short watermark makes the thread **permanently stale**: it regenerates every ~2 minutes forever, each time re-reading the same truncated prefix. That is the L7 spend-loop class this lane has already paid for once.

- **Paginate to completion**, then take the high-water mark from the true last row.
- **Do NOT change the watermark semantics.** `updated_at = highWater` is correct and load-bearing (design-of-record §4.1/§4.4: a message committing *during* a regen keeps `last_activity_at` ahead of the captured mark and stays flagged stale). The defect is the truncated read feeding it, not the design. Moving to wall-clock would reintroduce a race this lane deliberately closed.
- **On budget exhaustion: do NOT write the blurb or the watermark.** Writing a watermark from an incomplete read IS the bug. Log loudly and return `false` (the existing "keep the previous blurb" path); the composer already renders the loud stale marker.

### 2.5 Class Three — the retry floor, `refreshThreadDigestIfStale` (SAME FILE)

Today: `const wrote = await regen(...); if (wrote) lastRegenAtMs.set(threadId, nowMs);` — the ~2-minute floor is set **only on success**, so a persistently failing regeneration never records an attempt and retries on every 30-minute sweep *and* every on-read compose, unbounded.

**Set the floor on the ATTEMPT, not on the outcome** — record it immediately before calling `regen`, so a failure, a throw, and an empty-thread `false` are all rate-capped.

**Why this is not optional and not scope creep:** §2.4 above *creates a new persistent-failure mode* (budget exhaustion → return false). Under today's success-only floor that failure would retry unboundedly. **This is a defect my own change would introduce, so it gets fixed here** — not routed. The floor's purpose was always to rate-cap *attempts*; a failing attempt still costs a full thread read and a Haiku call, so it must be floored too.

**Deliberately NOT building retirement/escalation.** It needs durable cross-restart state to mean anything, it holds no position (nothing queues behind it), and the floor already bounds the cost to one attempt per thread per ~2 min. Recorded as a decision, not an oversight.

### 2.6 The audit riders — three more consequential sites, one honesty fix

ACfr classified all 63 `.select(` sites in `src/` (the table lives in the lane brief). These four are the remainder that the rule catches:

- **`src/digest/index.ts` `sweepThreadDigests` — the registry scan** (`thread_digests` where state != dormant). It determines WHICH threads regenerate and has **no ordering at all**, so a cap silently picks an arbitrary 1000 and every other thread never refreshes. Paginate. On budget exhaustion: log and proceed with what was read (a maintenance sweep makes partial progress; the next sweep continues) — this one does NOT need to fail closed, and say so in a comment.
- **`src/composer/index.ts` `buildDigestEntries`** and **`src/digest/index.ts` `freshenOtherRoomDigests`** — both read `thread_subscriptions` for one agent unbounded. They determine what the agent believes its rooms ARE; a cap silently removes rooms from ambient awareness. Paginate both. (`created_at` is not on this table — use `subscribed_at` as the cursor column, or confirm against `migrations/007_thread_subscriptions.sql` and tell ACfr if a different column is the right cursor.)
- **`src/composer/index.ts`, the stale-count** (`newSinceCount = since.length`) — a count derived from a row count, so it silently reports 1000 when it is more. It only feeds a display marker, so this is an honesty fix, not a correctness one: give it an explicit page size **that we choose**, and render a saturated count as `"N+"` rather than a wrong exact number. Do not paginate a display count.

**Everything else in the audit is deliberately untouched.** Do not "fix" the rest — 29 are write-returning clauses (`.insert(...).select('id')`), 9 already carry an explicit `.limit()`, 11 are primary-key reads that return at most one row, and 4 are bounded by the agent roster or the capability catalog. **One that looks wrong and is not:** `sweepDormantThreads`'s `.update(...).select('thread_id')` — the cap applies to the returned *representation*, not to the rows the UPDATE modifies (the `WHERE` runs server-side), and the return value is ignored. Leave it.

## 3. Testing — the part that is easiest to fake, so read it twice

**🔴 THE FAKE DB MUST SIMULATE THE CEILING.** A test that mocks the client and asserts *"`.limit(500)` was called"* proves the code calls what the test expects it to call — it does **not** prove the ceiling behaves as you believe, and it will pass just as green over a broken fix. **Build a fake that returns AT MOST N rows per request, seeded with more than N rows, and assert the OBSERVABLE OUTCOME**: the summed number, the composed text, the watermark actually written. Then the test is a real catcher.

**Every new guard test must be watched FAILING against deliberately-broken real code.** Break the thing the test guards → confirm RED → restore → confirm GREEN. **State this per test in your report.** This lane has been bitten three times by tests that compared a thing to itself, including once inside a test written to guard the previous instance of the same failure.

Guards required (at minimum):

1. `assessGlobalVelocity` returns `pause` on an unestablished total, even when the partial sum is small.
2. The velocity input is required — a caller that omits it does not compile.
3. `lastHourSpendUsd` against a ceiling-simulating fake sums ALL rows, not the first page.
4. `lastHourSpendUsd` short-circuits once the running sum reaches the ceiling (assert pages requested).
5. Layer 10 composes messages from beyond the first page.
6. Layer 10 says so loudly when the budget is exhausted.
7. `regenerateThreadDigest` writes a high-water mark equal to the LAST row of the full set, not of page 1.
8. `regenerateThreadDigest` writes NOTHING on budget exhaustion.
9. The retry floor is set on a FAILED attempt (a second call inside the window does not re-attempt).
10. The sweep scan reads past the first page.
11. The subscription reads read past the first page.
12. The stale count renders `"N+"` when saturated.
13. **Cursor correctness with duplicate timestamps** — rows sharing one `created_at` across a page boundary are each counted exactly once, never skipped and never double-counted.
