## §4 — 🔴 THE DRAFTED TEXT. This is the part that exists nowhere else.

### ② → `qc.md`, *Patterns This Role Watches For* *(house format; no dates, no Step numbers, per that section's own rule)*

> - **A change that ADDS or EXTENDS one member of a set of SIBLING constructs** — a third bucket beside two, a second paginator, a parallel row-writer, a new branch in a partition that already had two. **Failure:** the new sibling reliably inherits the set's *shape* and silently not its *properties* — the guard, the cap, the success-wins rule, the field, the assertion that every other member carries — so the set reads as uniform and behaves unevenly. **Nothing on the page is wrong:** each member is correct in isolation and only the *set* is uneven, which is why reading finds nothing and the suite stays green. **Move:** enumerate every member of the set, not only the one the diff touched, and put their properties side by side in one place; for each property ask *"does EVERY sibling have this, or only the ones that predate this change?"* Then run the same check over the siblings' **tests** — the asymmetry lands in the assertion as often as in the code. **Not** a demand that siblings be identical; many legitimately differ. The finding is a property that is **silently** absent, never one that is deliberately different — say which you concluded and why. *Seen 5x — four inside a single change-set (a success-wins rule applied to two of three id-buckets; a field set on one durable row and not its twin; an assertion written for one row and not the other; a page cap added to one paginator and not the sibling it was copied from), and once independently in a different runtime as a gate pair guarding one predicate in opposite polarity.*

### ② → `dc.md`, Build Mandate

> - **When you add a member to an existing SET of siblings, mirror its PROPERTIES, not just its shape.** A third bucket beside two, a second paginator, a parallel writer — the new one gets written to *look* like the others and reliably misses one thing they *do*: the guard, the cap, the precedence rule, the field. **Nothing fails**, because each member is correct in isolation; only the set is uneven, so neither the compiler nor the suite has anything to say. **The countermeasure is a test shape, not vigilance: assert the siblings in ONE block, so an asymmetry is visible on the page instead of having to be remembered.** *(QC's manual carries the review-side lens; this is the author-side half.)*

### ③ → `ac.md`, Architectural Mandate

> - **A fail-safe default is right when the failure would otherwise be SILENT — and WRONG when it converts a LOUD failure into a quiet one.** Bounding a value so garbage falls back to a sane default is the correct instinct most of the time, and it becomes a **regression** exactly where the unbounded version already fails loudly and diagnosably. **Before adding a bound, ask what the value actually DOES when it is garbage:** if it silently disables a guard, poisons a comparison, or coerces to something harmless-looking, bound it; if it throws at startup naming the bad value, **leave it alone** — bounding it trades the best diagnostic you have for a process that comes up "fine" and fails later with nothing in the logs to explain it. ⚠️ **Group by failure LOUDNESS, never by syntactic shape** — a set of knobs that look identical can fail in opposite directions. **And when you deliberately leave one unbounded, write the reasoning AT THE CALL SITE**, or the next person will "finish the job" as a cleanup.

### ② → `LEARNINGS.md` *(un-numbered appendage at the bottom of Unpromoted — numbers are assigned at `#sweep` promotion, never at capture)*

> **A NEW MEMBER OF A SIBLING SET INHERITS THE SHAPE AND SILENTLY NOT THE PROPERTIES — so assert siblings in ONE block, where an asymmetry is visible instead of remembered.** *Trigger:* any change that adds or extends one member of a set that already has two or more — a third bucket, a second paginator, a parallel writer, a new branch in an existing partition. *Failure:* the new member is written to *look* like its siblings and misses one thing they *do* — a guard, a cap, a precedence rule, a field, an assertion. ⚠️ **Nothing is wrong on the page.** Each member is correct in isolation and only the *set* is uneven, so reading finds nothing, the compiler is silent, and the suite stays green. *Move:* enumerate **every** member of the set, not only the one the diff touched, and lay their properties side by side; ask of each property whether *every* sibling has it or only the ones that predate the change — then repeat the pass over the tests, because the asymmetry lands there just as often. **The durable countermeasure is structural rather than attentional: assert the siblings in a single block, so the gap is visible at review time rather than dependent on someone remembering the set has three members.** *Evidence:* fired **four times inside one change-set** in one runtime, and **independently in a second runtime** as a gate pair whose two halves guarded the same predicate in opposite polarity — the same defect in different clothes. ⚠️ **Both domains, which is the bar — so the propagation target is the founding team's docs of record (`evryn-team-workspace/CLAUDE.md`, `shared/protocols/*`), which no AC/DC/QC manual reaches.**

### ③ → `LEARNINGS.md` *(same placement and shape)*

> **A FAIL-SAFE DEFAULT IS RIGHT WHEN THE FAILURE WOULD OTHERWISE BE SILENT, AND WRONG WHEN IT CONVERTS A LOUD FAILURE INTO A QUIET ONE.** *Trigger:* a hardening pass that routes a set of similar-looking inputs — env knobs, config values, parsed parameters — through a bounded/defaulting parser, on the reasoning that they share a shape. *Failure:* **the shape is not the property that matters.** One member of the set already fails **loudly** — it throws at startup naming the exact bad value — and bounding it replaces that with a silent fallback, so the process comes up healthy-looking and fails later with nothing to explain it. ⚠️ **The pass makes that one site strictly worse while making every other site better, and the result looks uniform and correct**, which is why nobody re-examines it. *Move:* for each site ask what the value *does* when it is garbage, and **group by failure loudness, never by syntactic shape** — silent-disable, poisoned-comparison and coerced-to-harmless get bounded; throws-at-boot-naming-the-value does not. Note that syntactically identical knobs can fail in **opposite polarity** (one comparison's false means "safe," another's means "broken"), so *"same shape"* reasoning is unsafe on exactly the set that invites it. **Where you deliberately leave one unbounded, write the reasoning at the call site**, because the next reader sees an inconsistency and finishes the job. *Evidence:* four env knobs of identical syntactic shape in one runtime — three failed silently (a disabled emergency escalation, a hot loop, a permanent false health-red) and were correctly bounded; the fourth threw a named error at boot, was bounded, reviewed, and **deliberately reverted**. ⚠️ **SECOND DOMAIN NOT CONFIRMED — anticipatory only:** the sibling runtime had no numeric env parsing at all when this was found, so the propagation target is **the first numeric knob added there.** *(Local half is DONE and needs no re-write: the governing principle and full mechanism sit at the call site in that runtime's config module, with a pointer from the test header.)*
