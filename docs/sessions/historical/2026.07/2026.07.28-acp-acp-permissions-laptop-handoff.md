## THE SITUATION — permissions were never taking, all session

**Symptom:** Justin had to manually authorize *every single Bash call*, all session, despite `_evryn-meta/.claude/settings.json` carrying a bare `"Bash"` allow rule (the broadest rule that exists).

### 🔴 THE ACTUAL ROOT CAUSE (found 2026-07-28, after several wrong turns)

**`~/.claude.json` had TWO entries for the same project, differing only in the CASE of the Windows drive letter — and the two front-ends read different ones.**

```
c:/Users/jbmcg/Evryn/Code/_evryn-meta  → hasTrustDialogAccepted: false   ← VS Code extension reads THIS
C:/Users/jbmcg/Evryn/Code/_evryn-meta  → hasTrustDialogAccepted: true    ← the `claude` CLI wrote THIS
```

The CLI normalizes the drive letter to **uppercase**; the VS Code extension uses **lowercase**. So accepting the trust dialog in a terminal genuinely works — and is invisible to VS Code, which keeps reading its own `false` entry. This is also why the extension never showed a trust dialog: from its perspective an entry already existed, it just said `false`.

**Fix applied:** `hasTrustDialogAccepted: true` set on **all seven lowercase-drive Evryn entries** (not just `_evryn-meta`) so DC/QC/Lucas sessions rooted in their own repos don't hit the same wall. Backup at `~/.claude.json.bak-pre-trust-fix`.

**If this recurs:** check for case-variant duplicate keys in `~/.claude.json` FIRST. Any per-project state keyed by path is vulnerable to this split, not just trust.

**The two layers it presented as (both real, both downstream of the above):**

1. **The repo is untrusted.** `~/.claude.json` records `"hasTrustDialogAccepted": false` for **every** Evryn project, including `c:/Users/jbmcg/Evryn/Code/_evryn-meta`. Claude Code treats a repo's `.claude/settings.json` as executable config (it can carry hooks), so in an untrusted folder it does not apply it. The allow-list was inert.
2. **Settings resolve once, at session startup.** Editing either settings file mid-session changes nothing. This is why the mid-session fix attempt could not be validated, and why a restart is mandatory.

**What was NOT the cause** (tested and eliminated — do not re-litigate):
- User-level settings overriding project settings. `~/.claude/settings.json` originally had **no** `permissions` block at all, so there was nothing to override with.
- `cd` in compound commands. A wrong theory, briefly asserted and retracted.

**The sandbox's real role — it is NOT the root cause, but it shapes every symptom.** Sandboxed commands are auto-allowed *without consulting the allow-list at all*. So:
- Local, read-only, in-project commands (`git status`) run **silently even with permissions fully broken** — they never reach the permission layer.
- Anything that **escapes** the sandbox — network egress to a non-allowlisted host, writes outside the project root — falls through to the allow-list, and prompts when it isn't loaded.

This is why `git status` felt fine while `git pull` across ten repos (network + writes into nine outside directories) and every Slack ping (network to `hooks.slack.com`) always prompted. **⚠️ Consequence for testing: a silent simple command proves NOTHING about permissions.** Always test with something that escapes the sandbox — the Slack ping is the ideal probe.

**⚠️ The methodological trap that burned the previous session twice — do not repeat it.** A Bash command producing output is **NOT** evidence that permissions work. Justin was approving each prompt, so every command "succeeded." Permission state can only be established by **Justin reporting whether a prompt appeared.** Never infer it from command success. The previous session claimed "PERMS OK — verified" on exactly this bad inference and had to retract it.
