### 6.1 The two isolation lines

**The lines, verbatim.** `identity/core.md:56` — *"When someone trusts you with their truth, it lands somewhere that is structurally incapable of betraying them — not because you've promised, but because of what you are."* `identity/internal-reference/trust-arc-scripts.md:58` (beat 4, "Go Deeper") — *"Each person's conversation with you is completely isolated — its own separate track, its own heavily-encrypted database query. No one on the platform can browse, search, or discover other users."*

**What the code does today:**
- **Cross-user notes leak back into context (Step 97). [read]** `create_user` (`src/triage/classify.ts:1962–2010`) returns `JSON.stringify({ user, created })` from `findOrCreateUser`, whose find path uses `findUserByEmail` (`src/db/users.ts:28–40`, `.select("*")`), so **every column including the firewalled `cross_user_notes`** comes back to Evryn. The tool is in the always-on list (`classify.ts:2696–2712`). It fires as soon as any user has a cross-user note and Evryn calls `create_user` on them. **After T-101 fix 1:** the column is stripped at the helper boundary.
- **Reads are scoped to "some identity key", not to the person in the conversation. [read]** `supabase_read` is always on (`classify.ts:2697`). Its guard `evaluateSupabaseRead` (`src/security/supabase-read-guard.ts:363–368`) takes only `{table, select, filters, limit}`, **with no knowledge of whose conversation this is**. For `users` / `messages` / `emailmgr_items` it requires an equality filter on an identity key (`:92–103`, e.g. `messages`: `sender_id`, `recipient_id`, `thread_id`…), **but any value passes.** So in a conversation with user A, Evryn can read user B's `users` row (minus `cross_user_notes`) or B's messages, by typing B's id or email. **This is T-101 fix 2.** **After it:** keyed to the verified channel. *(The design statement that "Evryn literally cannot reveal User B's info to User A because User B's data was never in her context window" — `ARCHITECTURE.md`, Identity Composition — is true of what the runtime **loads**, and not of what she can **fetch**.)*
- **"Heavily-encrypted database query" — no per-user or application-level encryption exists. [searched]** `git grep -i "encrypt|pgcrypto|pgp_sym|createCipher|crypto."` over `src/` returns nothing. The only encryption artifacts in the committed prod dumps are Supabase's built-in `vault.secrets` and the `extensions.encrypt` function grants (platform plumbing, unused by our code). **[inferred]** Supabase encrypts storage at rest at the provider level, which is not per-user and not per-query. **After T-101: unchanged; nothing in T-101 adds encryption.** ⇒ **This sentence is false today and stays false after T-101.**
- **"No one on the platform can browse, search, or discover other users." [read + inferred]** True for *users*: no user-facing surface exists in v0.2. For *Evryn herself*, see the read-scoping point above.
- **The context-contamination finding (§3), now T-101 fix 5,** also bears on "structurally incapable": her context very likely carries a developer file with internal pointers.

**[inferred] Net for Mira:** the true structural claims today are that one user's data is never *loaded* into another's prompt, there is no open messaging, and every outbound message is approval-gated.
