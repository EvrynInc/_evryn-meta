## 4 · New findings

### N9 · BLOCKER · `verify` lets the report choose the bound N. Truncating it hides a compaction or a stray write (a false PASS, exit 0); the same blind spot opens honestly in the same turn as `check`
- **What the code does:** `cmdVerify` re-hashes lines 1..`meta.n` and re-runs `check` bounded at `meta.n` (`packout.mjs` lines 310–316). Both `n` and `sha` come from the report. The sha is sha256(12) of the first `n` lines, which anyone can recompute.
- **Evidence, forged (`probes-1.txt` P9, P9b):**
  - A good packout plus a compaction marker (row 33) → `check` exit 1, C11 FAIL. I edited the report: `n` 33 → 32, `sha` recomputed by `hashFirst`, `C11: PASS`. Then `verify --report … --predecessor testsess --handoff …` printed **`VERIFY PASS same machine: transcript 1..32 sha 69a830a6a2f4 unchanged; 12 verdicts re-derived …`, exit 0.**
  - The same move with an unlisted, uncommitted Write after `n` (C10 FAIL) → **`VERIFY PASS`, exit 0.**
- **Evidence, honest (`probes-4.txt`; no field edited):** a repo file written in the same turn as `check`, whose Write row lands after `check` counted lines → `check` C10 **PASS**, `verify` **PASS** exit 0. The same check re-run at verify time, unbounded, gives **C10 FAIL ("written at 33")**. **The lag is real top-level:** each of AC-PG's two final real-path reports records N two rows short of its own `check` call (N=1220 against row 1222; N=1467 against row 1469; `checklag.mjs`). AC-PG's 18:20 entry also saw the false-FAIL face of it (C8, `check` run in parallel with the handoff Read).
- **Spec:** ruling ⓹ bounds verify at N, which is right for the *content* checks the transcript keeps growing past. But C6, C10 and C11 judge the **absence** of something bad, and for those a bound the seat chooses (or that lags) is an off switch. **A compacted seat is exactly the case the spec says must stop (C11).**
- **Fix sketch** (AC's design call; any one closes the forged face):
  - verify finds the last `packout.mjs check` Bash call whose output names this report (`report: <path>`), and judges at least to that row, not to `meta.n`; or
  - require that no write, launch or compaction lies between `meta.n` and that row.
  - **To close the honest face too:** judge C11 unbounded (a compaction anywhere before the successor starts means the predecessor compacted), and C6/C10 at least to the check call's own row.
- **Test that fails without it:** P9 (the forged `n` plus recomputed sha) must FAIL, and P9b too.

### N1 · BLOCKER · F1's fix compares the hostname, but the hostname is a report field: QC1's own forgery plus one more edit gets `DOWNGRADED`, on this machine, with the transcript present
- **What the code does:** the full re-check runs only when `fs.existsSync(meta.transcript)`; otherwise `meta.machine === os.hostname()` decides FAIL versus DOWNGRADED (`packout.mjs` lines 310, 325). Both inputs come from the report.
- **Evidence (`probes-1.txt` P1b):** QC1's P1 edits plus `machine: "SOME-OTHER-HOST"` → **`VERIFY DOWNGRADED (cross-machine) the report was made on SOME-OTHER-HOST; its transcript is not on this machine; checked only the report's hashes (handoff sha … unchanged; no FAIL). NOT a pass`, exit 3**, with or without the footer flags. `fs.existsSync(<real transcript>)` = true; host `JBM_XPS_15_9510`.
- **Why it matters even though exit 3 is "not a pass":** spec §3.3 makes the downgrade a **proceed** path ("the successor says so in its Report #0"). So the forgery buys a successor that proceeds with one disclosure line, from a report whose real check FAILed.
- **Fix sketch:** verify locates the predecessor's transcript itself, from the footer's `PREDECESSOR` (or `meta.session`), under `PACKOUT_PROJECTS_DIR`, with the same `findTranscript` that `check` uses. It treats `meta.transcript` and `meta.machine` as hints only. It downgrades **only** when no transcript for that session exists on this machine. (This also closes the copy route in N11's second bullet.)

### N13 · NON-BLOCKER (should-fix; an accidental false PASS on C7) · a second `begin` silently ignores its arguments
- **Evidence (`probes-2.txt` P13):**
  - begin #1 with no `--incoming` prints `BEGIN-ARGS: agent=soren · incoming=-`.
  - begin #2, same session, with `--agent AC-X --incoming <file>` → exit 0, `BEGIN-ARGS: agent=soren · incoming=-`.
  - begin #3, `--resume` from another session, with `--agent thea --incoming <file>` → exit 0, the same.
- **Consequence:** a seat that re-runs `begin` to add the incoming it forgot gets **C7 PASS ("no incoming handoff given")** without ever reading it. And a `--resume` onto a stale state (an abandoned packout of the same handoff path) inherits that state's agent and incoming, so a different profile is judged, and nothing says so.
- **Fix:** `begin` refuses (exit 1) when its `--agent` or `--incoming` differ from the state's, naming both. Or it records per-session arguments and prints the ones in force.
