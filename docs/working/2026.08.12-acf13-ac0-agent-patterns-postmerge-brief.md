### 8a. The canary — the arming mechanism, and the rule that matters more than the script

**`Monitor` streams each stdout line into your chat as a notification, and a notification RE-INVOKES you. So a script that prints one line every N minutes is a self-wake.** ⚠️ **`Monitor` and `TaskStop` are DEFERRED tools — `ToolSearch` for them first** (`select:Monitor,TaskStop`), **and kill the canary with `TaskStop` when you are done**, or it fires into a finished session.

```
Monitor({ description: "<name> self-wake", persistent: true, timeout_ms: 3600000,
  command: 'H=<absolute path to your handoff or todo doc>
while true; do sleep 600; echo "CANARY $(date +%H:%M) — you may have stopped. Your owed list is deliberately NOT in this message: read it live at $H. Then CONTINUE where you left off."; done' })
```

> #### 🔴 **NEVER PUT A STATIC LIST INSIDE THE CANARY. Point it at a document.**
>
> ***(Justin's ruling, 2026-08-17: "DO NOT put a static list into a canary — have it reference something — your running to-do list, a doc — anything but a list internal to the canary that immediately goes stale.")***
>
> **This is not a style preference; it was caught twice in one session.** A canary armed with an owed-list is **frozen at the moment you armed it** — so within an hour it is telling you to do work you have already finished, and **an instance that trusts it redoes finished work.** *(That is the same failure as a SPRINT Step whose scope is a checklist: shipping the items changes nothing about the list. Three instances of it were found in the tracker the same week.)*
>
> ⚠️ **Worse than useless, because it is CONFIDENT.** The canary's whole job is to orient an instance that may be disoriented — **so a stale one is a lie delivered at exactly the moment you are least able to check it.**
>
> **⇒ The canary carries ONE thing that is fixed: a pointer to where the truth lives.** If you want a live signal, compute it in the script from the file — never hardcode it. ⚠️ **And if the computation can be WRONG, drop it** — an early version of mine reported *"0 open items"* because its pattern did not match the file's format, which is a confident lie delivered at the moment the reader is least able to check it.

> #### ⭐ **AND THE CANARY SHOULD RE-CHECK EVERY SHARED DOC, EVERY TICK.**
>
> ***(Justin's design, 2026-08-17: "maybe everyone's night-time canaries should be a double-check on shared docs as well — that's something that could be written directly into the canaries, since that's a check-every-time kind of thing.")***
>
> **This closes a failure that occurred the same hour it was proposed.** A peer AC replied in a shared channel doc, **the watcher never fired, and it was found only because Justin asked directly.** ⚠️ **Root cause: re-arming a watcher RESETS ITS BASELINE, so anything that arrived during the gap is silently swallowed.** A killed process misses everything.
>
> **⇒ The two mechanisms are not redundant — they fail differently, which is the whole point:**
> - **The WATCHER is event-driven: low latency, but it can miss** (baseline reset, re-arm gap, process death) **and its silence is indistinguishable from nothing having happened.**
> - **The CANARY is a periodic sweep: higher latency, but it re-checks UNCONDITIONALLY**, so a missed event is caught on the next tick.
>
> **Concretely: have the canary print the LAST HEADING of each shared doc it is responsible for**, and say *"if that is not your own last entry, go read it."* Cheap, self-updating, and it cannot go stale because it reads the file every time.
>
> 🔴 **The rule this generalizes to, which is worth more than the script: ABSENCE OF A NOTIFICATION IS NOT EVIDENCE OF ABSENCE.** Any mechanism whose failure mode is *silence* needs a second mechanism whose output is *unconditional*.
>
> ⭐ **AND IT PROVED ITSELF WITHIN THE HOUR, ON A SECOND, DIFFERENT FAILURE — which is the strongest argument for it.** I killed the watcher intending to re-arm it without a retired file, **a good idea arrived mid-task, and I never completed the replacement.** For some minutes I had **no watcher at all** and did not know it. **The old canary firing is what exposed it.**
>
> **⇒ Two lessons, and the second is the more general one:**
> 1. **KILL-THEN-RE-ARM IS A GAP.** A monitor you stop *intending* to replace is a monitor you may simply not have. **Re-arm first where you can, or verify immediately after.**
> 2. **When you retire an instrument, kill it — do not just arm its successor.** I had **two canaries running** simultaneously for the same reason: I armed the improved one and never stopped the old. **The stale one kept firing with the older, weaker message.** *(Harmless here. In a mechanism whose whole purpose is telling a disoriented instance what is true, it would not always be.)*

### 8b. The watcher — and the refinement that makes a multi-lane inbox usable

**Same mechanism, different job: watch a file and be notified when someone else writes to it.** This is what makes a committed-doc channel work between a conductor and lanes running as separate instances.

**The naive version fires on EVERY change to the file — including your own.** With four lanes and a conductor answering in four docs, **that is four self-notifications per round**, and that noise is what buries a real lane entry at 3am.

```
who=$(grep -oE '^#{2,3} [^#]*\b(ACf[a-z0-9-]*|AC0-[0-9a-z]+)\b' "$f" | tail -1 | grep -oE '\b(ACf[a-z0-9-]*|AC0-[0-9a-z]+)\b' | tail -1)
case "$who" in
  <your own name>) echo "(self) $f grew — your own entry; no action." ;;
  "")              echo "INBOX >> $f grew but NO AC NAME in the last heading — read it yourself and do not trust this line." ;;
  *)               echo "INBOX >> $f — NEW ENTRY BY: $who. Read the bottom, answer IN THAT FILE." ;;
esac
```

**Two bugs were found in this instrument in one hour, both by running it and neither by reading it — which is the argument for the third branch above:**
1. **It fired on my own writes** *(fixed by the `who` check).*
2. **Matching the last `###` heading caught a SUBSECTION of my own reply**, so it reported the author as *"What I am doing on our side."* **Fixed by matching on an AC-name pattern rather than any heading** — and, more importantly, **by making the unmatched case SAY SO instead of reporting a confident wrong answer.**

⭐ **The generalizable rule, which is the part worth putting in `CLAUDE.md`: an instrument that cannot identify its input should say "I don't know," not guess.** The second bug was harmless because it was visibly absurd. **A slightly wrong name would have been believed.**

```bash
D="$HOME/Evryn/Code/_evryn-meta/docs/working"
cd "$D" || { echo "🔴 WATCHER DID NOT START: $D does not exist - it is watching NOTHING."; exit 1; }
f=<THE DOC>; [ -f "$f" ] || { echo "🔴 WATCHER DID NOT START: lane doc $f not found in $D."; exit 1; }
```
