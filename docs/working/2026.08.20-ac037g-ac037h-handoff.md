> *"I want to get rid of the 'working' folder. We have 'sessions' and 'working' and they're the same thing basically — it's just junk to have both."*

## 1.4 The companion rule, already landed

**A real doc is not a session doc.** A design doc, a research report, a spec — anything whose value outlives its session — **goes to its department's project folder, not to `/sessions`.** I wrote this into `.claude/agents/ac.md`'s routing table on 2026-08-20 with the one-question test: *would someone look for this because of what it CONTAINS, or only because of when it HAPPENED?*

### My draft

**A file, `docs/sessions/held-session-docs.md`. One row per held doc:**

| Path | Why it is alive (one line) | **Retire upon** (a testable condition) | Owner | Held since |
|---|---|---|---|---|

**Five design decisions, each with its reasoning, because the reasoning is the part you should attack:**

1. 🔴 **ABSENCE FROM THIS FILE MEANS RETIRABLE.** *This is the whole design.* A doc not listed is not held — it is a retirement candidate by default. **Without this inversion the file is decorative**, because the dangerous failure is not a stale row, it is a doc quietly held by nobody's decision.
   - ⭐ **What licenses such a harsh default: Justin's no-repointing rule makes a wrong retirement nearly free.** It is a `git mv`, the doc stays findable, and no reference breaks. **The two changes only work together** — do not adopt this half without that one.
2. **The condition must be TESTABLE, not a vibe.** *"Still in play"* and *"might be useful"* are true of almost everything and expire silently. **A condition someone can check in under a minute is the entire value of the file** — it converts an expensive re-derivation into a cheap boolean.
3. **The OWNER column exists so a condition never stalls.** If the owner is another lineage (ACT, ACv), the checker does not touch it — it pings. Without this, a cross-lane condition sits untested forever because nobody is sure whose it is.
4. **`HELD SINCE` is the staleness detector, and it works without anyone remembering.** **A row older than ~14 days gets RE-JUSTIFIED at the next `#lock`** — not auto-retired, re-argued. *(Same shape as the `current-state` bulletin's "an entry more than 7 days old is OVERDUE BY DEFINITION," which already works precisely because the date does the work rather than someone's memory.)*
