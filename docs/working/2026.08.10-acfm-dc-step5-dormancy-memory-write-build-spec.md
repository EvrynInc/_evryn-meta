## 0. What this is, and why it is the piece that makes the rest safe

Threads in this runtime **age out**. After 7 days with no activity a thread goes dormant and its shared blurb stops appearing in every member's ambient digest. Step 2 made that digest **ever-member visible** — you keep seeing a room's blurb after you leave it — which means the digest is now the *only* ambient trace a room leaves behind.

**So a thread that ages out with nothing written down simply vanishes from every member's awareness.** That is real context loss, and it is *worse than the behavior we had before*, because the digest is what people now rely on. Step 5 closes the lifecycle: **join → participate / leave → age out → memory.**

**What it does, concretely:** when a thread goes quiet, every agent who was **ever** a member of it — leavers included — is woken **one last time, fully composed as themselves**, with the whole thread loaded, and writes **its own** memory of what that thread meant to *it*. Not a shared summary copied into eight memories: eight different memories, each from its own perspective, because a digest is shared ambient awareness while a memory is intimate and written once. Justin's framing, and it is load-bearing: *"the equivalent of joining the thread one last time."*

**The cost is real and already accepted.** Each write is a full ~64K-token Opus wake even though its output note is a paragraph. Justin weighed that and took it. Your job is to make sure it happens **once** per (thread, agent) and cannot stampede.

## 2. What you are building

### 2.1 Migration `018_thread_dormancy_writes.sql` — the per-member completion record

```sql
create table if not exists public.thread_dormancy_writes (
  thread_id    text        not null,
  agent        text        not null,
  completed_at timestamptz not null default now(),
  primary key (thread_id, agent)
);
```

- RLS enabled, service-role-only, richly commented, idempotent — house style, matching 015/016.
- **The header comment must carry the invariant this table exists to enforce**, stated positively: *a thread's digest may only disappear after every ever-member already holds its memory.* A row here means "this agent's closing memory for this thread has landed." **A missing row is the retry**, which is why nothing is ever recorded optimistically.
- Note the deliberate rhyme with `message_processing` (Step 4): the same per-(scope, agent) crash-safe shape, for the same reason — a parked or crashed wake leaves no row, so the next sweep picks it up again. Say so in the comment; a reader who sees the parallel will not "simplify" either one.
- **Add `{ kind: 'table', name: 'thread_dormancy_writes' }` to `EXPECTED_SCHEMA` in `src/boot/schema.ts`, in this same trip** — same reason as Step 4: it is what makes migration-then-code self-enforcing.

### 2.2 The two-phase lifecycle — rewrite `sweepDormantThreads` in `src/digest/index.ts`

Today (`src/digest/index.ts` ~615) the whole function is one UPDATE: everything past the cutoff goes straight to `dormant`. **That is the hole.** Marking dormant drops the digest, and the memory writes would be enqueued separately — so a crash, a park, or one failed write between the two leaves the thread **gone from everyone's awareness with nothing written down**: exactly the silent loss this Step exists to prevent, reintroduced by its own mechanism.

**Required shape — three deterministic phases, all idempotent, run in this order:**

**(a) live → `closing`.** Any thread with `state = 'live'` and `last_activity_at < cutoff` becomes `closing`. **The digest STAYS VISIBLE** — and it stays visible *structurally*, not by anyone remembering: both composition-side filters are already `.neq('state','dormant')` (`src/digest/index.ts` ~133 and ~547), so a `closing` thread's blurb keeps composing with no change from you. **The filter IS the invariant. Do not touch those two lines**, and add a comment at the transition saying that they are what makes this safe.

**(b) `closing` → fire the outstanding writes.** For each `closing` thread, compute the outstanding set (§2.3) and enqueue one dormancy wake per outstanding ever-member. This is the only phase that spends money.

**(c) `closing` → `dormant`, and ONLY when the outstanding set is EMPTY.** Every ever-member holds a `thread_dormancy_writes` row → mark `dormant`, and the digest drops. A failed or parked write leaves the thread `closing` with its digest still up, and the next sweep retries it.

⚠️ **Idempotency is not optional here, and here is the specific reason:** today's predicate is `.neq('state','dormant')`, which **re-matches every `closing` row on every single pass**. The completion record is the only thing standing between that and a duplicate ~64K Opus wake per member per pass.

### 2.3 The outstanding set — and the deadlock you must design out

> **outstanding(thread) = ever-members(thread) ∩ ACTIVE_AGENTS − {agents with a `thread_dormancy_writes` row for that thread}**

- **ever-members(thread)** = every `thread_subscriptions` row for that thread, **with NO `dismissed_at` filter**. Leavers are ever-members: they kept the digest, and they deserve the ending. (Contrast with Step 4's fan-out, which uses *current* members — `dismissed_at is null`. The two are deliberately different questions; do not unify them.) **Put this reader in `src/threads/membership.ts`** beside Step 4's fan-out, *not* in `digest/index.ts` — it is a membership question, and it keeps your diff out of ACfw's file. It is bounded by the agent roster, so it needs no pagination; say why in a comment.
- **🔴 INTERSECT WITH `ACTIVE_AGENTS`, and this is the deadlock guard, not an optimization.** A subscription row belonging to an agent that is no longer a configured main can never produce a wake — so without the intersection its completion row never appears, the outstanding set never empties, and the thread **sits in `closing` forever with its digest permanently visible.** That is a silent, permanent leak of a room that should have closed. Comment it as the deadlock guard so nobody removes it as redundant.
- **An EMPTY outstanding set on the first pass is correct and must go straight to `dormant`.** This is what keeps **finding L2** ("pseudo-threads aren't rooms") honored *structurally*: the `bump_thread_activity` trigger creates a `thread_digests` registry row for **every** thread id including `wakeup:<id>`, `checkin:…` and `system:parked:…`, and those have no subscriptions — so their ever-member set is empty, they complete instantly, and **no dormancy wake ever fires into a pseudo-thread.** Do not add a separate prefix check; the empty set already is the check. **Test it explicitly** — that this falls out for free is exactly the kind of property that gets broken later by someone who never knew it was load-bearing.

### 2.4 🔴 The stampede landmine — the sweep's cadence, and a comment that becomes a lie

**`sweepDormantThreads` is called on EVERY 15-second scheduler cycle, ungated** (`src/scheduler/index.ts` ~441). The digest sweep right above it is time-gated to 30 minutes; the dormancy sweep is not — and **the comment at `src/scheduler/index.ts` ~193–195 justifies that explicitly**: *"the dormancy sweep stays every cycle (a cheap deterministic UPDATE, no model)."*

**Your change makes that sentence false.** It becomes a call that can enqueue a full Opus wake per ever-member per thread.

**Two things are therefore mandatory, in the same commit:**

1. **Give the dormancy sweep its own cadence gate**, exactly mirroring `lastDigestSweepAt` — a `lastDormancySweepAt` and an exported `DORMANCY_SWEEP_INTERVAL_MS`. **Use 30 minutes.** A thread ages out on a 7-day boundary; resolving that up to 30 minutes late is invisible, while running it every 15 seconds is four sweeps a minute over a table that only grows.
2. **Rewrite the comment.** This is a defect your own change creates, not an adjacent bug — the rule is that you fix it here. The new text should say what is now true: the dormancy sweep is gated because it can *spend*, and the completion record is what makes a re-entered `closing` thread cheap.

⚠️ **Belt and braces, and take both:** the cadence gate bounds how often the sweep *runs*; the completion record bounds what each run *costs*. Neither alone is enough — a 30-minute gate with no completion record still re-fires every write every 30 minutes, forever.

### 2.5 The dormancy wake itself

Add a **third trigger kind**, `'dormancy'`, alongside `'wakeup' | 'message'` in `src/scheduler/dedup.ts`.

**Derive the candidates statelessly in the scheduler's `cycle()`** — from (`closing` threads) × (their outstanding sets). Do **not** invent a queue table. The database state *is* the queue, which is what makes it crash-safe and idempotent for free, and it means the candidates ride the existing `planDispatches`, inheriting per-agent serialization and priority ordering with no new machinery.

- **Priority: the lowest tier (p3).** A closing memory must never preempt a live conversation. Sender is the synthetic `'system'` actor, which already classifies p3 — verify that rather than assuming it.
- **`threadKind: 'room'`** — earned, because §2.3's empty-set rule means a dormancy candidate structurally cannot exist for a pseudo-thread. Say that in the comment; it is the same "declare only what the site knows" discipline as Step 4.
- **Widening the union will surface every non-exhaustive switch as a compile error. That is the feature** — fix each one deliberately rather than adding a default case that swallows the new kind.

**The compose changes — exactly two lines, in ACfw's files, so keep them surgical:**

- **`WakeRequest` gains a mode** (`src/wakes/index.ts`) — e.g. `mode?: 'dormancy-write'`. Carry it through `buildPlannedWakeRequest`.
- **Skip layer 9 entirely** at `src/composer/index.ts` ~379: when the mode is `dormancy-write`, `digestEntries` is empty and `buildDigestEntries` is **not called**. Not merely un-freshened — *not composed at all*. This wake's only job is "what did THIS thread mean to me"; other rooms' summaries are noise for it, and skipping the layer saves the tokens as well as the fan-out. **Leave a one-line comment naming the ACfw collision** so a rebase conflict there is legible rather than mysterious.
- **Skip `freshenOtherRoomDigests`** at `src/wakes/index.ts` ~227. Without this, a dormancy sweep over N ever-members × M other rooms each fans out into a burst of Haiku regens, on a batch job, for rooms nobody is reading. (`wakes/index.ts` is *not* ACfw's file — you are free there.)

**🔴🔴 THE ONE THAT WILL BURN THE HOUSE DOWN: a dormancy wake must write NO message row. None.**

`migration 016`'s `bump_thread_activity` trigger fires **AFTER INSERT on `agent_messages`** and sets `last_activity_at = now()` for that thread. So if a dormancy wake mirrors a reply into the closing thread:

1. `last_activity_at` jumps to now → the thread is no longer past the cutoff,
2. the next sweep sees a live thread, and later re-closes it,
3. the closing memory fires **again**, forever —

**a self-sustaining ~64K-Opus-wake-per-member loop, which is precisely finding L7's failure class** (the park→wake→park loop that burned ~$144/hr and is the reason every park record is now written inert). And under Step 4 it is worse than a loop: the reply mirror **fans out**, so every other member wakes too.

**Required, structurally:**
- **No `deliverReply`** on the request.
- **The reply mirror at `src/wakes/index.ts` ~470 must not run for this mode** — and guard it *at the mirror*, not by hoping the model returns an empty reply. A guarantee that depends on model output is not a guarantee.
- **Write the comment at the guard explaining the loop**, naming the trigger by name. The next person to read that block must not be able to remove the guard without understanding what it holds back.
- **Red-verify it**: remove the guard, watch a test go RED proving a message row (or an activity bump) would occur, restore.

**Where the memory actually gets written:** through the existing wake-output `notes` path and `appendNoteToMemoryFile` — canary-guarded, atomic tmp+rename, git-committed. You are adding no new write path. **The prompt must tell the agent this is the thread-closing memory**, so a future instance reads it as an ending rather than a mid-stream note, and it should invite a short answer or `"none"` — a thread the agent barely touched deserves one line, and `"none"` is a legitimate completion.

**The thread-ID stamp (the echo rule).** `appendNoteToMemory`'s `meta` is `{ agent, timestamp, wakeId? }` — **there is no thread id**. Add one, **at the writer, once**: it is required here (a re-activated thread leaves the agent holding a memory *and* a fresh digest line, and without the shared id they read as two unrelated things), and SPRINT Step 6 is *only* this stamp, so building it here costs nothing extra and closes that Step's whole substance. Thread it through `appendNoteToMemory`, `appendNoteToMemoryFile`, and the `append_note` tool, into the entry header.

**Recording completion:** insert the `thread_dormancy_writes` row **only after the wake completes and its note has landed** (including a deliberate `"none"`). A parked, killed, or errored wake records **nothing** — that is the retry, and recording optimistically is the single most dangerous shortcut available in this build, because it drops the digest on a memory that was never written.

### 2.6 Tests

- **Phase transitions:** past-cutoff live → `closing`, never straight to `dormant`; `closing` with an outstanding member stays `closing`; `closing` with an empty outstanding set → `dormant`.
- **🔴 The atomicity invariant, directly:** a thread whose members have not all completed **still composes its digest**. This is the whole point of the Step — assert it, don't infer it.
- **Ever-members include leavers** (a `dismissed_at`-set subscriber is in the outstanding set).
- **The deadlock guard:** a subscriber outside `ACTIVE_AGENTS` does not block completion.
- **L2:** a pseudo-thread registry row produces **zero** dormancy candidates and goes dormant on the first pass.
- **Idempotency:** two consecutive sweeps over the same `closing` thread enqueue the writes **once**.
- **🔴 The loop guard:** a dormancy wake writes no `agent_messages` row and causes no activity bump.
- **Layer 9 is absent** from a dormancy-write composition, and `freshenOtherRoomDigests` is not called.
- **Completion is not recorded** when the wake parks or errors.
- **The stamp:** a note written from a thread-scoped wake carries the thread id in its header.
