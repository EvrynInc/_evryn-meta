## Item 1 — 🔴 A verified containment hole: `create_user` serializes the firewalled `cross_user_notes` column into Evryn's context

**Justin's call (2026-08-04 ballot, item 1a):** mint this as a numbered SPRINT Step and give it **its own lane.** Not folded into an existing lane; not fixed inside AC2's Step-35 work.

### What is wrong

`users.cross_user_notes` is **architecturally firewalled** — it is blind-write-only (`append_cross_user_note`), processed only by Reflection, and **Evryn must never see it**. That is ADR-027 Decision 3, and `ARCHITECTURE.md`'s Data Model section carries it.

The hole is a four-link chain, all in shipped code on `main`:

1. `findUserByEmail` and `findUserById` (`evryn-backend/src/db/users.ts`) both do `.select("*")` on `users`.
2. `select("*")` returns **every** column — including `cross_user_notes`.
3. `findOrCreateUser` returns that full row on its find path.
4. The `create_user` MCP tool handler (`evryn-backend/src/triage/classify.ts`) returns `JSON.stringify({ user, created })` — **no projection, no strip.**

### This is not an inference — the codebase documents the behavior against itself

`evryn-backend/src/security/supabase-read-guard.ts` was written about exactly this and states it verbatim:

> *"the handler does `db.from('users').select(args.select ?? '*')` → `select:*` returns ALL columns incl. cross_user_notes → a firewall-bypass."*

That module's `USERS_RETURNABLE_COLUMNS` constant exists **solely** as the all-columns-*except*-`cross_user_notes` list. But it is applied **only** on the generic `supabase_read` path. **AC4's Bundle 2 closed that door and left this one open.** The typed helpers were never brought under the same projection.

### The failure scenario

1. A gatekeeper gives feedback on a contact ("she never followed through").
2. Evryn routes it via `append_cross_user_note` to that contact's `cross_user_notes` — correct, by design.
3. Later, Evryn calls `create_user` with that contact's email. **The tool's own description actively invites this** as a have-I-seen-them-before check (*"`created: false` on a return-visit, so you can tell whether you've seen this person before"*).
4. The gatekeeper's **raw** feedback about that person — plus the reporter's `from_user_id` — lands in Evryn's context **while she is working with that person.**

That is precisely the wall ADR-027 Decision 3 exists to build, and its own stated premise is that instruction alone is not enough: *"If Evryn is one confused volley away from leaking 'uuid-12345 said he was bad in bed,' that's not firewalling — it's hoping the model follows instructions."*

### Severity, stated honestly

- **Not live today.** Prod has no contacts and no recorded cross-user feedback, so there is nothing to leak yet.
- **It goes live the moment the gatekeeper feedback loop runs** — which is core to how Mark calibrates Evryn's judgment, i.e. one of the first things that happens after he starts forwarding.
- `create_user` is registered **unconditionally** on all 8 `runEvrynQuery` pathways, so there is no pathway gating to lean on.
- Reachability is *ordinary operation*, not an edge case — the tool description points Evryn at this exact usage.

### Recommended fix direction (the owning lane should confirm it)

**Strip the firewalled column at the typed-helper boundary** (`findUserByEmail` / `findUserById` in `src/db/users.ts`), **not** at `create_user`'s return. Reasons:

- It closes the **class**, not the instance — any future tool that returns a full `users` row inherits the protection.
- It puts the projection in the same conceptual place the read-guard already put it, so there is one rule rather than two.
- ⚠️ **Watch the read-guard's own warning** while doing it: that module notes that *omitting* a real column from the returnable list silently **drops** it from reads (a legit-flow break), and that `story` / `profile_jsonb` must **stay** readable (Evryn legitimately needs the story to broker). So the fix is "exclude exactly one column," not "narrow to a hand-picked set."

## Item 2 — Add a NAMED efficacy check for the gatekeeper-recognition fix to Gate-B (SPRINT Step 88B)

**Justin's call (2026-08-04 ballot, item 3):** add it — routed to you because Step 88B lives in the sprint, which is yours to edit.

### The problem this closes, which generalizes past this one fix

AC2's Step 35b/35d pair fixes Evryn dismissing a real user's record as "the test account." It passed a full-load QC review: **GO, zero blockers**, 122 discriminating checks, five mutations red, typecheck clean.

**And none of that says the fix works.**

The change is *wording in a prompt*, aimed at changing how the model reasons. Unit tests can prove nothing regressed; they **cannot** prove Evryn now reads a thin-but-real record as real. The failure mode is that a correct *"safe to merge"* gets read as *"the fix works"* — and the stronger the unit coverage, the more convincing that false closure. Unnamed, the efficacy question silently never gets answered and the Step closes.

### The check to add

Under **SPRINT Step 88B (Gate-B)**, as a named line item with an owner:

> **Thin-record recognition (from Step 35b/35d).** With a **freshly-created gatekeeper whose profile is still thin** (no story written, no notes yet — i.e. the state a real gatekeeper is in immediately after `create_user` and before onboarding fills the profile), confirm Evryn treats the record as **real**: she does not refer to it as a test/fixture account, does not hedge on the person's existence, and does not decline to act on the basis that the record looks like a placeholder.

**Why Gate-B is the right venue, not a separate exercise:** Gate-B is already a *full create-from-zero* gatekeeper run. A freshly-created gatekeeper **is** the exact case Justin hit — `status: "active"` with an empty profile. The check costs nothing extra to observe; it only needs to be *named* so somebody actually looks.

### The durable lesson, if you want it recorded beyond this one check

This is a general class, and it is now a promoted QC review-pattern (in `evryn-quality/CLAUDE.md`, Justin-approved 2026-08-04): **a change whose code is deterministic but whose purpose is to change how the model reasons** needs its verdict split into *"safe to merge"* (unit-verifiable) and *"does it work"* (needs a live exercise) — with the efficacy half named, owned, and attached to a specific downstream gate. It is the mirror of the stubbed-coverage rule, and the more dangerous of the two, because there is nothing wrong with the review.
