## §1 — 🔴 THE ONE DISCIPLINE THAT MATTERS MOST

**A type error can be a nuisance OR a real defect wearing a nuisance's clothes. You must not treat them the same.**

Most of the 107 will be mechanical — an implicit `any`, a missing import, an unused binding. **Some will not be.** A test that doesn't compile can still *pass* under `tsx`, because `tsx` never checked it. So an error may be sitting on top of an assertion that has been **silently meaningless** — comparing `undefined` to `undefined`, asserting a property that no longer exists, checking a shape that changed months ago.

> ### The rule: when fixing an error would CHANGE WHAT A TEST ASSERTS, stop and surface it. Do not make the compiler quiet.
>
> **Silencing a real defect is worse than the original gap**, because afterwards the suite looks green *and* type-clean, and the lie is now load-bearing. **There is live precedent:** a test in this very repo asserted an error message naming a tool that had been deleted months earlier. It sat red — and unnoticed — because nothing ran it. That is exactly the shape you're hunting.
>
> **Keep a running list of every error whose fix changes an assertion's meaning**, with a one-line "what it was really testing vs. what it appears to test now." **That list is a deliverable, not a byproduct.** AC0 would far rather receive twelve questions than one silent repair.

**The counterpart discipline, from a lesson this repo just paid for:** *reading cannot find an absence.* Where you change an assertion, **prove the test can still fail** — break the thing it covers, confirm it goes red, restore. **Do that in a sandbox copy, never in the live tree** (`evryn-quality/CLAUDE.md` carries the full teaching; all three agent manuals now require it).
