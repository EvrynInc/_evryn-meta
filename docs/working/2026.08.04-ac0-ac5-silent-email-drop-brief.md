## §1 — THE DEFECT (I traced this myself; verify it yourself too)

**Provenance:** originally surfaced by a Soren (CTO) subagent on 2026-07-28, *in passing* during a costing assessment — explicitly NOT a diagnosis. **AC0-28 then independently confirmed it at source** on 2026-08-04, and found one nuance Soren's read didn't carry (§1.3). **Do your own trace anyway.** Treat everything below as a well-supported pointer, not a spec.

### §1.1 — The mechanism

In `evryn-backend/src/email/client.ts`:

```ts
// fetchViaHistory, ~L237
const messages = await Promise.all([...messageIds].map((id) => fetchMessage(gmail, id)));
const valid = messages.filter((m): m is EmailMessage => m !== null).sort(...);
```

Three facts compose into the bug:

1. **`Promise.all` over the whole history delta is UNBOUNDED parallelism.** Every message id in the delta fires a Gmail `messages.get` simultaneously. At a burst this is exactly the shape that triggers Gmail rate-limiting.
2. **`fetchMessage` swallows its own failure** (`catch { console.error(...); return null; }`, ~L495) — no throw, no alert, no record.
3. **The `null`s are then filtered out.** The email is now gone from the batch entirely.

Because it never reaches `planPollBatch` (`src/email/poll.ts`, ~L351), **`transientCount` stays 0**, so `pollOnce` advances `latestHistoryId` to `candidateCursor` — **past mail nobody ever read.** No retry, no alert, no trace.

**The identical pattern is at the second call site:** `fetchCatchUpBatch`, ~L408 — the cold-start / historyId-expiry recovery path. Both need fixing.

### §1.2 — Why this is invisible today

Neither existing guard can see it, and understanding *why* is load-bearing for your fix:

- **`safety/polling-dead.ts`** escalates on `consecutiveErrors`. A swallowed fetch throws nothing, so the poll cycle *succeeds*. Zero errors.
- **`safety/heartbeat.ts`** pings Healthchecks only *after a successful poll*. The poll succeeded. It pings green.

So the system reports perfect health while dropping mail. **Do not add a fix that preserves that property.**

### §1.3 — The nuance I found (Soren's read said "permanently lost"; it's narrower than that)

There *is* an incidental partial backstop. On a **restart or historyId expiry**, `fetchColdStartCatchUp` re-scans from `getNewestItemCreatedAt()` **minus a 1-hour margin** (`DEFAULT_CATCHUP_MARGIN_MS`, `deriveCatchUpPlan`). So a dropped email **is** recoverable — but only if the process restarts within roughly an hour of the drop, and only via that path. In steady-state running, nothing recovers it, and past ~1 hour it is gone for good.

**Why this matters to you:** it means (a) the severity claim is real but should be stated accurately, and (b) **the margin is not a design you can lean on** — it's a coincidence of a feature built for a different purpose. Don't "fix" this by widening the margin.

### §1.4 — Why it matters now

Invisible at Mark's steady-state ~200/day. **A gatekeeper's first day of forwarding is a burst** — auto-forwarder switch-on plus whatever backlog rides with it — which puts the highest-risk moment at the exact moment we can least afford it: a dropped introduction, in front of the pilot gatekeeper, that we never learn about.

## §2 — THE FIX (direction, not a spec — you own the design)

Two things must become true. The second is the architecturally interesting one.

**(A) Bound the concurrency.** Replace the unbounded `Promise.all` with a bounded-concurrency batch at both call sites. Pick the limit deliberately and make it env-tunable in `config.ts` (follow the existing `parseHaikuScreenMode` / `parseClusteringMode` pure-parse pattern, including their fail-safe-to-a-sane-default discipline — a garbage env value must never mean "unbounded").

**(B) 🔴 Make a fetch failure REACH the cursor decision as transient.** This is the real fix; (A) alone only makes the failure rarer.

The cursor decision lives in `planPollBatch` (`poll.ts`), which decides to hold the cursor when `transientCount > 0`. But the failure happens in `client.ts`, which currently returns `{ messages, latestHistoryId }` — **a shape with nowhere to put "and N of them failed to fetch."** So the fix requires changing the contract between `client.ts` and `poll.ts`.

**Precedent to follow, not invent:** the codebase already solves this exact shape for the circuit breaker. A breaker halt returns a `"halted"` outcome that `planPollBatch` treats **identically to `"transient"` — do not mark, hold the cursor** (`poll.ts` `HandleOutcome`, `safety/halt-signal.ts`). **Your failure mode wants the same treatment through the same seam.** Read that path before designing; matching it is almost certainly better than a parallel mechanism.

**Design calls that are yours** (decide them; don't ask me):
- What the new `fetchNewEmails` return shape is (a failed-id list? a count? a per-message result union?).
- Whether a partial-fetch failure holds the cursor for the *whole* batch (simplest, matches the existing all-or-nothing behavior) or something finer.
- The concurrency limit and its default.
- Whether a repeated fetch failure deserves its own alert, and if so via `notifyDev` (rate-limited — see `shouldAlertForKey` in `poll.ts`, already built for exactly this).

**One invariant you must not break:** re-processing an email is *safe* — the durable `external_id` dedup (`findItemByExternalId` + `resolveExternalId`) and the in-memory `processedIds` set both prevent duplicates. **Holding the cursor and re-fetching is cheap and correct.** Verify this yourself before you rely on it; it is what licenses the whole "hold and retry" approach.

**Defect independently re-confirmed at source**, exactly as §1 describes. Two additions:

- **There is a THIRD fan-out with the same pattern, not two:** `fetchLatestBatch` (`client.ts` ~L452). Naturally capped at 10 by `maxResults`, so its rate-limit exposure is small, but it swallows failures identically. **All three are in scope for the fix.**
- 🔴 **A wedge hazard §2 does not name, and it is the reason the fix is not just "make failures transient."** `fetchMessage` returns `null` for TWO categorically different things — *"this message is genuinely gone"* (deleted / no payload) and *"the fetch failed."* Making **both** hold the cursor would let a single genuinely-deleted message hold the cursor **forever** — retried every poll, mail piling up behind it, ingest permanently wedged. That is strictly worse than the bug being fixed. **Justin's explicit requirement (2026-08-04): no pathway may wedge like that.**

**The design AC5 settled (authoritative; supersedes §2's "design calls that are yours"):**

1. **Split the null.** `fetchMessage` returns a discriminated `FetchMessageResult` — `ok` · `gone` (404/410/no-payload → permanent, skip forever) · `failed` (429/5xx/network/auth → transient). It stays **total (never throws)** — an unguarded throw inside a fan-out rejects the whole batch (§6).
2. **Bounded concurrency** at all three call sites, via a `mapWithConcurrency` helper. New knob `GMAIL_FETCH_CONCURRENCY`, default **5**, bounds [1,25], mirroring `parseBoundedTimeoutMs` (AC2's Step-94 numeric fail-safe parse — a better precedent than the mode-parsers §2 pointed at). Garbage/out-of-range → default, **never** unbounded, never 0.
3. **`fetchNewEmails` returns `{ messages, latestHistoryId, failedIds }`;** `planPollBatch` takes `fetchFailedIds` and folds them into `transientCount` → whole-batch cursor hold, mirroring the existing `"halted"` precedent rather than a parallel mechanism.
4. 🔴 **Anti-wedge — new leaf `src/safety/fetch-retry.ts`**, shaped exactly like `safety/polling-dead.ts` (pure predicate + stateful shell + test-reset hook + canary). A failed id is retried under **two independent budgets** — `GMAIL_FETCH_MAX_ATTEMPTS` (5) **OR** `GMAIL_FETCH_MAX_HOLD_MS` (30 min), whichever exhausts first. Two bounds, not one: attempts alone stretch for hours under the poll loop's exponential backoff; wall-clock alone retires too fast during a fast-poll burst.
   **On retirement the id stops counting toward `transientCount` (cursor frees), but is never silent:** (a) a durable `emailmgr_items` row — `status: "escalated"`, `user_id: OPERATOR_USER_ID`, `external_id: <gmail message id>`, `metadata.reason: "gmail_fetch_failed"` — which the existing 4h stale-`escalated` re-ping backstops automatically, and whose `external_id` keying means a later-fetchable message dedups against it rather than double-creating; (b) `notifyEmergency`; (c) cleared from the map.
   **⚠️ The retirement path itself is wrapped in its own try/catch and retires REGARDLESS** — if the durable write fails (Supabase down), it still alerts, still logs, still frees the cursor. A retirement that can throw would rebuild the wedge inside the fire escape.
   **The invariant to check any future change against: every id ends in exactly one of three states — succeeded, `gone` (skipped permanently), or failed-then-force-retired under a bounded attempt count AND a bounded wall clock. There is no fourth state, and no state that holds the cursor indefinitely.**
5. **Alert tiers (Justin approved 2026-08-04):** held-and-retrying → `notifyDev` through the existing `shouldAlertForKey` 30-min gate, new key `"gmailFetch:transient"` (degraded, nothing lost). **Retirement → `notifyEmergency`** (mail actually lost). Split deliberately: if everything went to emergency it would be tuned out; if everything went to dev the real loss would be missed.
