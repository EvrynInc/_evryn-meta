## Class One — does NOT exist in the dangerous form

**The shape is here.** `digest/index.ts` has two fan-outs that swallow per-item failures:

- `freshenOtherRoomDigests` — `Promise.all(stale.map(r => refreshThreadDigestIfStale(...).catch(err => console.warn(...))))`
- `sweepThreadDigests` — the same pattern over the sweep's candidates.

**But the third ingredient is missing, deliberately.** A failed regeneration **never advances the watermark**: `regenerateThreadDigest` writes `thread_digests.updated_at` *only* on a successful blurb (`if (!blurb) { …; return false; }` before the upsert). So a swallowed failure leaves the thread marked stale, the next pass retries it, and the composer renders the stale blurb to the agent **with an explicit loud marker** (`⚠ stale: N message(s) posted since this summary; refresh failed — read_thread to catch up`).

That is the correct shape and it holds. **Verdict: does not exist.**

⚠️ **One caveat worth carrying, because it links your classes:** Class Two *produces Class One's outcome by a different route.* A truncated read advances the watermark on incomplete data — same damage (a position moves past unread content), different cause. So "Class One is clean" is true about the *error path* and not a statement about the *read path*.

## 🔴 Class Two — EXISTS. Three instances, verified at source

Your framing translated to this runtime: **PostgREST applies a default row ceiling when a query sets no explicit limit.** Three reads set none, and each then does something consequential with what came back.

### Instance 1 — the agent's working memory (`composer/index.ts`, layer 10)

```ts
await db.from('agent_messages').select('*')
  .eq('thread_id', wake.threadId)
  .neq('message_type', 'heartbeat')
  .order('created_at', { ascending: true }),   // ← no .limit(), no pagination
```

**Why this one is newly live and not longstanding:** until yesterday a hard 30-message window (`windowThread`) capped this layer, which made any underlying ceiling irrelevant. **Memory-track item (c) removed that window on 2026-08-04** — *specifically so an agent would load the whole conversation* ("the thread IS the session," ADR-052 §3.3). The window that made the missing limit harmless is exactly what we deleted. Above the ceiling, an agent silently receives the **oldest** N messages and believes it has the entire thread.

### Instance 2 — the digest watermark (`digest/index.ts`, `regenerateThreadDigest`)

Same unbounded read, and then:

```ts
const highWater = messages[messages.length - 1]!.created_at;   // newest message RECEIVED
… .upsert({ thread_id, blurb, updated_at: highWater })
```

**This is your "cursor that means where-I-got-to vs where-the-world-is" question, in its other form.** `updated_at` genuinely means "where I got to" — which is the *correct* choice — but a truncated read makes "where I got to" a lie about how much was read. Staleness is `last_activity_at > updated_at`, so a short watermark makes the thread **permanently stale**: it regenerates every ~2 minutes (the floor), forever, each time re-reading the same truncated prefix. **That is the L7 spend-loop class this lane already paid for once.**

### 🔴 Instance 3 — the runaway-spend brake (`money/ledger.ts`, `lastHourSpendUsd`)

```ts
await db.from('cost_events').select('usd_equiv').gte('created_at', since),  // ← no .limit()
… rows.reduce((sum, r) => sum + Number(r.usd_equiv), 0)
```

The sum feeds `assessGlobalVelocity`, which warns at 80% and **pauses the entire fleet** at 100% of the hourly ceiling.

**If this read is capped, the total is understated — so the brake reads low exactly when spend is highest**, because a runaway is precisely what generates enough `cost_events` to reach a ceiling. **The safety mechanism weakens as the condition it guards against intensifies.** This is the one I'd fix first.

## Class Three — a mild version exists; not a wedge

**Where:** `refreshThreadDigestIfStale` maintains an in-process ~2-minute floor per thread, but sets it **only on success**:

```ts
const wrote = await regen(db, config, threadId);
if (wrote) lastRegenAtMs.set(threadId, nowMs);
```

So a **persistently failing** regeneration never records an attempt, the floor never engages, and it retries on every 30-minute sweep *and* every on-read compose — **with no attempt bound, no wall-clock bound, and no retirement or escalation.** That is the unbounded-retry shape your §3 names.

**Why it is not the wedge you're warning about:** it **holds no position.** Nothing queues behind it; the only consequences are repeated Haiku spend and a thread that stays honestly marked stale to the agent. Your invariant ("every item ends in succeeded, permanently skipped, or force-retired") is violated only in the weak sense that there is no *retirement* — but there is also nothing being starved.

**Verdict: exists, low severity.** Folding it into ACfr's lane, since it lives in the same module as Class Two instance 2 and the same trip will be in `digest/index.ts` anyway. **Your §3 warning is noted and will bind that lane:** if we add a hold anywhere, it gets bounded on both axes with guaranteed retirement.

## Class Four — N/A. No column-level firewall exists here to bypass

**Answering explicitly rather than leaving it open, per your §4.**

The runtime *does* have the mechanical shape: `select('*')` appears in the composer's thread and tray reads, in `read_thread`, in `search_messages`, and in `get_job_status` — and those results **are** serialized into an agent's context.

**But there is no firewalled column for them to leak.** I checked every migration (001–016) and all of `src/` for any notion of a column an agent must not see: there is none. The only redaction machinery in the codebase (`redactToken` in `boot/workspace.ts`) scrubs a **git token out of error text**, not a database column. The team runtime's tables are agent-facing by design — `agent_messages`, `thread_digests`, `thread_scratchpads`, `jobs` — and hold no third-party or cross-user material of the kind the product's firewall protects.

**Two things that would change this answer, so a future reader knows what to re-check:**
1. **Item (d)** introduces a `message_processing` join table and internal members-wake. If any per-agent visibility rule ever lands, this question re-opens.
2. If the team DB ever stores anything about a *person outside the company*, the product's exact shape becomes possible here.

**Also worth recording as a mitigating property, not a defence:** every one of those `select('*')` sites **projects at render time** — `renderMessage` emits five fields, `get_job_status` formats specific columns. So even if a firewalled column were added tomorrow, the *rendering* layer would not automatically leak it. That is luck rather than design, though — nothing enforces it, and I would not lean on it.

## Your "one genuine ask" — Class Two has now appeared in two runtimes independently

Flagging it as you asked, because that is a different and more serious fact than either instance alone.

**The shared root is not "someone forgot a limit."** In both runtimes the unbounded read *reads correctly today* and only fails at a volume nobody has hit yet — so it passes review, passes tests, and passes production, right up until it doesn't. **The generalizable rule I'd propose for the manuals:**

> **Any read whose result determines a position, a watermark, a completeness judgment, or a safety threshold must set its page size explicitly and follow pagination to completion — or fail loud. An unset limit is a silent ceiling you do not control and did not choose.**

That is stronger than "paginate your API calls," because it names *which* reads matter: the ones feeding a decision about how much you've seen. A `select` that just renders a list can be capped harmlessly; a `select` that feeds `sum()` or a high-water mark cannot.

**I'd suggest it lands in `evryn-quality/CLAUDE.md`'s patterns list** (QC is the layer positioned to catch it on any diff, in either runtime) rather than in a tracker — but that's Justin's call and yours, and I'm not making it unilaterally.
