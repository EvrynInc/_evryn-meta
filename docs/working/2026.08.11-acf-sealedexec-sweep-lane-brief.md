## 1. The mission, in one paragraph

**On 2026-08-10 our own test suite executed code downloaded from the public registry, and nobody had authorized it.** Two files in `evryn-team-runtime` invoked a tool as `npx tsc`. When no local binary resolves, **`npx` silently downloads and runs a package of that name** — and someone had **squatted `tsc`**. Its banner printed live into our test output. **That is unreviewed third-party code executing on the machine that holds every credential this company has**, and its symptom is *a slow test*, not an alert. **Your job: find every place this can happen, across every repo, and close them — under a named, greppable rule so the next reader can check compliance instead of guessing.**

## 2. The rule you are enforcing — SEALED-EXEC

**It is already written, in `evryn-dev-workspace/CLAUDE.md` (Build Mandate). Read it there; do not re-derive it.** In one line: **never let an executable be resolved from the network at run time — invoke the local binary by path.**

**The five criteria for an authorized exception** (all must hold, plus Justin's explicit go): pinned exact version · integrity-verified in a committed lockfile · installed as a declared dependency · **no network access at execution time** · a named human decision.

**The comment convention, which is the whole audit trail:**
```
// SEALED-EXEC: followed <YYYY-MM-DD> — <what resolves it, and why it cannot reach the network>
```

## 3. Scope — every repo, and the enumeration must be DYNAMIC

**Sweep all active repos**, not a list someone typed once: `evryn-backend` · `evryn-team-runtime` · `_evryn-meta` (including `dashboard/`) · `evryn-website` · `evryn-ops` · `evryn-quality` · `evryn-dev-workspace` · `evryn-team-workspace`. **Enumerate them dynamically** — a hardcoded list silently omits the repo added last week.

**Sweep `src/`, `tests/`, `scripts/`, CI config, `package.json` scripts, Dockerfiles, and any shell invoked from code.** ⚠️ **The incident was in a TEST.** Do not treat test and script code as lower-stakes — it runs on the same machine with the same credentials, and it is *less* reviewed, not more.

## 4. 🔴 How to search — because the obvious grep is the one that fails

**`grep "npx "` IS NOT SUFFICIENT AND WILL GIVE YOU A FALSE ALL-CLEAR.** ACf ran exactly that across two repos, got nothing, and **correctly refused to report it as clean** — because it cannot see the form the vulnerability most often takes:

```js
spawnSync('npx', ['tsc', ...])      // ← invisible to `grep "npx "`
execFile('npx', [...])
spawn(cmd, args)                     // ← where cmd is a variable
```

**Search for the CLASS, not the string.** At minimum: every `spawn` / `spawnSync` / `exec` / `execFile` / `execSync` call site, and read what resolves the first argument · every `npx` / `bunx` / `pnpm dlx` / `uvx` / `pipx run` / `go run` anywhere · `curl … | sh` and `wget … | bash` · bare tool names in `package.json` scripts and CI steps.

**And then read the call sites.** A grep tells you where to look; **it cannot tell you whether the first argument resolves to a local path.** ⚠️ **A grep is evidence, never a completeness proof** — say so in your report, and say what you actually *read* versus what you *matched*.

## 5. What to fix, and what to route

- **Fix in place:** any invocation you can convert to a local path (`node node_modules/<pkg>/bin/<x>` and its equivalents), plus its SEALED-EXEC comment.
- **⚠️ Route, do not fold, anything that needs a dependency added or a build config changed** — that is a different review surface.
- **Every fixed call site gets the comment.** A fixed site with no comment is an incomplete change; the comment is what makes compliance checkable later.
- **Consider a guard.** A test that fails when a forbidden pattern appears in tracked source would make this structural instead of a one-time sweep. ⚠️ **If you build one, do NOT scope it through a hand-maintained list of directories** — that exact mistake is already tracked as a defect in `evryn-team-runtime` (SPRINT Step 31), where the anti-vacuity test iterates the same hardcoded constant it is meant to check, so it can never notice its own gap.

## 6. Explicitly out of scope

Package *dependencies* themselves (that is supply-chain review of `package.json`, a separate and larger question) · anything requiring a version bump · the product's own runtime behavior.

## 7. Laws for this lane

1. **A grep is evidence, never a completeness proof.** Report what you read, not only what you matched.

4. **Report UNKNOWN as unknown.** A repo you could not fully establish is *not* a clean repo, and saying so plainly is worth more than a tidy all-clear. **This lane exists because someone nearly reported an inconclusive grep as a clearance.**
