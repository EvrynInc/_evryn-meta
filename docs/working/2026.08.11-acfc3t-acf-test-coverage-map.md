## §3 — 🔴 `memoryWriteFailed`: Step 5's atomicity invariant has no executed coverage, and its attempt gate has none at all

**Why this matters:** `memoryWriteFailed` is the flag that stops the runtime recording a closing memory nobody actually wrote. If it is wrong, a thread's digest drops on a memory that does not exist — **the exact silent context loss Step 5 was built to prevent.**

**Both ends are source-asserted only, and nothing else:**

| End | Location | Guard |
|---|---|---|
| producer — flag set in the catch | `wakes/index.ts:548` | `dormancy-wake.test.ts:283` — regex over stripped source |
| producer — flag carried on the completed return | `wakes/index.ts:665` | `dormancy-wake.test.ts:285-290` — regex |
| consumer — `onCompleted` early-returns on the flag | `scheduler/index.ts:703-714` | `dormancy-wake.test.ts:255-279` — regex |

**There is no executed test anywhere that sets the flag, reads it, or exercises the interaction with `recordDormancyWrite`** — and there structurally cannot be one without a live SDK, because both producer sites sit **downstream of `query()`** (`wakes/index.ts:417`).

**Three specific things those regexes do and do not buy:**

- ✅ `/return \{ status: 'completed',[^}]*memoryWriteFailed \}/` **would** catch the mutation its comment names (`memoryWriteFailed: false` breaks the match). **That guard is real.**
- 🔴 **Nothing catches a change to the ATTEMPT GATE at `wakes/index.ts:528`.** Alter `output.notes.trim().toLowerCase() !== 'none'` and the write silently never attempts — so `memoryWriteFailed` stays `false`, `recordDormancyWrite` fires, and **the thread drops its digest on a memory nobody wrote. That is Step 5's exact failure, reachable through a line no guard touches.**
- ⚠️ **`dormancy-wake.test.ts:275-278`'s ordering assertion is very nearly tautological.** Its extracted region *ends* at `recordDormancyWrite(…)`, so `indexOf('recordDormancyWrite')` is at the region's end **by construction**; the ordering assertion can only fail if `memoryWriteFailed` is absent from the region — which the preceding assertion at `:266` already catches. **It reads as a strong ordering guard and adds approximately nothing.**

**How far a unit test CAN get into `runWake`** (traced through `composition-failure-honesty.test.ts`'s fixture, which — correcting `dormancy-wake.test.ts:14-15`'s header — **does** import and execute `runWake`): lines ~202–337 are reachable (budget block, gate read, `wakeCtx` assembly, the guarded freshen+compose section, and the whole composition-failure park path, which ends in `return { status: 'parked' }` at `:336`). **Everything from `:416` down is unreachable without the live SDK** — cost capture, all four remaining park paths, the memory write, the followup wakeup, the mirror and fan-out, and the `status: 'completed'` return.

**⇒ `dormancy-wake.test.ts:14-15`'s header should be corrected in place** — not because the distinction is academic, but because a reader who trusts *"there is no unit path through `runWake`"* will not think to extend `composition-failure-honesty`'s pattern, **which is currently the only demonstrated way to execute any of `runWake` at all.**

## §6 — Four wiring gaps where a pure function is proven and its wiring is not

**This is one recurring shape, and it is the most transferable thing in this report.**

2. **`workspace-git.test.ts:52-55` re-implements the runtime rule it claims to cover** — a live instance of QC's own *"a test helper that RE-IMPLEMENTS the runtime guard it covers"* pattern.
