## §1 — What is actually lost today, in plain English

**The setup, cold.** Each of the eight founding-team agents doesn't run continuously. It *wakes*: the runtime assembles a fresh prompt for it — who it is, its memory file, the whole conversation it's waking into, a one-line summary of its other rooms — the agent does its turn, and the wake ends. Next time, the runtime builds that prompt again from scratch.

**What survives a wake, and what doesn't.** What survives is everything the runtime writes down: the agent's identity, its `MEMORY.md`, the conversation transcript (including its own replies), and its private per-room scratchpad. **What does not survive is everything the agent did that it didn't say out loud** — its reasoning, every tool it called, every result it got back, and up to 40 intermediate steps of work inside a single wake.

**The concrete cost, which is real and is the thing worth fixing:** an agent can spend a whole wake investigating something, conclude *"nothing here yet, I'll keep an eye on it,"* and by its next wake have **no memory of having investigated at all.** It cannot know what it already ruled out. So it can look again, and again, and each look costs a full wake.

**What "giving them a session" would mean.** A session is the model's own running memory of a conversation — the way a normal chat works, where you don't re-explain yourself each message. It would fix the problem above completely, because nothing would be thrown away.

**My recommendation in one sentence: don't do it — but do fix the problem, with two cheaper things that target it directly.** The reason isn't cost or risk appetite. It's that a session would quietly break the single mechanism the whole memory design rests on: **that every wake re-reads the agent's memory fresh, so something learned in one room is in its head in the next one.** A session would freeze each room's copy of that memory at the moment the session started — so Lucas-in-room-A and Lucas-in-room-B would slowly become two different Lucases who no longer learn from each other. That is precisely the "different versions of the same person" failure the team already built a mechanism to prevent.

**The good news is that the two cheap fixes are genuinely cheap**, and one of them is nearly free: the runtime already *has* the agent's private per-room notepad, and it already tells agents to use it — it just tells them to record *where they are*, not *what they already checked and found nothing in*. That is a one-clause change. The second fix has the runtime record the agent's tool-work automatically, so it can't be forgotten. Details in §4.

## §2 — The recommendation, conditional on the persistence question

### §2.1 — The persistence question: ESTABLISHED, from the pinned SDK's own typings

The lane brief named one unknown as gating everything: **does an SDK session survive a process restart?** It matters because ARCHITECTURE cardinal invariant 4 says everything durable lives in Postgres — crash → Railway restart → re-arm losslessly — and a session living in SDK-side state would be the first thing in this system that isn't.

**I established it from the typings rather than by inference. The answer is two-branched, and the branch is a configuration choice we would be making:**

| | Where the transcript lives | Survives a Railway redeploy? |
|---|---|---|
| **Branch A — default** | The SDK persists sessions to disk under `CLAUDE_CONFIG_DIR`, by default (`Options.persistSession`, `sdk.d.ts:1546`, documented `@default true`; when false, sessions "cannot be resumed later"). **This runtime points `CLAUDE_CONFIG_DIR` at a temp directory** — `src/boot/env.ts:189-195` defaults it to `${TMPDIR/TEMP/TMP or /tmp}/evryn-team-runtime-claude-config`. | **NO** — and worse than "not persisted." It persists to precisely the directory designed to be discarded. |
| **Branch B — with `sessionStore`** | The SDK exposes a **pluggable external store** (`Options.sessionStore`, `sdk.d.ts:1558`; the `SessionStore` type at `sdk.d.ts:4647-4724`). Its `load()` is "Called once, in the SDK parent, before subprocess spawn. The result is materialized to a temporary JSONL file; the subprocess resumes from that file" (`sdk.d.ts:4670-4682`). **Postgres is explicitly contemplated in its own doc comment** ("e.g. Postgres JSONB may reorder object keys"). | **YES, in principle** — with three sharp caveats below. |

**Branch B's three caveats, all from the typings and all load-bearing:**

- **It is marked `@alpha`** — on `Options.sessionStore`, on the `SessionStore` type, and on every related helper.
- **It is a MIRROR, not a primary.** "The subprocess still writes to local disk… the adapter receives a secondary copy" (`sdk.d.ts:4635-4637`); `append()` is "Called AFTER the subprocess's local write succeeds — durability is already guaranteed locally" (`sdk.d.ts:4649-4650`). It **cannot** be combined with `persistSession: false` — "local writes are required for the mirror to function" (`sdk.d.ts:1552-1553`). So the durable path is still the container filesystem, with Postgres alongside it.
- **On failure it DROPS DATA.** "Rejection is retried (3 attempts total)… After the final failure the batch is dropped and a `mirror_error` system message is emitted" (`sdk.d.ts:4664-4667`). It is not silent — `SDKMirrorErrorMessage` is in the message union `query()` yields, so the runtime would see it — but a dropped batch is gone. **A store with a documented drop path is not the same guarantee as invariant 4.**

### §2.2 — The recommendation

> **Do NOT adopt sessions — and this holds on BOTH branches, for a reason that does not turn on persistence at all.**

- **If sessions do NOT survive a restart (Branch A, today's config): do not adopt.** A per-room session that evaporates on every redeploy is strictly worse than what exists — the agent would gain a memory it silently loses, which is a harder failure to reason about than never having had one. **This branch is disqualifying on its own.**
- **If sessions DO survive a restart (Branch B, Postgres-backed store): still do not adopt — but now the reason changes**, and it is §3.1 below: a session freezes the agent's identity and memory at session-creation time, which breaks the one-trunk model. Branch B removes the *persistence* objection and leaves the *architectural* one standing, untouched.

**⇒ The honest headline for a decision-maker: the persistence question, which everyone treated as the gate, turns out not to be the deciding factor.** I established it because I was asked to and because Branch A is genuinely disqualifying — but even had it come back clean, my answer would be the same. **The deciding argument is §3.1, and it is not in the lane brief, ACfm's analysis, or ADR-052.**

**What I recommend instead — three tiers, in order, and tier 3 is conditional:**

1. **Sharpen the scratchpad instruction from *status* to *work-done*.** Nearly free; rides two edits that are already scheduled. (§4)
2. **Build a deterministic per-wake work record from the `PostToolUse` hook that already fires.** This is the real fix, it targets the exact stated pain, and it preserves every invariant. (§4.3)
3. **Only if 1 and 2 prove insufficient**, run the bounded trial in §5 — and only on Branch B, never on Branch A.

**I agree with ACfm's shape** (*"do not swap the model wholesale, and do not dismiss the problem either"*) and I would **strengthen it in two places**: ACfm ranked the scratchpad instruction as the cheap 80% — I think it is less than 80% *and* cheaper than it thought (§8.1), and I would put the deterministic work record ahead of any session trial rather than treating a trial as the natural next step.

## §3 — The full cost ledger of adopting sessions

### §3.1 — 🔴 The decisive one: a session freezes the trunk, and the trunk is the design

**This is the argument I would want Justin to weigh above every other line in this document.**

**What the runtime does today, verified at source:** `composeWake` re-reads, from the workspace clone, **on every single wake** — the team manual and `runtime-ops.md` (layer 1), the Hub (2), team current-state (3), spokes (4), the agent's identity file (5), and **`MEMORY.md` (6)** (`src/composer/index.ts:305-360`). None of it is cached across wakes. The clone itself is refreshed on a ~15-minute pull.

**Why that matters — it is the mechanism the memory design explicitly rests on.** The design-of-record §4.6 states it directly: what an agent learns in room A reaches room B *"not by messaging herself but through the trunk: a thread-stamped note written in A is in her head the next time B wakes her — **because both wakes are the same mind loading the same memory**."* `runtime-ops.md:26` tells every agent the same thing in the cache-stable prefix of every wake: *"there is one memory: your notes land in your one trunk, and every wake starts from that trunk."* And the runtime writes those notes at wake end, into that same file (`src/wakes/index.ts:527-551`).

**⇒ Now put a per-(agent, thread) session on top of that.** Room A's session and room B's session each carry their own copy of identity + memory + current-state, frozen at whenever that session started. **A note Lucas writes in room A no longer reaches his live session in room B.** The trunk stops being a trunk and becomes N drifting branches.

**And this is not a new failure — it is a solved one, re-opened through a different door.** Per-agent wake serialization (SPRINT Step 3, merged `5ed56e5`) exists precisely to kill "a genuine momentary fork of one mind… the 'disembodied versions' failure" (design §4.6). It solved the *concurrency* form. Sessions would re-introduce the *staleness* form: not two wakes running at once, but two rooms holding two divergent frozen contexts indefinitely.

**⇒ The dilemma is unavoidable, and it does not depend on any unknown.** Either:

- **You re-send the full composed base on every resumed turn** to keep identity and memory fresh — in which case you pay the ~63K-token base (design §6.1's measured figure) **on top of** the whole accumulated session transcript, every turn. That is strictly more expensive than today, and the transcript has no equivalent of the 7-day age-out that currently bounds a thread. **This defeats the purpose.**
- **Or you don't** — in which case the session is permanently stale in identity and memory, and gets staler the longer it lives. **This defeats the memory model.**

There is no third position. **A session and a re-composed trunk are two answers to the same question, and the runtime already chose one and built five merged Steps on top of it.**

### §3.2 — The wake manifest stops describing what the model sees (invariant 2)

ARCHITECTURE cardinal invariant 2 makes every wake a diffable event: `composeLayers` emits a per-component `{name, chars, sha256}` array and `composeWake` persists it to `wake_manifests` (`src/composer/layers.ts:440-591`, `src/composer/index.ts:559-570`). Its stated purpose, in migration 010's own table comment, is *"the answer to 'they just got dumb and I don't know why'."*

**With a session, the manifest would describe the new turn and not the accumulated history the model is actually reasoning over.** The `SessionStoreEntry` type is explicit that transcript entries are opaque to us — "the concrete entry shape is… CLI-internal and not part of the SDK API surface… Adapters should treat entries as pass-through blobs" (`sdk.d.ts:4726-4744`). So the one artifact built to make an underperforming agent diagnosable would cover a shrinking fraction of the input. **This is a real loss and it is one of the runtime's genuinely unusual strengths.**

### §3.3 — Invariant 4, restated precisely

Covered in §2.1. Short form: **Branch A breaks invariant 4 outright. Branch B satisfies it only through an `@alpha` mirror whose documented failure mode is to drop a batch.**

### §3.4 — It makes a standing instruction false in all eight agents at once

`runtime-ops.md` is **composer layer 1** — composed into every wake of every agent (`src/composer/index.ts:61`, `TEAM_COMMON_FILES`). Its §1 tells each agent, verbatim: *"There is no hidden longer session behind this; what you see is what you have"* (`runtime-ops.md:22`). §1 also carries the note rule and the scratchpad relief valve that hang off that premise, and `:26` carries the one-trunk claim §3.1 is about.

**Adopting sessions makes those lines false in the cache-stable prefix of all eight agents simultaneously** — and correcting them is a Justin-gated identity edit that invalidates every agent's cached prompt prefix fleet-wide, which is exactly why such edits are batched (SPRINT Step 35). **So the change is not only architectural; it forces an identity edit, and a large one.** I did not attempt that wording, per my constraints.

### §3.5 — ⚠️ The compaction objection, honestly reported: it is WEAKER than when ADR-052 was written

**This cuts toward sessions and I am reporting it plainly even though my recommendation is against.** ADR-052 §3.2's stated basis is that SDK compaction "summarizes history opaquely and un-steerably." Against the pinned SDK, that is now substantially overstated:

- **Compaction is observable, structurally.** `SDKCompactBoundaryMessage` is in the message union `query()` yields (confirmed in the `SDKMessage` union at `sdk.d.ts:3908`), and it carries `trigger: 'manual' | 'auto'`, `pre_tokens`, `post_tokens`, `duration_ms`, and the preserved-message UUIDs (`sdk.d.ts:2864-2897`). The runtime's existing `for await` loop already sees every message and currently handles only `type === 'result'` (`src/wakes/index.ts:434-453`) — **it would take a branch, not a redesign.**
- **Compaction is interceptable.** A `PreCompact` hook exists, with `trigger` and `custom_instructions` (`sdk.d.ts:2193-2197`).
- **Compaction is plausibly disableable.** `Settings.autoCompactEnabled` exists (`sdk.d.ts:6366`, inside `export declare interface Settings` at `:4793`), and `Options` accepts settings in-process two ways — `settings?: string | Settings` (`:1835`) and `managedSettings?: Settings` (`:1859`). ⚠️ **I could NOT confirm this specific key is accepted by either path** — see §6.2.

**⇒ Two consequences worth stating separately.** First, **Justin's own proposal is available in a strictly better form than he proposed it**: he suggested *"give the agents a standing order to announce if they compact."* The runtime can **detect** compaction itself, deterministically, from a message it already receives — an instruction the agent could forget is not needed. That is structural rather than instructional, which is the house preference. Second, and this is the part that matters for the decision: **it does not rescue sessions**, because §3.1 never depended on compaction. **The original objection got weaker; a stronger one replaced it.**

## §4 — The cheap alternative, costed

### §4.1 — 🔴 Correction: the instruction already exists. It is scoped wrongly, not missing.

**The lane brief §2 and ACfm's Q1 both state that "nothing today instructs an agent to use the scratchpad as a working record." That is wrong as written, and I am the only lane that loaded the identity half to check it.**

`runtime-ops.md:25` — layer 1, in every wake of every agent — already says:

> **"You have a private scratchpad in each room — use it for working state, and keep it out of your memory.** `scratchpad_write` keeps one private note per thread: where you are, what you're tracking, a number you derived, what you're waiting on."

The `scratchpad_write` tool description says the same (`src/tools/tools.ts:359-375`): *"your current position, open points you are tracking, a number you derived, what you are waiting on."*

**⇒ What is actually missing is narrower and more specific: every one of those phrasings is about STATUS — where I am, what I'm waiting on. None of them is about WORK ALREADY DONE — what I looked at, and what I found nothing in.** That negative-result half is exactly the loss Justin named, and it is the half the current wording does not ask for.

**This makes the cheap option cheaper than ACfm costed it** — it is a clause added to an existing bullet, not a new beat competing for space in a Justin-gated file.

### §4.2 — What the instruction fix would and would not recover

| | |
|---|---|
| ✅ **Recovers** | The specific, repeated pain: *"I already checked X and there was nothing there."* Written once, it composes back into that room's wakes for as long as the room lives, and it costs nothing extra — the agent is already writing a reply. |
| ✅ **Preserves** | Every invariant. The scratchpad is our table (`thread_scratchpads`, migration 015), our data, in Postgres, composed as an enumerated layer 13 with its own manifest component. Inspectable and diffable — everything a session is not. |
| ❌ **Does NOT recover** | Anything the agent doesn't think to write. It is an instruction, and **instructions decay** — the team's own manual says so (`evryn-team-workspace/CLAUDE.md`, "Protocols decay in context"). |
| ❌ **Does NOT recover** | Work done in a room the agent has *left*, or in a `pseudo` scope. The write gate refuses anything that is not a declared room (`resolveScratchpadTarget`, `src/tools/tools.ts:153-176`), correctly — but that means a wakeup or check-in wake has nowhere to record what it investigated. |
| ❌ **Does NOT recover** | Detail at volume. The soft bound is ~4,000 chars with a nudge (`SCRATCHPAD_SOFT_MAX_CHARS`, `src/tools/tools.ts:103`), and it is a **snapshot, not a log** — each write replaces the whole note, so a rewrite can silently drop last week's ruled-out list. |

**⇒ My honest answer to the brief's question — "does an instruction alone close enough of the gap?" — is NO, not on its own.** It closes the common case cheaply and should be done immediately. But it is an instruction the agent must remember, governing a snapshot that overwrites itself, and the pain Justin named is exactly the pain of a thing being forgotten. **Closing a forgetting-problem with an instruction to remember is the weakest shape available.** That is why I recommend §4.3 alongside it, not instead of it.

### §4.3 — ⭐ The option nobody has proposed: a deterministic work record from a hook that already fires

**The runtime already receives everything needed, and currently throws it away.**

The `PostToolUse` hook is wired on every wake (`src/wakes/index.ts:392-396, 429-432`). Its input type carries **`tool_name`, `tool_input`, `tool_response`, `tool_use_id`, and `duration_ms`** (`PostToolUseHookInput`, `sdk.d.ts:2168-2178`). Today's handler reads two of those five fields and writes one line to stdout:

```ts
console.log(`[wake ${wakeId}] tool ${hookInput.tool_name} completed in ${hookInput.duration_ms ?? '?'}ms`);
```

**⇒ The proposal: capture a compact per-(agent, thread) record of what was called and what came back, and compose it back into that room's wakes** — as its own layer, or folded beside the scratchpad. Its properties are exactly the ones a session lacks:

- **Deterministic.** It does not depend on the agent choosing to write anything. This is the whole difference from §4.1, and it is the difference between an instruction and a structural invariant — the distinction the team's own writing protocol prefers.
- **Enumerable and diffable.** Our schema, our rows, a real manifest component. Invariant 2 holds.
- **Durable in Postgres.** Invariant 4 holds, with no `@alpha` dependency.
- **Steerable.** We choose what to keep, how much of a result to retain, and for how long — the exact control the ADR-052 §3.2 objection says a summarizer denies us.
- **Bounded by construction**, on the same lifecycle as the scratchpad — it dies at dormancy, after the closing memory has had its chance at it.

**Why this beats a session on the specific complaint.** Justin's pain is that an agent re-investigates what it already ruled out. A session solves that by keeping *everything*, at the cost of §3.1. A work record solves it by keeping *the part that was actually lost* — and unlike a session it is **ours**, so we can compose it wherever we want, including into a *different* wake in a *different* room.

⚠️ **Two things I want stated as caveats rather than sold.** (a) This is a real build with a migration, a composer layer, and a retention decision — larger than §4.1 and smaller than sessions; I have **not** scoped it and it needs its own design pass. (b) `tool_response` can be large, so what gets retained is a genuine design question (a truncated head? a hash plus a one-line shape? the agent's own one-liner?) — and getting it wrong re-creates the context bloat the scratchpad was built to relieve.

## §5 — If Justin wants a trial anyway: its exact shape

**I recommend against running this before §4.1 and §4.3 have been tried. If it runs, these are its terms.**

- **Precondition — hard: Branch B only.** A trial on today's `/tmp`-backed default (Branch A) would measure a session that vanishes at every redeploy and would teach nothing about sessions. So the trial requires a Postgres-backed `SessionStore` first — itself an `@alpha` integration.
- **Which agent: Lucas — and this is not a choice.** `AGENTS` in `src/config/agents.ts:40-49` contains exactly one entry, and `ACTIVE_AGENTS` is its keys. He is the only main stamped on.
- **Which thread:** one long-running Slack room, after the Meta-Meeting, deliberately chosen to be *busy* — a quiet room would never reach compaction and would prove nothing.
- **What to measure** — four things, and three of them are kill criteria:
  1. **Does the pain go away?** Count wakes where Lucas re-investigates something a prior wake in that room ruled out. This is the only success measure that matters.
  2. **Does compaction fire at all** under tight membership? Observable structurally via `SDKCompactBoundaryMessage` (§3.5) — log `trigger` and `pre_tokens`/`post_tokens` on every occurrence.
  3. **Does the trunk go stale?** Write a note in another room, then check whether the session room's next wake reflects it. **This is the §3.1 test and I expect it to fail.**
  4. **Token cost per wake** vs. the same room's pre-trial baseline.
- **What decides it — stop the trial if ANY of these occur:** compaction fires even once in a membership-bounded room; measure 3 shows the session carrying stale memory; or a `mirror_error` lands (`SDKMirrorErrorMessage`) showing the store dropped a batch.
- **What would make it a success:** measure 1 improves materially **and** measures 2–4 all stay clean. **I do not expect measure 3 to stay clean, and if it doesn't, §3.1 is confirmed empirically and the question is closed for good** — which is a genuinely useful outcome even in failure.

## §6 — What I could NOT establish

1. **Whether `resume` re-applies a fresh `systemPrompt`.** `Options.resume` is documented only as "Loads the conversation history from the specified session" (`sdk.d.ts:1761-1763`); nothing in the typings states whether a `systemPrompt` supplied alongside it replaces, appends to, or is ignored against the persisted one. **⚠️ Note carefully: §3.1's dilemma holds either way** — one answer gives staleness, the other gives cost — so this gap does not soften the recommendation. It would need settling before any trial.
2. **Whether `autoCompactEnabled: false` is actually accepted** through `Options.settings` or `Options.managedSettings`. The key exists on `Settings` and both options accept a `Settings` object, but `managedSettings` is documented as "filtered restrictive-only — non-allowlisted keys are dropped regardless" (`sdk.d.ts:1836-1846`) and **the allowlist is not in the typings.** `Options.settings` is not described as filtered, so it is the more plausible route — **but I did not verify either, and I did not run anything.** Reported as UNVERIFIED rather than inferred.
3. **Whether Railway's filesystem is genuinely discarded on redeploy for this service.** I reasoned from the runtime's own invariant 4, which presumes a disposable container, plus `CLAUDE_CONFIG_DIR` defaulting into temp. **I did not inspect the Railway service config and cannot rule out an attached volume.** This is a config fact someone with Railway access should confirm before Branch A is ruled out on my say-so — though note that a temp directory is a poor place for durable state even *with* a volume.
4. **Anything about session behavior at runtime.** This lane read typings and source; **it executed nothing.** No session was created, resumed, or observed. Every SDK claim here is a claim about the pinned `0.3.207` type declarations, not about observed behavior.
5. **Whether the eventual eight-agent fleet changes the arithmetic.** Every measured token figure I cite (design §6.1's ~63K base) predates seven of the eight mains existing. I did not re-derive it.

## §7 — Does this warrant an ADR?

**Recommendation: it depends on which way Justin decides, and only one branch needs a new ADR. I have not written one.**

- **If he declines sessions (my recommendation):** **no new ADR.** ADR-052 §3.2 already records the decision; what changed is the *reasoning*, and that belongs as a short dated amendment to ADR-052 — noting that the compaction objection weakened (§3.5), that the persistence question was settled against the pinned SDK (§2.1), and that a stronger objection replaced both (§3.1). **A decision that confirms an existing ADR should sharpen it, not spawn a second document that says the same thing** — that is the one-home discipline.
- **If he adopts sessions, or authorizes the §5 trial:** **yes, a new ADR** — it reverses a ratified decision, and the trial's kill criteria belong in the record before it runs, not after.
- **§4.3 (the deterministic work record) does not need an ADR to be *explored*** — it changes no ratified decision. It would need a design pass and, if built, a SPRINT Step.
