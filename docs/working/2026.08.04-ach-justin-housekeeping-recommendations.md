# QUEUE 3 — The four held test scripts

**What this is:** four scripts sit in `evryn-backend/tests/` outside version control. Each self-labels "EPHEMERAL … delete after use". They keep getting re-flagged as "don't touch" at every handoff without anyone revisiting why.

**Why they've been stuck:** nobody is protecting the *files* — the hold is on the **dev-database state they read** (a fictional gatekeeper record, "Megan"), which an outstanding verification still needs.

## 8. What I found — this is a real gap, and it's sharper than it looked

The test **data is committed and permanent**: 13 fictional-gatekeeper email fixtures, their answer key, and a README. Your build document calls this a **"permanent regression suite."**

But **nothing committed can actually run it.** Specifically:

- **The seeder is uncommitted and has no committed equivalent.** I checked: **no committed file anywhere sets up the Megan gatekeeper** — her user record, her mail lane, or her criteria. That capability exists *only* in the untracked `_gate-a-seed.ts`.
- **The runner is uncommitted, but a committed runner already does 90% of the job.** The committed `tests/run-fixtures.ts` runs the *general* 18 fixtures. It doesn't reach the Megan set only because it looks in one folder and doesn't descend into the sub-folder they live in.
- **Your own staging runbook already documents this**, independently of me: it notes the committed runner "does NOT read the `megan/` subdir yet" and that an automated run needs it pointed at the sub-folder — **a small change to the existing runner.**

**So if these four files are deleted as their headers instruct, a suite we call permanent becomes unrunnable** — and it's needed again for **Gate-B**, the mandatory full rehearsal before a real gatekeeper goes live.

## 9. My recommendation — and where I disagree with AC0

AC0's read was: delete the two forensics scripts, and **promote both** the seeder and the runner into the committed suite. **I agree on three of the four and disagree on one.**

- **9.a — `_gate-a-review.ts` and `_gate-a-times.ts` → DELETE** (agreeing with AC0). Both are genuinely one-shot: read-only database queries written for one past review. `_review` hard-codes a dev-specific record ID; `_times` hard-codes a list of six specific fixtures. Neither generalises.
- **9.b — `_gate-a-seed.ts` → PROMOTE into the committed suite** (agreeing with AC0). This is the real gap. It has **no committed equivalent**, it's the only way to stand up the fictional gatekeeper, and it's already well-behaved: it looks up rather than hard-coding IDs, and it hard-aborts if pointed at production.
- **9.c — `_gate-a-run.ts` → do NOT promote it as-is. Instead, extend the runner we already have** (this is where I differ from AC0). Promoting it would commit a **second** fixture-runner alongside `run-fixtures.ts` — duplicating the same file-parsing and pipeline-driving logic in two places that will drift apart. Your staging runbook already identifies the cleaner fix: **teach the committed `run-fixtures.ts` to take a folder argument** so it can run either set. That's a smaller change, removes a duplicate, and leaves one runner to maintain.
  - *One detail to carry over when it's built:* the held script's grading logic was written before the "runtime does the bookkeeping" change shipped, and one of its comments still describes the older world. The logic still works, but whoever does this should re-check it against how verdicts are recorded today rather than porting the comment.
