## 0. Orientation — what this runtime is, and what this Step changes

`evryn-team-runtime` runs Evryn's **AI founding team** (Lucas the CoS, Soren the CTO, Emma, Mira, and four more) as long-lived agents. An agent doesn't hold a session: it **wakes**. A scheduler polls every 15 seconds, finds triggers, and for each one composes a fresh 13-layer prompt (identity + memory + skills + the thread + a tray of addressed messages) and runs one Opus turn. Everything durable is a Postgres row; a crash and restart re-arms from the database losslessly.

**Today, an internal message wakes exactly one agent: the one named in `agent_messages.to_actor`.** That is the whole delivery model for agent↔agent traffic. It cannot express "this message is for the four agents in this room," and `agent_messages.processed_at` — a **single column on the message row** — cannot express "processed by Lucas, not yet by Emma." The first finisher marks it and every other member's trigger silently vanishes.

**Step 4 replaces that with membership.** A message posted into a room wakes **that room's current members, minus the author**. Membership is the gate: no model call, no heuristic — the member list *is* the wake list. Two new verbs let agents manage their own membership (`leave_thread`) and reach across rooms (`post_to_thread`). This is the single largest cost lever in the whole memory track: an 8-agent-relevant discussion where only the 3 needed agents are members costs 2–3 wakes per message instead of 7.

**Scale honesty, so you build with eyes open.** `ACTIVE_AGENTS` is `['lucas']` today. With one main, "members minus the author" is the empty set for every thread, so **almost nothing you build here changes live behavior until more mains stamp on (Phase 3)**. That is expected and accepted: getting the *schema* right is the expensive-to-change thing and we are in here now. Everything here is **unit-testable today** (fixture two agents' subscription rows and assert the fan-out) and **live-unverified until Phase 3**. Build it with tests; never let it read as proven.

## 2. What you are building — the seven pieces

### 2.1 Migration `017_message_processing.sql` — the per-recipient delivery record

**Why a join table and not a flag or a jsonb array** (decided by ACf 2026-07-16, do not re-litigate): a **per-agent cursor** ("messages since my last wake") would break ARCHITECTURE cardinal invariant 4 — a wake that *parks* still has a manifest, so it still advances a manifest-derived cursor, and a parked member would permanently lose a message. A **`processed_by jsonb` array** on the message row is read-modify-write on a hot row under concurrency, which is the exact hazard migration 012's `accrue_job_spend` exists to eliminate. The join table preserves crash recovery exactly: a parked member's row stays null and retries.

```sql
create table if not exists public.message_processing (
  message_id   uuid        not null references public.agent_messages(id) on delete cascade,
  agent        text        not null,
  processed_at timestamptz,
  created_at   timestamptz not null default now(),
  primary key (message_id, agent)
);
```

- **The partial index is load-bearing, not an optimization**: the scheduler runs the pending scan every 15 seconds forever, and the table only grows. Index the *pending* subset, which stays small:
  ```sql
  create index if not exists message_processing_pending_idx
    on public.message_processing (agent, created_at)
    where processed_at is null;
  ```
- **RLS enabled, service-role-only**, matching migrations 001–016 exactly. Idempotent (`if not exists` / `on conflict`) so a re-apply converges.
- **Column comments in the house style** (see 015/016 for the register). The `processed_at` comment must say what it means and what its NULL means: *pending for this agent; a parked or crashed wake leaves it NULL so the next cycle retries it — that is the crash-recovery property this table exists for.*
- **The header comment must carry the WHY**, at the length 015 and 016 use: what fan-out-on-write is, why the recipient set is frozen at write time (below), and that the late-invite behavior falls out of it structurally.

**Also in this migration — the two new tool capabilities.** A new tool is **silently dead** unless all five links land, and migration 015's header explains why each DB piece is separately load-bearing. Mirror 015's `(2)` block **exactly** for both `tool:leave_thread` and `tool:post_to_thread`:
- a `capability_catalog` row (absent → the capability is invisible to the operator in the dashboard),
- an `agent_capabilities` granted seed for `lucas` (absent → the **fail-closed** wake gate kills the tool for lucas),
- the `capability_tiers` `conversation-only` preset key (absent → every main that stamps on in Phase 3 never receives the grant, and the tool is silently dead for all of them).

Write the catalog descriptions **for the agent**, in the second person, at the length and warmth of 015's `tool:scratchpad_write` entry.

### 2.3 The fan-out helper — one home, called at every qualifying write

Create **one** exported function, in a new module (`src/threads/membership.ts` is the natural home — it sits beside `src/threads/kind.ts`, which already owns the thread-kind vocabulary):

```ts
export async function fanOutMessage(
  db: Db,
  args: {
    messageId: string;
    threadId: string;
    threadKind: ThreadKind;   // DECLARED by the caller — never parsed from the id
    authorActor: string;
    toActor: string | null;
  },
): Promise<string[]>          // the agents fanned to, for logging/tests
```

**The recipient rule, exactly:**

> recipients = (current members of `threadId`) ∪ ({`toActor`} if non-null) − {`authorActor`}, intersected with `ACTIVE_AGENTS`

- **Current members** = `thread_subscriptions` rows for that thread with `dismissed_at is null`. (Note the asymmetry and preserve it: *current* membership gates waking; *ever*-membership — no `dismissed_at` filter — gates digest visibility and, later, the dormancy memory. `src/digest/index.ts`'s `readEverMemberThreadIds` is the ever-member reader; do not "unify" them.)
- **`toActor` is the INVITE.** If `toActor` is non-null and not already a current member, **fan out to them AND upsert their `thread_subscriptions` row** (`subscribed_at = now()`, `dismissed_at = null`, `onConflict: 'agent,thread_id'` — the same shape `src/slack/index.ts`'s `subscribe()` uses). This is what makes "@mention/addressing = invite" structural instead of an instruction, and it is what keeps the current addressed-message path a strict subset of the new one — no regression.
- **Intersect with `ACTIVE_AGENTS`.** A subscription row for an agent that is not a configured main would otherwise accumulate rows nothing ever drains.
- **Insert with `on conflict (message_id, agent) do nothing`** so a retried fan-out converges.

**🔴 REFUSE TO FAN OUT INTO A PSEUDO-THREAD — fail closed, on the DECLARED kind.** If `threadKind !== 'room'`, return `[]` and write nothing. Two reasons, and both are load-bearing:
1. It is finding **L2** ("pseudo-threads aren't rooms") honored structurally. `wakeup:<id>`, `checkin:<agent>:<date>` and `system:parked:<agent>` are one-shot bookkeeping scopes, not rooms; nobody converses in them.
2. **It is what licenses §2.5's `'room'` claim.** Because the table can structurally only contain room rows, the candidate builder that reads it can honestly declare `threadKind: 'room'` — a claim it cannot support today. Weaken this refusal and you silently break that.

**Never infer the kind from the id's shape.** The kind is declared at the site that knows what it built and carried verbatim — that is the existing discipline in `src/scheduler/dedup.ts` (`CandidateTrigger.threadKind`) and `src/tools/tools.ts` (`ToolThread`), and it exists because a parked wakeup's park note re-enters carrying the wakeup's own one-shot thread id, and a shape-parser called that a room.

**Where it is called — enumerate and classify, do not guess.** Run `grep -rn "from('agent_messages')" src` and classify **every** insert/upsert site. As of `0c5f4fa` there are four, and these are the rulings:

| Site | Fan out? | Why |
|---|---|---|
| `src/wakes/index.ts` ~470 — the reply mirror in `runWake` | **YES** | This is members-wake for agent replies: Lucas answers in a room, and the room's other members hear it. This is the mechanism, not a side effect. |
| the new `post_to_thread` tool (§2.4) | **YES** | Its entire purpose. |
| `src/wakes/index.ts` ~519 — `parkNote` | **🔴 NO** | Park notes are written **inert** (`processed_at` set at write) because a park record that re-entered the scheduler woke the agent every 15 seconds under a persistent fault — one ~64K Opus wake per cycle, ~$144/hr (finding **L7**). Fanning a park note out to N members re-creates that loop N times over. **Write no `message_processing` rows for park notes at all**, and put a comment at the site saying why, citing L7. |
| `src/boot/recovery.ts` ~43 — the restart park note | **🔴 NO** | Same record, same reason. |
| `src/slack/index.ts` ~84 — `mirrorMessage` | **NO** | Inbound Slack traffic wakes through the Bolt handlers, and the scheduler's scan has always excluded `channel:'slack'`. Changing that is a different build with a different blast radius. Leave the Slack inbound path exactly as it is. |

⚠️ **The reply-mirror call must not change `runWake`'s failure posture.** A fan-out failure must not take down a completed wake — the reply is already delivered and already in the ledger at that point. Follow the file's existing pattern for non-fatal post-work.

### 2.4 The two tools

Both go in `src/tools/tools.ts`'s `createTools`, following the existing entries' shape exactly: `{ name, description, inputSchema (zod RAW SHAPE, not `z.object()`), handler }`. Both must be added to **`toolNames` in `src/wakes/index.ts` (~line 255)** — a tool absent from that list is filtered out of the wake's allowed-MCP set and is dead.

**`leave_thread`** — the agent's own exit. Today only Justin's 👋 or `/dismiss` can end a membership, which defeats the leave-freely half of the model, and leaving is where a real share of the cost saving comes from.

- **No arguments. It acts on `ctx.thread` — the thread this wake is scoped to.** A thread id is *never* a model-supplied argument on a write in this codebase, and this write has the silent-failure shape that rule exists for: a wrong id on `leave_thread` would leave a room the agent meant to stay in *and report success*, and the agent would simply stop being woken somewhere it thinks it still lives. `ctx.thread` carries id and kind together as one union precisely so this cannot be expressed wrong. Read the `ToolContext.thread` doc comment before you write this handler.
- **Refuse when `ctx.thread` is null, and refuse when `ctx.thread.kind !== 'room'`** — you cannot leave a one-shot scope you were never a member of. Return an honest, plainly-worded refusal explaining which case it is (the tool-refusal register in `resolveScratchpadTarget` is the model to follow).
- **🔴 UPDATE `dismissed_at`; NEVER DELETE the row.** The subscription row is the record of *ever*-membership, and ever-membership is what keeps the thread's digest visible to a leaver and what will earn them the thread's closing memory at age-out (Step 5). Deleting the row erases a person from a room's history. Use the same shape as `src/slack/index.ts`'s `dismiss()`.
- The success message should tell the agent what it just did *and what it keeps* — it stops being woken there, it keeps the thread's digest, and it can still `read_thread` it. That last part matters: an agent that thinks leaving is amnesia won't leave.

**`post_to_thread`** — post into another room you are a member of; its members wake.

- **Arguments:** `thread_id` (required), `body` (required), `to_actor` (optional — the invite).
- **A model-supplied `thread_id` is correct here and only here**, because reaching another room is the tool's entire purpose. What makes it safe is the membership guard below, which turns a typo into a loud refusal instead of a message shouted into a void.
- **🔴 GUARD: refuse unless the calling agent is a CURRENT member of `thread_id`** (a `thread_subscriptions` row for `ctx.agent` with `dismissed_at is null`). Design §4.6 is verbatim: *"post a message into any thread you're a member of."* Refuse loudly and name the thread id back.
- **Validate `to_actor` against `isSafeActorName`** (already exported in that file) and against `ACTIVE_AGENTS`; reject an unknown actor at call time rather than writing a row nobody will ever process.
- **Mechanics:** insert one `agent_messages` row (`from_actor: ctx.agent`, `to_actor`, `channel: 'system'`, `thread_id`, `message_type: 'fyi'`, `body`), then call `fanOutMessage` with `threadKind: 'room'` — which the membership guard has just *established*, so the claim is earned rather than assumed. Say that in a comment.
- **The description is runtime.** An agent reads a tool description at decision time, so it programs behavior as surely as code. It must convey: post into a room you're in; its members wake; use it to carry something across rooms or hand work over; optionally pull someone in with `to_actor`. Keep it concrete and short.

### 2.5 The scheduler — from addressed-scan to members-scan

In `src/scheduler/index.ts`'s `cycle()`, **replace** the `agent_messages` unprocessed-addressed scan (~line 359, the `.is('processed_at', null).in('to_actor', ACTIVE_AGENTS)…` query) with a two-query pending-members scan:

1. Pending rows: `message_processing` where `processed_at is null` and `agent in ACTIVE_AGENTS`, ordered `created_at` ascending, `.limit(CANDIDATE_SCAN_LIMIT)` (keep 50; name it as an exported constant so tests can reason about it).
2. Their messages: `agent_messages` `.in('id', <the ≤50 ids>)`, filtered `.neq('message_type','heartbeat')` exactly as today.

**Three things about that shape you must preserve deliberately, and comment:**

- **The `.limit(50)` is CORRECT and must NOT be "fixed" with pagination.** ARCHITECTURE cardinal invariant 8 requires pagination for any read whose result determines a position, watermark, completeness judgment, or safety threshold. This read is none of those: it is a **bounded work batch**, and anything it does not pick up stays pending and is retried on the next 15-second cycle. Paginating it to exhaustion would pull an unbounded backlog into memory to then discard all but one decision per agent. Write the comment that says so, or the next reader will "fix" it.
- **The second query's `.in('id', …)` is bounded by construction at ≤50 ids and is therefore safe** — but say so in a comment, because a sibling lane (`ACfw`) is right now fixing a **total wake outage** caused by an unbounded `.in()`: past roughly 370 ids the id list blows the URL length and PostgREST returns HTTP 414. Any `.in()` you add must be provably bounded, and this one is bounded by the limit above it.
- **Fairness:** ordering oldest-first guarantees progress (the oldest pending always makes the cut) and bounds starvation, exactly as today's scan does. Fan-out multiplies rows per message, so say it out loud in the comment rather than leaving it to be rediscovered.

**Rename `addressedMessageCandidate` → `memberMessageCandidate` in `src/scheduler/dedup.ts`, and change its declared `threadKind` from `'pseudo'` to `'room'`.**

> 🔴 **Read that function's existing ~20-line doc comment before you touch it.** It explains, carefully, why the answer *was* `'pseudo'` — the site was handed a mix of one-shot scopes and genuine Slack rooms (park notes copy `req.threadId` verbatim and stamp `channel:'system'`, sailing through the `.neq('channel','slack')` filter) with **no way to tell them apart**, so `'pseudo'` was the honest *"not established as a room,"* not a claim of one-shot-ness. **What changes is the epistemics, not the caution.** The candidate's only source is now `message_processing`, and §2.3's refusal means that table structurally cannot hold a pseudo-thread row. So the site can now declare `'room'` **knowingly**, which is exactly what that comment said item (d) would make possible.
>
> **Rewrite the comment to record the new reasoning and what licenses it** — do not delete it, and do not leave the old text in place. A comment your change makes false is a defect your change created. The rewrite must name the dependency explicitly: *this claim holds only while `fanOutMessage` refuses non-room threads.*

**Consequence to state, not to fix:** with the `to_actor` scan gone, park notes become permanently invisible to the scheduler. That is **L7's intent** (they are already written inert), so it is a confirmation rather than a change. Verify nothing else depended on that scan, and report what you checked.

### 2.6 The three findings routed here from Step 3

These are pre-existing defects that were deliberately **routed** to this Step because Step 3 touched the same code and a rider would have arrived with none of that build's review attention. They are in scope. Each gets a red-verified guard.

**(i) The `inFlight` lock-leak — `acquireThreadLock` in `src/scheduler/index.ts` (~225).**

```ts
if (inFlight.has(agent)) return false;
inFlight.add(agent);                 // added BEFORE the await
await persistThreadLocks(agent, …);  // if this throws, the add is never rolled back
return true;
```

A transient DB failure on that persist leaves the agent in the in-memory `inFlight` set **forever**: `planDispatches` skips an in-flight agent, so every subsequent decision for that agent defers, every cycle, silently. There is no park, no ping, and no recovery short of a process restart — the agent simply stops waking and nothing says so. Step 3 widened this from one-thread to whole-agent, which is what makes it worth fixing now.

**The fix is the rollback**: wrap the persist so a throw removes the agent from `inFlight` before rethrowing. Comment it — the reason the `add` precedes the `await` is that it must, to close the race, so the next reader needs to know the rollback is what makes that safe.

**(ii) The lying log line — `dispatch()` in `src/scheduler/index.ts` (~260).** On a refused lock it logs *"already in flight — queued for next cycle."* For cycle-planned triggers that is true (they stay unconsumed and retry). For the **two direct-dispatch callers it is false and there is no retry path at all**:
- **Slack** (`wakeForThread` → `dispatch`): Slack rows are written `to_actor: null` / `channel: 'slack'`, and the cycle's scan has always excluded them. A mention or DM arriving while the agent is awake elsewhere is **dropped**.
- **The daily check-in cron**: dispatches per agent with no `markProcessed`, no `onDispatched`, and no retry.

**Fix the LOG and add a why-comment above `dispatch()` naming both callers. Change no behavior** — the spec deliberately asks for no Slack retry, and adding one would re-derive settled design. Content is not lost (Slack mirrors the message and the next message re-composes the whole thread); the defect is that the log will actively mislead whoever debugs this later.

**(iii) Priority case-sensitivity — `senderPriority` in `src/scheduler/dedup.ts` (~109).** `'justin'` is matched case-insensitively; `mains.has(fromActor)` is case-**sensitive**, so a main whose actor name arrives capitalized classifies as a **worker (p3)** and loses the queue to genuinely lower-priority traffic. It cannot bite until this Step wires real inter-agent senders, which is why it was routed here.

**Fix it structurally, not at the call site:** lowercase the incoming actor once, and build `MAINS` from `ACTIVE_AGENTS.map(a => a.toLowerCase())` so the guarantee cannot be defeated by a config value's casing. Keep the injectable `mains` parameter (tests use it) and make the doc comment state that the set is expected lowercase.
