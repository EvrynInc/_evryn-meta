## 1.3 The overload protocol — four named strategies, one forbidden move

**Justin:** *"we need to give the scouts some instruction on how to manage the scenarios where it will overload itself. We just have to be equally clear that they have to tell us precisely how they solved the overload problem — otherwise we know how they're going to solve it: by not reading things they need to. **The default is: read every file on the approved list, in full.** An agent may only depart from that via one of these four, and **must name which one it used, per file:**

1. **Fan out sub-readers** — one per Atlas section, each holding one subsystem in full, parent reconciles. *This is exactly how the Atlas itself was built, so we know it works at this scale.* **Keep them alive as a bench** so a cross-seam question can go to both sides and be reconciled.
2. **Run it instead of reading it** — execute the suite, run `npm run depmap`, fire a probe. (Justin's idea, and a good one: sometimes the way to understand something is to run it.)
3. **Read a bounded slice — but only one the Atlas itself justifies.** Atlas §01 carries a table saying "changing prompt assembly? read `:95–352` and `:407–709`." **A slice with an Atlas citation behind it is a decision; a slice without one is a guess.**
4. **Hard stop** — *"I cannot do this in one head; here is the split I need."*

🚫 **THE ONE FORBIDDEN MOVE, named as forbidden so it has nowhere to hide: *"I PRE-judged this file unlikely to matter."*** It is their default, it is never legitimate, and the per-file disclosure exists to make it impossible to do quietly. *(Justin's wording — "pre-judged," not "judged." ### ✅ THE COORDINATION MECHANISM — settled, and deliberately NOT a mailbox

**Justin asked whether you two need a shared merge-coordination doc. The answer we landed on is no, and the reasoning matters so nobody builds one later:**

**Git already protects two of the three collision modes.** A merge that would overwrite his uncommitted work is **refused** (that happened tonight and it worked). A push race is **rejected** as non-fast-forward. **The one git does NOT catch is a by-path commit sweeping his uncommitted edits in a file you both touched — and worktrees eliminate that**, because neither of you has uncommitted edits in the canonical tree. ⇒ **The dribs-and-drabs collisions a mailbox would catch are the ones that only happen when you are NOT in worktrees.**

🔑 **So the mechanism is just this, immediately before any merge to `main` in a shared repo:**
1. **`git fetch`** — is `origin/main` where you thought?
2. **Check his worktree HEAD** — `git -C ../_evryn-meta-acf rev-parse HEAD`. **If it moved in the last few minutes, he is mid-something; wait.**

**Why this beats a mailbox: a SHA is observable truth; a mailbox line is a self-report that can be stale.** And you would have to be merging within the same *second* for git not to catch it anyway — one of you gets a non-fast-forward rejection, fetches, and re-checks. *(I used exactly this check tonight and it is how I knew ACf was live rather than reaped.)*

✅ **Justin has told ACf to do the same thing, so this is symmetric and agreed — not something you are doing unilaterally.**

🚫 **Do NOT build a lock, a check-in/check-out protocol, or a log of every edit.** They rot, and **a stale lock is worse than no lock because it looks authoritative.**

- 🔴 **`git add <paths>` does NOT scope a commit.** A bare `git commit` afterwards commits the **entire index**. ⇒ **Always put the pathspec on the commit: `git commit -F - -- path/a path/b`.**
- 🔴 **Even a by-path commit takes that file's whole working-tree state.** ⇒ **`git diff <file>` first on anything shared.**

### 🔴🔴 THE SHARPEST §0.5 FINDING OF THE NIGHT — A REAL HOLE IN THE THREE-TRIP DESIGN, AND IT CAUGHT *ME*

**A DERIVE trip is a load PROPOSAL. It is not a load AUTHORISATION. Tonight I treated one as the other, and only the reviewer's refusal to absorb it stopped me.**

**What happened.** Lane E's QC proposed — with good reasoning — a *targeted* runtime load: 6 of 45 `src/` files in full plus a 772-line slice of `classify.ts`, on the Atlas's own routing rows. **I approved it.** It then loaded exactly that, and came back and **refused to let it pass silently:**

> *"THE FULL `src/` SET IS NOT LOADED, AND YOUR BRIEF DOES NOT CARRY THE `#cascade-override` TOKEN… I proposed the scoping myself and still think it is defensible — **but the rule is written precisely to stop me rationalizing my way to that conclusion**, so I am flagging it rather than absorbing it."*

**It was right, and I ran the protocol's own test to check.** The subset carve-out is permitted **only** if all three hold: the spinner has *recently read that full runtime itself* — **I have read ONE `src/` file** · *understands those files well* — **no** · *knows for certain* the subset suffices — **no**. **I fail all three.** The protocol also says in terms that *"this change looks small"* is not a legitimate override case, and *"if you are in even a little doubt: OVER-LOAD."* ⇒ **No token issued. Load expanded to all 45** (the 38 it lacked = 12,266 lines; all 45 carry canaries, so no carve-out was needed).

🔑 **THE MECHANISM, stated so it can be fixed rather than re-hit.** Two-trip loading's guarantee is that *the agent cannot compute relevance during the load.* **The DERIVE trip deliberately gives that ability back** — that is its whole purpose. **What nobody accounted for is the second-order effect: the agent's proposal can carry a NARROWING, and the spinner's approval then LAUNDERS it into a subset carve-out that the spinner had no standing to make.** It does not feel like a carve-out from either seat: the agent proposed it (so it looks like the agent's judgment) and the spinner approved it (so it looks authorised). **Neither party performs the brutal three-condition test, because neither experiences itself as the one taking the carve-out.**

⇒ **The rule this needs, and I recommend it be written into the protocol's three-trip section:** **when reviewing a derived proposal, the spinner must explicitly ask "is this proposal NARROWER than the agent's standing cascade?" — and if it is, that is a subset carve-out, subject to the full three-condition bar and the `#cascade-override` machinery, no matter who first suggested it.** *(Approving a proposal is not a lighter act than issuing an instruction.)*

**Why this is the most valuable thing tonight produced about the design:** the three-trip shape was adopted to stop agents under-loading. **This is a path by which it can cause under-loading instead — quietly, with both parties acting in good faith.** It is exactly the class §0.5 exists to surface, and it was found by the safeguard working, not by the failure landing.
