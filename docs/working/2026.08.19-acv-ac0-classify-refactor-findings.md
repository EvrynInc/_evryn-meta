## 🔴 Six extraction hazards — in descending order of how badly they bite

1. **The tool surface is constructed INSIDE the query engine** (`classify.ts:2690`), and `allowedTools` is hand-maintained at `:2696–2725` **separately** from the `tools:` array at `:2513`. The two must agree or a tool silently fails to register — a documented, empirically-hit bug. ⇒ **Splitting tools from the query engine requires designing a registration seam that does not exist today.** This is the single biggest reason *"just move the tools out"* is not a move.

2. **Three mutable containers passed by reference across the tool/query boundary** — `ThreadScopeContext` (written by a *tool handler*), `NoteTurnContext.keepAlive` (written by the *runtime* before the query starts), `ToolCallContext` (read by every tool handler, the web-guard hook, the halt path, and usage capture). ⇒ **This is the "function every concern calls" — except it is shared mutable state, which is worse, because the coupling is invisible to the type system.**

3. **Two module-level caches with no invalidation** (`:206`, `:246`). A split that ends up importing the composer twice **breaks the byte-identical-prefix property the Anthropic prompt cache depends on** — and that ~90% cost reduction is load-bearing, not incidental.

4. ⭐ **A SECOND import cycle nobody has named.** `classify.ts:91` imports from `security/web-guard.ts`, which imports `type ToolCallContext` back from `classify.ts`. **`import type`, so it erases at compile time and is not a runtime cycle** — but it is a real source edge, and it means **the security layer depends on a type defined in the god-module.** ⇒ **Moving `ToolCallContext` is a prerequisite for moving anything.** Not recorded anywhere before this brief; `dependency-map.md`'s documented blind spots do not cover it.

5. **`noteTurnContext.resolve` is a deliberate dependency inversion** added specifically to dodge a `classify ↔ process` cycle. Any extraction must preserve it or that cycle returns.

6. **Eight files import from here, and they import ACROSS concerns** — `approval/flow.ts` takes prompt-composition *and* the query engine; `email/process.ts` takes six symbols spanning three concerns; `security/web-guard.ts` takes a type. ⇒ **There is no clean single cut**; every consumer needs its imports re-pointed at two or three new modules.

## ⚠️ The promise the refactor must NOT make

**Extracting `classify.ts` does not deliver concurrency.**

The serialization is in the **caller** — `src/email/poll.ts:416` is a plain `for (const email of args.emails)` with `await args.handle(email)`. **You could shatter `classify.ts` completely and Evryn would still process one email at a time.**

This is already written in `BUILD-EVRYN-v0.3.md` and it keeps getting forgotten. **Scoping the extraction as a concurrency win produces a refactor that lands, changes nothing measurable, and reads as a failure.** It is a *precondition* for that work, never a delivery of it.

⚠️ **And the compounding half:** the serial loop is currently acting as a **safety brake** — it structurally bounds the rate at which the spend door is entered, which is *why* a 600/hr velocity ceiling suffices. Removing it is a **safety change, not a performance change**, and per-lane breaker scoping (the thing that would make it safe) is **designed and NOT built**.

### 2. 🔴 MONEY: clearing an env var — not deleting it, CLEARING it — switches BOTH runaway detectors off, silently

**Executed, with a control in the same run.** With `BREAKER_LOOP_SIGNATURE_THRESHOLD=""` and `BREAKER_VELOCITY_CEILING_PER_HOUR=""`:

```
5000 IDENTICAL signatures -> loop detector:  *** NEVER TRIPS ***
5000 attempts             -> velocity:       *** NEVER TRIPS ***
40,000-char exfil URL     -> web guard:      *** ALLOWED ***
cloud-metadata SSRF URL   -> web guard:      denied   <-- still LOOKS alive
```

⭐ **CONTROL, same run, vars UNSET: the loop detector TRIPPED correctly.** ⇒ **Unset is safe; created-then-emptied is not** — the opposite of what anyone would guess, and ordinary operator housekeeping produces the unsafe state. **Mechanism:** `??` catches only `undefined`/`null`, so `""` reaches `parseInt("")` → `NaN`, and every `>=` against `NaN` is false.
