## 1. The problem, in one paragraph

`evryn-team-runtime` is the autonomous harness for Evryn's 8 founding-team agents (ADR-050). It is **dormant by construction** — deployed to Railway, woken by nobody, until the Meta-Meeting. The runtime **deliberately refuses to boot** under several conditions: missing/invalid configuration, a missing database relation, an unavailable workspace clone, a genuine double-run. **Every one of those refusals is correct and we are keeping all of them.** The defect is that they are **completely silent to Slack** — what Justin experiences is a deploy that simply never comes up, with nothing but a log line he would have to go hunting for in Railway. Your job: **make every boot refusal send an emergency Slack ping before the process dies, without changing what refuses or when.**

**Why this matters more than its size suggests:** the next deploy of this runtime is also the deploy that applies two pending migrations (015 + 016). `src/boot/schema.ts`'s guard exists precisely to refuse boot if those have not landed first. So **the first time that refusal ever fires in anger is likely to be a live deploy** — and today it fires into silence.

## 3. What to build

### 3.1 New module — `src/safety/emergency.ts`

Two exports. Keep the whole module free of any `RuntimeConfig` import — that absence is the structural guarantee behind constraint 1 in §4, and a future editor must be able to see it at a glance.

**(a) `sendEmergencyAlert(message, deps?)` — the boot-safe sender.**

- Reads **`process.env` DIRECTLY** — `EMERGENCY_ALERTS_WEBHOOK_URL`. **Never** a parsed `RuntimeConfig`.
- **Injectable dependencies for testability** (the house pattern — `boot/schema.ts` injects its probe, `digest/index.ts` its model call, `boot/singleton.ts` its clock): accept an optional deps object carrying at least `env` (default `process.env`) and `fetchImpl` (default `fetch`). Choose the exact shape; keep it minimal.
- **Missing/empty var → log-only, return normally.** `console.warn` naming **only the variable name**, never a value. This mirrors `src/safety/notify.ts:15–17` exactly. It must **never** throw and must **never** refuse boot (§4 constraint 3).
- **ONE POST attempt, `AbortSignal.timeout(5000)`** — mirroring `notify.ts`'s timeout but **NOT its 3-attempt backoff loop**. Deliberate: `notify` retries because the process keeps running; this process is *dying*, and ~3.5s of backoff before `process.exit(1)` buys nothing and risks the exit.
- **Total function: it never throws.** Wrap the whole body in `try/catch`; on failure `console.error` a token-free line. The `process.exit(1)` downstream depends on this.
- **Secret hygiene (§4 constraint 4):** the webhook URL must appear in **no** log line, **no** error message, **no** thrown value. Log the variable *name* and the message text — never the URL. Note that `fetch` failures can carry the URL in the error; construct the failure log from your own text, not from the raw error object's stringification, or scrub it.

**(b) `handleBootFailure(err, deps?)` — the funnel body, extracted so it is testable.**

This is **ACfb's main structural addition beyond the lane brief, and it exists for one reason:** the await-before-exit ordering (§4 constraint 2) is the single thing most likely to ship a fix that reviews clean and never delivers an alert — and an inline closure inside `boot().catch(...)` **cannot be unit-tested at all**, because nothing exports it. Extracting it is what makes that guard test possible.

Behavior, in this exact order:

1. Compute the message text **once** from `err`, reusing the existing expression at `index.ts:14` (`err instanceof Error ? err.message : String(err)`), so the log line and the alert can never diverge. **Use `.message`, never the stack** — stacks are unreadable on a phone and can carry paths/argv.
2. `console.error` the existing `FATAL: <message>` line **FIRST**. Rationale: the Railway log record must never be traded for the Slack ping — if anything goes wrong downstream, the log is already out.
3. **`await`** the emergency send.
4. `process.exit(1)`.

Take an injectable deps object (`send`, `exit`, `log`) so a test can drive all three and observe their ordering.

### 3.2 `src/index.ts` — wire the funnel

`boot().catch(handleBootFailure)`. Keep this file at its stated size and single job (its header says *"All real logic lives in the modules; this file is dotenv + boot + die-loudly"* — honor that; do not inline the sender here).

**Two things to get explicitly right, and to comment:**

- **The `.catch` handler is now async.** `Promise.prototype.catch` accepts an async handler and returns a promise nothing awaits. That is safe **only because** `handleBootFailure` is total (never throws) and ends in `process.exit(1)`. Write that reasoning into a comment, so the next reader does not "harden" it into something that can swallow the exit — and so nobody later "simplifies" it back to a non-async handler.
- **Never `void` the send.** `void sendEmergencyAlert(...)` followed by `process.exit(1)` kills the request before it lands. This is the exact bug the guard test in §5.1 exists to catch.

## 4. The four hard constraints — non-negotiable, each with a concrete failure behind it

1. **Boot-safe: read `process.env` DIRECTLY; never a parsed `RuntimeConfig`.** `loadRuntimeConfig()` is *itself* one of the things that can throw, so the alert must not depend on its output. This is safe because `dotenv` runs at `index.ts:11`, **before** `boot()` — `process.env` is populated either way. *Failure if ignored: the config-refusal case — the single most likely refusal — becomes the one case that cannot alert.*

2. **AWAIT the send before `process.exit(1)`.** The exit is synchronous; a fire-and-forget `fetch` is **killed before the request lands**. ⚠ **This is the trap most likely to produce a fix that reviews clean, ships, and never delivers a single alert.** It gets the dedicated guard test in §5.1.

3. **The webhook var is OPTIONAL — a missing one must NEVER itself refuse boot.** Otherwise the alerting *for* boot refusals *becomes* a boot refusal — circular, and it would brick every environment that has not set the var yet, including dev. Absent → log-only, exactly how `createNotifier` degrades when `TEAM_ALERTS_WEBHOOK_URL` is unset (`src/safety/notify.ts:15`).

4. **Secret hygiene: the webhook URL must NEVER reach a log line, an error message, or an argv.** House pattern is `src/safety/notify.ts` — it logs the message text and never the URL.

**Also preserve (load-bearing; do not break these on the way through):**

- **`process.exit(1)` still happens, always.** A failed or timed-out alert must never turn a refusal into a hang and must never suppress the exit. Degrade loudly to the existing `console.error`, then exit.
- **The fail-safe posture stays fail-safe.** `boot/env.ts` and `boot/schema.ts` refuse loudly on purpose (ADR-048 pattern). Adding an alert must not add a swallow anywhere in `boot()`.
- **`npm run typecheck` strict-green and `npm test` fully green** before you hand anything back.

## 5. Tests — and the lane law that governs them

> ### ⚠ EVERY new guard test must be watched FAILING against deliberately-broken REAL code before it is trusted.
> Break the thing the test guards → confirm **RED** → restore → confirm **GREEN**. **A test written to guard something in this codebase will, by default, compare that thing to itself and pass green while the bug is live.** This has bitten this exact lane **three times**, including once in a test written to guard the previous instance of the same failure. **You must state, per test, that you did this, naming the exact mutation you made and what the red output was.** A test you cannot report a red run for does not count, and ACfb will re-run the trip.

House conventions: `node:test` + `node:assert/strict`, files at `tests/<topic>.test.ts`, run by `npm test` (`tsx --test tests/*.test.ts`). Put these in **`tests/boot-emergency-alert.test.ts`**. `tests/boot-schema.test.ts` is the closest existing analog for shape (injected probe, boot-refusal semantics) — follow its register, including its header comment recording that it was red-verified.

**5.1 — AWAIT-BEFORE-EXIT (the load-bearing one).** Assert the funnel **awaits** the send before exiting — ordering, not mere occurrence. Make the injected sender record when it *resolves* and the injected exit record when it is *called*, then assert resolve-before-exit.
- **Break-to-red: change `await sendEmergencyAlert(...)` to `void sendEmergencyAlert(...)`.** The test **must** go red.
- ⚠ **A test that only asserts "the sender was called" passes under `void` and is therefore worthless.** If your mutation does not turn it red, the test is wrong — fix the test, not the mutation.

**5.2 — A missing var never refuses boot and never throws.** With `EMERGENCY_ALERTS_WEBHOOK_URL` unset, `sendEmergencyAlert` resolves normally, logs the variable *name*, and makes **no** fetch call. *Break-to-red: make the absent-var branch throw.*

**5.3 — The exit still happens when the send FAILS.** Injected sender rejects; injected fetch rejects; and the timeout path — for each, `handleBootFailure` still calls exit(1) exactly once. *Break-to-red: remove the internal try/catch so the rejection escapes.*

**5.4 — The URL never reaches any log line or error message.** Set a sentinel URL value, force a failure, capture **all** console output, assert the sentinel appears nowhere. *Break-to-red: log the URL in the failure path.*

**5.5 — Message content.** The posted body names **the environment**, **the refusal reason**, and **that the deployment is dead and needs a human**. Include the case where `EVRYN_ENV` is **unset** — it must render as an explicit unknown form, never the string `undefined`. *(That case is real, not defensive: "EVRYN_ENV unset" is itself one of the refusal reasons — precisely the case a parsed config could not have told you.)* *Break-to-red: drop the environment from the message.*

**5.6 — The funnel is uniform across refusal types (the §2.2 sharpening).** Drive `handleBootFailure` with a `SingletonError` and with an `Error('BOOT REFUSED: workspace path does not exist')` — both **post-notifier** refusals — and assert identical handling to a config refusal. This pins that this is one uniform path, not a config-only fix.
