## The CLASS — stated so it is checkable in a codebase I have never read

> **A halt / kill / dormancy signal that is returned as an ORDINARY IN-BAND VALUE — a bare string, a sentinel, a null, a magic number — rather than as a distinct type, a thrown error, or a discriminated union.**
>
> **The consequence: every call site must REMEMBER to check for it, and nothing forces them to.** A pathway that forgets does not crash — **it treats *"we are halted"* as a real answer from the system and carries on**, compiling cleanly with a green test suite.

**Why the class travels even though the instance does not:** it is not about NUL bytes, or Slack, or Postgres. It is about **a safety signal whose type makes the check optional.**

## The instance that produced it, as evidence rather than as the point

In `evryn-backend`, `runEvrynQuery` returns `Promise<string>` and signals a circuit-breaker halt by returning a sentinel string. That signature was **deliberate** — it let existing callers keep compiling when the sentinel was introduced. **The cost showed up later:** `src/notify/slack.ts` calls `runEvrynQuery` and **never checks `isHaltSignal`** — zero references in the file. So during a halt the sentinel flows onward as if it were Evryn's answer, and the operator gets a generic error instead of being told the system is halted.

**Two details that make it a good specimen:** the protocol had **already named this failure in the abstract** (*"a new pathway that calls `runEvrynQuery` and forgets `isHaltSignal` will silently treat a halt as a real, empty answer — compile clean, tests green"*) and it happened anyway; and **only one of several call sites checks**, which is exactly what an optional check produces over time. Tracked as `evryn-backend` SPRINT **Step 117**.

## The question

**Does `evryn-team-runtime` have an analogous shape?** It has its own kill switch and its own dormancy mechanism, so the honest question is:

- **Is any halt / kill / pause / dormancy state communicated to callers as an in-band ordinary value** rather than as a type the compiler can enforce or an exception that cannot be ignored?
- **If so, does every consumer check it — or only the ones whose authors remembered?**

## 🔑 What a "no" would have to rule out

**So the answer is falsifiable rather than reassuring** — a clean "no" should be able to say that either:

- **(a)** the halt/dormancy state is **structurally unignorable** — a distinct type, a discriminated union, or a throw — so a forgetful call site fails to compile rather than failing silently; **or**
- **(b)** there is only **one consumer**, so "every call site checks" is trivially true and stays true only while that remains one.

⚠️ **What would NOT rule it out:** *"the current call sites all check."* **That is the state this product runtime was in right up until a new pathway was added that did not.** The property that matters is whether a *future* call site can forget.
