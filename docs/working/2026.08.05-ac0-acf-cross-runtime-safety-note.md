## §1 — 🔴 CLASS ONE: a swallowed failure lets a cursor advance past data nobody read

**This is the most valuable one, and it's the one I'd check first.**

### What happened in the product

Three ordinary-looking facts composed into silent data loss:

1. A fan-out fetched N records in parallel.
2. **A failed individual fetch caught its own error and returned `null`** — no throw, no alert, no record.
3. **The `null`s were filtered out** before the result reached the code that decides whether to advance the read position.

So the failure never reached the decision. The batch looked complete, the "how many failed?" count stayed at zero, and **the cursor advanced past mail nobody had read.** No retry, no alert, no trace.

### The part that makes it a *class* rather than a bug

**Every health signal stayed green, and that was correct behavior.** The liveness checker keyed on consecutive *errors* — and nothing threw. The heartbeat pinged only after a *successful* poll — and the poll succeeded. **The system truthfully reported perfect health while losing data.** That's what makes this class so dangerous: it isn't a monitoring gap you can close by adding an alarm, because every existing alarm was working exactly as designed.

### ⇒ The question for the team runtime, in checkable form

> **Is there any place where (a) a batch or fan-out processes multiple items, (b) an individual item's failure is caught and converted into a falsy/empty/skipped value rather than propagating, and (c) something downstream then advances a position, marks a batch complete, or writes a "processed up to here" watermark — using a count or a set that the swallowed item never entered?**

Concretely, the shapes I'd grep for in your runtime — **adapt these, they're product-flavored:**
- `Promise.all` / `Promise.allSettled` over a mapped fetch, followed by a `.filter(Boolean)` or `.filter(x => x !== null)`.
- Any `catch { return null }` / `catch { return [] }` inside a function called from a fan-out.
- **Anything that persists a "last seen" marker** — a digest cursor, a last-processed timestamp, a `historyId`-equivalent, a wake watermark, a "threads seen up to" pointer.

**The product's fix, if it's useful as a template rather than a prescription:** the failure was made *structurally visible* — the fetch returns a discriminated result (`ok` / permanently-gone / transiently-failed), transient failures ride up to the position decision and **hold** it, and the hold is bounded on **two** independent budgets so it can't wedge (see §3). The key move was **changing the return contract** so there was somewhere to put "and N of them failed" — the old shape had nowhere.

## §2 — 🔴 CLASS TWO: a paginated API called without pagination, plus a cursor that means "now"

**This one needed no failure at all. Only volume.** I'd argue it's the more likely of the two to exist elsewhere, because it looks completely correct on the page.

### What happened in the product

A list endpoint was called with **no page-size parameter and no page token**, and the loop that should have followed the "next page" token didn't exist. Two facts from the vendor's own type definitions turned that into loss:

1. The page size **defaulted to 100** when unset (the max is 500).
2. The cursor field returned by the response means **"the current position of the whole mailbox"** — *not* "the last record on the page you just received."

So the runtime read page one, never asked for pages two onward, and then **stored a cursor that had jumped past all of them.** Above ~100 new records between polls, everything past the first page was silently skipped. The vendor documents the precondition explicitly — *store the returned cursor only if there was no next-page token* — and the runtime stored it unconditionally.

### ⇒ The question for the team runtime

> **Does the team runtime call any list/history/search API without explicitly setting a page size AND following pagination to completion — and then persist a cursor or watermark derived from that response?**

Three specific things to check, because each is independently sufficient to cause loss:
- **Is a page size set explicitly?** An unset default is a silent ceiling, and defaults change under you on a vendor upgrade.
- **Is the next-page token read and followed?** If the field exists on the response type and nothing reads it, that's the tell.
- **🔴 Does the cursor you persist mean "where I got to" or "where the world is now"?** These are different values and they look identical in a variable named `latestId`. **This is the subtle half** — pagination can be perfect and you can still skip everything if you store a "now" pointer after a partial read.

**Design note worth stealing:** the product's paginator **throws** if it hits its page cap with a next-page token still outstanding, rather than returning a partial set. That's deliberate — a partial return forces every caller to choose between silent loss and an undetectable spin. **Failing loud was chosen over degrading quietly**, and I'd endorse the same default for anything analogous over there.

## §3 — CLASS THREE: the anti-wedge counter-risk (read this before you "fix" anything from §1)

**If you find class one, do not fix it naively — the obvious fix creates a worse bug, and the product nearly shipped it.**

The instinct on finding §1 is: *"make a failure hold the cursor and retry."* But the failing item may be **permanently** gone rather than transiently failing. Hold on every failure and **one dead item holds the cursor forever** — everything piles up behind it, the retry runs every cycle, and **every health signal stays green the whole time.** That is strictly worse than the original bug: the original lost one message; this loses all of them, indefinitely.

**The product's resolution, in principle:**
- **Split the failure taxonomy** — permanently-gone is skipped forever, transient is held. Conflating them is the whole trap.
- **Bound the hold on two independent budgets** — attempt count **and** wall-clock, whichever exhausts first. One alone isn't enough: attempts alone stretch for hours under exponential backoff; wall-clock alone retires too fast during a rapid-poll burst.
- **On retirement, the item is never silent** — a durable record, an escalation, and the position freed. **And the retirement path itself is wrapped so it completes even if its own writes fail** — otherwise you've rebuilt the wedge inside the fire escape.
- **The invariant to hold any design against:** *every item ends in exactly one of three states — succeeded, permanently skipped, or force-retired under a bounded attempt count AND a bounded clock. There is no fourth state, and no state that holds the position indefinitely.*

> **The team-runtime question here is narrower:** if you have anything that retries-and-holds — a wake that defers, a digest that waits for a dependency, a queue item that re-queues — **is its hold bounded on both axes, and is retirement guaranteed to complete?**

## §4 — 🔴 CLASS FOUR: the read-side firewall bypass (this one is AC2's, and it is explicitly unanswered)

**Flagging the asymmetry up front, because it's what makes this easy to wave off: you already answered the WRITE-side analog for the team runtime — it never had a raw-write surface. This is the READ side, and it is a different question.**

### What was found in the product

A column exists that the agent must **never** see — third-party feedback about a person, write-only via a dedicated function, processed only by a background pass. The firewall was enforced with a column-deny **on the generic read path** only.

But a **typed helper** did `select("*")`, returned the whole row, and a tool handler serialized that row into the agent's context **unprojected**. So the firewall held at the door everyone was watching and was open at the one nobody was. **Verified link-by-link at source; the codebase even documents the behavior against itself in the guard module, and its "returnable columns" constant exists solely as the all-but-that-column list — applied only on the generic path.**

Bounded at one in the product: every other tool that could return a user row was swept and all were properly projected.

### ⇒ The question for the team runtime, in checkable form

> **Is there a typed DB helper that does `select("*")` (or otherwise returns a whole row), whose result is then serialized into an agent's context — bypassing a column-level firewall that is applied only at some *other* read path?**

The team runtime has agent-facing DB reads and its own agent-visible tables, **so the question is live there** — that much I'm confident of from the architecture alone. Whether it has a firewalled *column* to bypass, I have no idea. **If it doesn't, the answer is "N/A, no column-level firewall exists" and that's a complete answer** — please say so explicitly rather than leaving it open, because "unanswered" and "answered no" look identical in a status doc six weeks later.
