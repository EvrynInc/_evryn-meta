**The defect.** In `evryn-backend/src/email/client.ts`, `fetchViaHistory` (~lines 237–239) fans out over every message id in the Gmail history delta:

```ts
const messages = await Promise.all([...messageIds].map((id) => fetchMessage(gmail, id)));
```

This is **unbounded** parallelism. `fetchMessage` catches its own errors and returns `null`, and the nulls are then filtered away (`.filter((m): m is EmailMessage => m !== null)`). Because those emails never reach `planPollBatch`, **`transientCount` stays 0 — so the Gmail cursor advances past them.** `fetchCatchUpBatch` (~lines 408–410) carries the **identical** pattern after paginating to completion.

**Why it matters, concretely.** Under Gmail rate-limiting or any transient API failure, affected emails are **silently and permanently lost** — no retry, no alert, no trace, and the cursor has already moved on. This is **invisible at Mark's steady-state ~200/day** and becomes a near-certainty on any burst. **A gatekeeper's first day of forwarding IS a burst** (auto-forwarder switch-on plus whatever backlog rides with it), which means the highest-risk moment for this bug is the exact moment we can least afford it: a dropped introduction we never know we dropped, in front of the pilot gatekeeper.

**Soren's proposed fix (~½ day, DC + QC):** replace the unbounded `Promise.all` with a **bounded-concurrency batch**, and **treat a fetch failure as transient** so it increments `transientCount` and the cursor holds rather than advancing past unread mail. Both call sites.
