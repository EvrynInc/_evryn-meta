### Step 43 — `cycle()`'s time-and-latch layer has no guards. **The design is PRE-DECIDED; do not re-open it.**

Seven pieces of mutable state in `src/scheduler/index.ts` have **zero executed coverage**, because `cycle()` is not exported and cannot be called: its **prologue** opens with `refreshRuntimeLock`, whose failure path ends in `process.exit(1)`, and its **epilogue** re-arms itself in a `finally`.

> 🔴 **DO NOT make `cycle()` callable.** That means owning both the exit path and the self-rescheduling loop, which is a far larger and more dangerous change than these defects warrant. **Extract the DECISION instead** — a pure, exported, `shouldSweep(lastAt, now, intervalMs)`-shaped function the closure calls.
>
> **The precedent is inside the file you are editing.** `scheduler/index.ts` already exports five pure helpers, and **`velocityGate` was extracted for exactly this reason** — a reviewer proved a caller could pass a wrong-but-valid literal, so the decision moved out of the closure to where a test could reach it. **🔴 And the split that decides whether you actually close this — the seven are TWO problems:**
- **Clock-driven** — `lastDigestSweepAt`, `lastDormancySweepAt`, `CYCLE_MS` rescheduling. These fall to an injected `now()`.
- **Latch / lifecycle** — `velocityWarned`, `inFlight`, `stopping`, `cycleTimer`, `pendingWakes`. **No clock injection touches any of these.**

**A fix that only injects a clock closes two and leaves five.** The latch half needs its own extraction — a pure decision over `(verdict, alreadyWarned)` returning **both** whether to fire **and** the next latch value, **so the RESET is testable, not just the fire.** ⚠️ **`velocityWarned`'s reset is the one that matters most: break it and Justin gets exactly ONE spend-velocity warning for the entire life of the process, then silence — while the gate keeps working perfectly and every test stays green.**

### Step 44 — one failing thread halts dormancy fleet-wide, silently

`sweepDormantThreads`' loop has **no try/catch**, so one throwing thread exits the loop *and the function*; the scheduler's caller **swallows the throw** with a `console.warn` and substitutes an empty list, taking the outstanding set with it; and the function takes **no `Notifier`**, so it cannot alert even if it wanted to.

**It fails SAFE** — digests stay up, nothing vanishes — **which is exactly why it would sit undetected forever.** The visible symptom is that threads simply stop closing.

**Its sibling `sweepThreadDigests` already does this right**, ending with per-thread `.catch()` isolation. **Match it, and route a real alert.**

### Step 50 — the serial closing-walk vs the 90-second singleton-lock window

The same loop walks closing threads **one at a time with two awaited round-trips each**, inside the cycle that refreshes the singleton lock — so a long enough sweep lets the lock go stale and another boot reclaims it, at which point this process exits.

**📌 Severity was corrected DOWN on 2026-08-11 and you should honour that:** at one active agent and a few dozen threads this is nowhere near firing. **It is in your scope only because it lives in the loop Step 44 is already opening** — fix it while you are there, do not let it expand the lane. Bound the per-sweep work (process at most N and let the next sweep continue — every phase is already idempotent) and/or batch the two per-thread reads.

### Step 7 — dormant→live revival

Nothing transitions a thread's state back to `live`, so a re-activated dormant room never returns to anyone's ambient digest. **Do it in the sweep, not in the database trigger** — the sweep already runs on a cadence and already owns this lifecycle; deterministic, testable, one place, no migration.

> 🔴 **REVIVAL MUST ALSO CLEAR THAT ROOM'S `thread_dormancy_writes` COMPLETION ROWS.** Those rows mean *"this agent has written its closing memory for this room."* **If a room half-closes, revives, and later closes again, every member already marked complete is SKIPPED — they get no memory of the room's second life, and the room can never fully close again.** A seam comment marks the spot.

✅ **Justin's requirement — *"if they were in the room when it went dormant, they are in the room when it comes out"* — needs NO work.** Membership rows are untouched by dormancy; the roster never left. **Recorded so you do not build restoration for something already true by construction.**

### 6.3 — Design calls `ACfd` made INSIDE the lane (the pre-decided ones in §3 are honoured, not re-opened)

- **Step 7 — the crash-safe ORDER of revival is: DELETE the completion rows FIRST, THEN flip the state to `live`.** This is not arbitrary and it is the whole safety property. Flip-then-delete leaves a window where a crash produces a **`live` room carrying stale `thread_dormancy_writes` rows** — and revival only ever selects rows whose state is *not* `live`, so nothing would ever come back for them. Those members would then be silently skipped at the room's second close: **exactly the failure Step 7 exists to prevent, reintroduced by its own fix.** Delete-then-flip converges instead: a crash between the two leaves the room still-not-`live` with rows already gone, and the next sweep simply redoes both (the delete is idempotent).
- **Step 7 covers `closing` → `live` as well as `dormant` → `live`.** The runtime already anticipates this: `digest/index.ts`'s dormant transition re-asserts `.eq('state','closing')` specifically so *"a thread revived to 'live' between the scan and this write is NOT dragged into dormant behind its members' backs."* That comment describes a revival path nothing implements.
