## THE BUG

**`~/.claude.json` can hold TWO entries for the same project, differing only in the CASE of the Windows drive letter — and the two Claude Code front-ends read different ones.**

```
c:/Users/<user>/Evryn/Code/_evryn-meta  → hasTrustDialogAccepted: false   ← the VS CODE EXTENSION reads this
C:/Users/<user>/Evryn/Code/_evryn-meta  → hasTrustDialogAccepted: true    ← the `claude` CLI writes this
```

The CLI normalizes the drive letter to **uppercase**; the VS Code extension uses **lowercase**.

**Consequences, all of which look like unrelated bugs:**
- An **untrusted** folder means Claude Code refuses to load that repo's `.claude/settings.json` at all (it can contain hooks, so it is executable config). The allow-list sits on disk, completely inert.
- Accepting the trust dialog in a terminal **genuinely works — and is invisible to VS Code**, which keeps reading its own `false` entry.
- The extension **never shows a trust dialog**, because from its perspective an entry already exists. It just says `false`. So the user has no way to discover or fix this through the UI.

**Net symptom: Justin hand-authorizes every Bash call that touches the network or writes outside the project root, forever, with no way to fix it from the interface.**

## ⚠️ TWO TRAPS THAT WILL MAKE YOU DIAGNOSE THIS WRONG

Read these before you test anything. ACp hit both, repeatedly, and reported three wrong conclusions to Justin because of them.

**Trap 1 — the sandbox masks everything.** Sandboxed commands are **auto-allowed without ever consulting the allow-list**. So a local, read-only, in-project command like `git status` runs **silently even when permissions are completely broken**. It never reaches the permission layer.
- ✅ **Test only with something that ESCAPES the sandbox** — network egress to a non-allowlisted host, or writes outside the project root. The Slack ping is the ideal probe.
- ❌ Never conclude anything from a simple local command running quietly.

**Trap 2 — you cannot see permission prompts; only Justin can.** A tool call returning output does **not** mean it was allowed — it very often means Justin clicked approve. He will frequently do this silently to avoid slowing you down.
- ✅ **Ask him explicitly: "did that prompt you?"** His answer is the only evidence that counts.
- ❌ Never write "permissions verified" off a successful command. ACp did this three times and had to retract each one.

### Step 2 — fix (back up first)

```bash
node -e "
const fs=require('fs'),path=require('path');
const p=path.join(process.env.USERPROFILE,'.claude.json');
fs.copyFileSync(p, p+'.bak-pre-trust-fix');
const j=JSON.parse(fs.readFileSync(p,'utf8'));
const targets=Object.keys(j.projects||{}).filter(k=>/^c:\//.test(k) && /Evryn\/Code/.test(k));
for (const k of targets) j.projects[k].hasTrustDialogAccepted = true;
fs.writeFileSync(p, JSON.stringify(j,null,2));
console.log('set true on', targets.length, 'lowercase-drive entries'); targets.forEach(k=>console.log('  ',k));
"
```

Adjust the `^c:\/` filter if the desktop's *lowercase* variant is the one already `true` — **set the flag on whichever case-variant the VS Code extension is reading.** If in doubt, set it on **both** variants; there is no harm.

**⚠️ Clobber risk:** the running session holds `~/.claude.json` in memory and rewrites it on exit, which can overwrite this edit. On the laptop it survived, but if the post-restart test still prompts, that is what happened. **Fallback:** close VS Code *entirely*, edit `C:\Users\<user>\.claude.json` in Notepad, set the flag by hand, save, reopen.
