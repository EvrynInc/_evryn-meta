## 1. The mission, in one paragraph

`evryn-team-runtime` is the autonomous harness for Evryn's 8 founding-team agents (ADR-050). It is **dormant by construction** — deployed to Railway, woken by nobody, and it stays that way until the Meta-Meeting. The runtime **deliberately refuses to boot** under several conditions (missing configuration, a missing database table, an unavailable workspace clone, a genuine double-run). Every one of those refusals is *correct* and we want all of them. **The defect is that they are completely silent to Slack** — what Justin actually experiences is a deploy that simply never comes up, with nothing but a log line he'd have to go hunting for. **Your job: make every boot refusal send an emergency Slack ping before the process dies, without changing what refuses or when.**

**Why now, and why it matters more than its size suggests:** the next deploy of this runtime is also the deploy that applies two pending database migrations (015 + 016). The schema guard exists precisely to refuse boot if those haven't landed first. So **the first time that refusal ever fires in anger is likely to be a live deploy** — and today it would fire into silence.

## 3. ACf's design position — ONE alert site, at the single funnel

**`src/index.ts:13` — `boot().catch(...)` — is the only top-level catch in the runtime's boot path, and every refusal above lands in it.** Verified: the sole `process.exit` on that path is `index.ts:15`. The only other `process.exit(1)` calls in `src/` are `scheduler/index.ts:349` (a *runtime* exit that already pings — see §6) and `tools/stdio-server.ts:68` (a separate process — see §6).

**So a single boot-safe alert in that catch covers every refusal uniformly — including refusals nobody has written yet.** ACf strongly prefers this to alert calls at N throw sites, for the reason this codebase keeps teaching: a structural invariant beats an instructional one. N sites is a list someone must remember to extend; one funnel cannot be silently bypassed.

**This is a recommendation you may overrule** — you'll have the code in front of you and ACf won't. If you find a reason the funnel is the wrong home, say so and say why.

### The four hard constraints — these are not negotiable, and each has a concrete failure behind it

1. **Boot-safe: read `process.env` DIRECTLY. Never a parsed `RuntimeConfig`.** `loadRuntimeConfig()` is *itself* one of the things that can throw, so the alert must not depend on its output. This is safe because `dotenv` runs at `index.ts:11`, **before** `boot()` — so `process.env` is populated either way. *Failure if ignored: the config-refusal case — the single most likely refusal — is the one case that can't alert.*

2. **AWAIT the send before `process.exit(1)`.** `index.ts:15` exits synchronously inside the catch, so a fire-and-forget `fetch` is **killed before the request lands.** The send must be awaited with a short timeout (`AbortSignal.timeout`, mirroring `src/safety/notify.ts`) and the exit moved after it. **⚠️ This is the trap most likely to produce a fix that reviews clean, ships, and never delivers a single alert.** Treat the exit-ordering as the thing most worth a real guard test.

3. **The emergency webhook var is OPTIONAL — a missing one must NEVER itself refuse boot.** Otherwise the alerting *for* boot refusals *becomes* a boot refusal — circular, and it would brick every environment that hasn't set the var yet (including dev). Absent → log-only, exactly how `createNotifier` degrades when `TEAM_ALERTS_WEBHOOK_URL` is unset (`src/safety/notify.ts:15`).

4. **Secret hygiene: the webhook URL must NEVER reach a log line, an error message, or an argv.** The house pattern is `src/safety/notify.ts` — it logs the message text and never the URL. Note the runtime **already** carries `TEAM_ALERTS_WEBHOOK_URL` (`src/boot/env.ts:181`) for normal ops; the emergency channel is a **separate, new** var. *(Justin's steer, carried from the L9 routing: point it at the product's `#emergency-alerts` — one "something's on fire" channel he already watches beats a second one he doesn't.)*

### Yours to decide (your lane, your design)

- The env var's name.
- Whether to inline the boot-safe sender in `index.ts` or extract a small helper (e.g. beside `safety/notify.ts`) — weigh testability against dragging a dying-process concern into the normal-ops module.
- The message shape. It must at minimum name **which environment**, **the refusal reason**, and **that the deployment is dead and needs a human**. Justin reads this on his phone at an unknown hour; write it for that.
- Whether `.env.example` and `README.md` document the new var. *(ACf's lean: both, yes. An undocumented operational var is how the next deploy quietly has no alerting.)*
- How to test it. **The house pattern is dependency injection** — `boot/schema.ts` injects its probe, `digest/index.ts` injects its model call — so inject the sender rather than making a live HTTP call in a test.

## 7. The lane's LAWS — carry these into every DC and QC brief you write

These were paid for. They are not advice.

1. **This runtime punishes local reasoning almost perfectly.** Behavior is half `src/` and half the **identity files** the runtime composes into each wake — so a `src/`-only load is reasoning about half the system. And defects live in **seams**: a value minted in one file, stored in a second, given meaning by a third. *Every* real defect this lane has found was caught by someone who had loaded the whole runtime; *every* miss came from someone reasoning locally while feeling confident.
2. **Every new guard test must be watched FAILING against deliberately-broken real code before you trust it.** Break the thing the test guards → confirm RED → restore → confirm GREEN. **A test written to guard something in this codebase will, by default, compare that thing to itself and pass green while the bug is live.** This has bitten this exact lane **three times**, including once in a test written to guard the previous instance of the same failure. **Require a per-test statement that this was done.**
3. **A grep is evidence, never a completeness proof.** The sharpest miss in this lane's history was a value minted under a different name that no grep aimed at the obvious term could find.
4. **An adjacent bug found during a build gets ROUTED, not FOLDED.** A build's review attention is aimed at that build; a rider arrives with none of it. Folding a neighbouring fix into item (a) broke a working safety path once already.
5. **Prefer a run-it-and-show-output probe over an argument.** Every real defect here was caught by someone who ran something, not by someone who reasoned well.
