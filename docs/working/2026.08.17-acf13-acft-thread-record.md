## §1 — What you are building, and why it is not optional

**Read `_evryn-meta/docs/decisions/055-thread-as-complete-record.md` in full before anything else. It is the decision and, more importantly, it records the alternatives that were rejected and why — each has been proposed more than once, including by the conductor who then had to be corrected.**

**The problem in one sentence:** every wake is a brand-new conversation, so **anything an agent read last wake is gone this wake** — and it has no signal that it is gone. Justin's statement of it, which is the canonical one: *"you think you know what's in a file — you fucking don't. He'll be lobotomized all the time and won't know it."*

🔴 **The rule that must survive any redesign you propose: DO NOT make this retrievable-on-request.** A query-on-demand shape **re-creates compaction at the file level** — the agent holds a reference, reasons confidently from what it believes the content was, and never queries, **because nothing tells it that it does not know.** If your design has the agent asking for something, it is wrong.

## §2 — Scope: SPRINT Steps 68 and 69

**`evryn-team-runtime/docs/SPRINT-team-runtime-memory.md` §H carries both in full. They are the spec; this brief does not restate them.**

- **Step 68** — full file bodies into the thread in position at first read; diffs in position where content moved; tool calls, results and a bounded distillation of reasoning the same way; **current file contents composed as their own layer so the agent never derives present state from a history of diffs.** Needs a migration (a new `message_type` that is composed into the thread but does **not** wake anyone, does **not** reset the dormancy clock, and does **not** mirror to Slack — two of those three filters already exist for `heartbeat`; **the third is the genuinely new combination**).

## §4 — What will make this hard, so you are not surprised

- **The size question is the design.** Composing full bodies makes wakes bigger *on purpose*. **Justin: *"I'd rather have them smart than cheap any day."*** The cost control is that a body is stored **once** and later reads are diffs — not that anything is omitted.
- **The runtime keeps a content-addressed store of versions so it can compute the next diff.** ⚠️ **That store is runtime-internal working material, NOT an agent-facing feature.** The agent never queries it. **Getting this backwards is exactly the rejected design.**
- **Data governance:** this creates a new durable copy of arbitrary file content in our DB. **Flag it as `NEEDS-JUSTIN` before it ships** — ADR-050's Tier-A/Tier-B rule applies.
- **Retention** ties to the thread lifecycle, dying at dormancy *after* the closing memory has had its chance. ⚠️ **Build the sweep deliberately, never as a scheduled TTL** — the product lane carries a live case where a built-but-never-scheduled deletion job would have destroyed a real backlog the moment someone "closed the gap."
