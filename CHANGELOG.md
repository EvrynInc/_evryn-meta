# Changelog — _evryn-meta (cross-repo docs · dashboard · protocols)

> **Truncation check:** the last line of this file should read `FULL FILE LOADED`. If you don't see it, reload until you confirm the complete file.

**How to use this file:** reasonably concise entries per substantive change to **this repo**. Most recent at top; detail lives in git log.

**What rises to a changelog entry — and who writes it.** An entry records a **deploy or a substantive change** (code, identity, schema, a protocol, a doc, the dashboard) — the unit is a *ship/change*, not a session. **Session-management narration does NOT belong here:** a conductor recounting coordination with its lanes ("answered AC2's notes," re-spin logistics, routine pushes), or in-flight status that hasn't shipped, belongs in handoffs and git — not the changelog. **The AC responsible for a ship owns its entry** and — being contextualized on the work — routes it to each repo the change actually touched.

**Scope — `_evryn-meta`, and read by EVERY AC on load.** This changelog records changes to `_evryn-meta` itself: the Hub + spokes, protocols, ADRs, load cascades, `CLAUDE.md`, and the monitoring dashboard (`_evryn-meta/dashboard`). Every AC skims it on load — it carries changes to their own operating manual, the protocols, and the cascades. **Routing rule:** an entry belongs here **iff the change touched a file in `_evryn-meta`.** A cross-repo change that does **not** touch `_evryn-meta` gets **no** entry here — logging "two other repos changed" is pure noise and doubles what ACs already load per-repo. If a change touched `_evryn-meta` **and** another repo, log the `_evryn-meta` slice here and the other repo's slice there.

**Monthly archive:** at month-end, move the prior month's entries to `docs/historical/changelog-historical/changelog-YYYY-MM.md` (trailing by one month).

**Skim on full-cascade load:** this file's top ~100 lines + section headers (the changelog-skim step in your load cascade points here).

## 2026-08-04 (AC5 — mutation testing codified in ALL THREE agent manuals: running beats reading for CLEARANCES, always in a sandbox)

- **The incident that forced it.** On the Step-96 ingest lane (see `evryn-backend/CHANGELOG.md`, same date), an unguarded invariant **survived TWO full-runtime QC reviews** — both cleared it by *reading*. It died to one deleted line that left **all six suites green**. 🔴 **Reading cannot find an ABSENCE.** When the code is *correct* and the *protection* around it is missing, there is nothing on the page to notice — the file looks right because it is right. The only way to see it is to break the code and observe that nobody complains. The second review returned a GO having **run nothing at all**: no probe, no test, no mutation. Its reasoning was good; an unexecuted check is a **claim**, not a verification. — [AC5 · Justin's call to run a third review]
- **`evryn-quality/CLAUDE.md` (`9bb8e53`)** — the full teaching. *Reading tells you what the system IS; running tells you what is TRUE.* The asymmetry is sharpest on **clearances** (a clearance asserts a negative, which you cannot read your way to), and findings must now say **what was RUN** to establish them; anything cleared by reading alone is labelled *"reasoned, not executed."* New review step; two new entries in Patterns This Role Watches For (**a test helper that RE-IMPLEMENTS the runtime guard it claims to cover** — the disguise that hid this defect; and **a change that BOUNDS one axis of a runaway while silently UNBOUNDING another**). — [AC5 · Justin-vetted]
- **🔴 The guardrail was NOT loosened — Justin caught AC5 about to loosen it.** QC's manual *forbade* modifying state in a reviewed repo, which is exactly why review 2 never mutated. AC5's first draft carved an exception into that rule; Justin stopped it (*"are we getting rid of an important guardrail?"*) — and he was right: the rule protects **three** distinct things (the reviewer/author seam; other agents sharing that tree, whose commits swallow a live mutation and whose branch you'd switch under them; and the fact that **a subagent killed mid-edit restores nothing**, leaving broken code nobody knows about). **The resolution: mutation never needed the reviewed tree — it needs *a copy*.** So the read-only rule is restated as **ABSOLUTE**, and mutation moves to a **disposable sandbox** (`git worktree add --detach`), **provisioned by AC**, who owns worktree lifecycle. Structural rather than instructional — *"restore afterwards"* is a rule to remember under pressure; *"you never have the reviewed tree open"* is a fact about where you're standing. Framed as **measurement, not repair**, so *"surface, don't ship"* is sharpened: QC can now **prove** a coverage gap instead of asserting one. — [Justin's design call]
- **`evryn-dev-workspace/CLAUDE.md` (`f9baedd`)** — extends the existing *"Tests are part of 'done'"* bullet rather than adding a section, because that rule is where the gap lives: **DC wrote two tests on this branch that could never fail, and both satisfied "the feature has tests."** Now: for any test pinning a fix or guarding an invariant, break the line it protects and confirm the verdict **flips**; still-green means a test that can never fail — *worse* than no test, since its name tells the next reviewer the case is covered. Sandbox by default here too (*"it's my own worktree"* is not the safety it appears to be), and report the evidence to AC — *"deleting line X turns 3 checks red"* beats *"I added a test."* — [AC5 · Justin-vetted]
- **`_evryn-meta/CLAUDE.md` (`a0d92f7`)** — one clause on the existing DID-vs-RECOMMENDED rule, since this is that same discipline aimed at the one artifact that isn't what it looks like: **for the claim "this behavior is covered by a test," the proof is a test that FAILS, not one that passes.** Plus sandbox-by-default and the reminder that **AC owns provisioning it for anyone it spins** — the failure that started all this was a reviewer authorized to mutate the *live* reviewed tree because AC hadn't thought it through. — [AC5 · Justin-vetted]
- **Scope discipline, deliberately:** the full teaching lives **once**, in QC's manual; DC and AC carry the short form aimed at their own specific failure. No sandbox machinery for DC (he has his own tree), no new section in AC's manual, and no *"mutate everything"* anywhere — it is scoped to tests guarding a fix or an invariant, since blanket mutation is slow and dilutes the signal. — [AC5]

## 2026-07-28 (ACp — AC permissions ROOT-CAUSED + fixed on the laptop: a drive-letter case split in `~/.claude.json` made every repo's allow-list inert)

- **The bug: `~/.claude.json` held TWO entries per project, differing only in the CASE of the Windows drive letter — and the two Claude Code front-ends read different ones.** The `claude` CLI normalizes the drive letter **uppercase**; the **VS Code extension uses lowercase**. Trust accepted in a terminal therefore lands on `C:/...` and is **invisible** to the extension, which keeps reading its own `c:/...` entry as `false`. An untrusted folder means Claude Code **refuses to load that repo's `.claude/settings.json` at all** (it can carry hooks = executable config), so the allow-list sat on disk completely inert. The extension also **never shows a trust dialog** — from its side an entry exists, it just says `false` — so there was **no way to discover or fix this from the UI**. Net effect: Justin hand-authorized every Bash call touching the network or writing outside the project root, indefinitely. — [ACp · Justin]
- **Fixed on the LAPTOP:** `hasTrustDialogAccepted: true` set on all 7 lowercase-drive Evryn entries (not just `_evryn-meta`, so DC/QC/Lucas sessions rooted in their own repos don't hit the same wall); backup at `~/.claude.json.bak-pre-trust-fix`. Also added **`additionalDirectories: ["C:\\Users\\jbmcg\\Evryn\\Code"]`** to `_evryn-meta/.claude/settings.json` — a real second gap: the allow-list covered the right *tools* but never declared the sibling repos in-scope, so cross-repo work would have kept prompting even after trust was fixed. **Verified by a 7-test battery, zero prompts, Justin-confirmed.** — [ACp]
- **⚠️ TWO DIAGNOSTIC TRAPS codified (this cost most of a session).** (1) **The sandbox masks everything** — sandboxed commands are auto-allowed *without consulting the allow-list*, so a local read-only command like `git status` runs **silently even when permissions are fully broken**; only a command that **escapes** the sandbox (network egress, writes outside the project root) actually tests the allow-list, and the Slack ping is the ideal probe. (2) **AC cannot see permission prompts — only Justin can;** a tool call returning output usually means *he clicked approve*, so "it ran" is worthless as evidence and AC must **ask him explicitly**. The one **self-evidencing** test is a **deny** rule firing (`rm -rf` on a non-existent path coming back *blocked*, not prompted) — a deny can only come from the settings file, so it proves the file is loaded with zero input from Justin. — [ACp, learned the hard way ×3]
